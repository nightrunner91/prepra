# Protocol: Article Focus Fixer

## 1. Назначение

Исправляет две секции в статьях `docs/`:

1. **`## Ключевые тезисы для интервью`** — маркированный список в теле статьи.
2. **`questions`** — массив строк во frontmatter.

**Цель:** после прочтения статьи читатель должен быстро сфокусироваться на действительно важном, а не тонуть в списке из 12+ тезисов и 10 однотипных вопросов.

## 2. Экономия контекста

**НЕ загружай весь текст статьи.** Для работы достаточно:

1. **Frontmatter** — первые строки файла до `---` (получить текущие `questions`, `title`, `section`).
2. **Содержание** (`## Содержание`) — список заголовков секций, чтобы понимать структуру.
3. **`## Ключевые тезисы для интервью`** — текущий список тезисов.
4. **`## Заключение`** — помогает понять, что автор считает главным.

**Алгоритм чтения:**

1. Прочитать первые ~20 строк файла (frontmatter).
2. Найти и прочитать блок `## Содержание` (обычно строки 20-40).
3. Найти и прочитать блок `## Ключевые тезисы для интервью` (через grep по заголовку, читать до следующего `##`).
4. Найти и прочитать блок `## Заключение` (через grep по заголовку, читать до следующего `##`).

Если после анализа этих четырёх блоков непонятно, какие концепции действительно ключевые — только тогда прочитать отдельные секции `##` выборочно.

## 3. Проблемы, которые решает скилл

### 3.1. Переизбыток тезисов

**Типичная проблема:** 10-15 тезисов, каждый пересказывает отдельный факт из статьи.

**Пример плохого списка (12 тезисов):**
```markdown
- `useEffect` выполняется после commit phase.
- Массив зависимостей определяет, когда эффект перезапускается.
- `Object.is` используется для сравнения зависимостей.
- Честные зависимости обязательны.
- Cleanup-функция чистит подписки.
- Cleanup-функция чистит таймеры.
- `useLayoutEffect` синхронный до paint.
- StrictMode вызывает эффект дважды.
- Каждый эффект — одна ответственность.
- Производные данные вычисляйте в рендере.
- В React 19 предпочтительнее `use()` + `<Suspense>`.
- `useEffect` нельзя вызывать условно.
```

**Что не так:** слишком много пунктов, многие — мелкие детали (`Object.is`, "чистит таймеры" отдельно от "чистит подписки"), дублирование с вопросами.

**Пример хорошего списка (6 тезисов):**
```markdown
- `useEffect` выполняется после commit phase; массив зависимостей через `Object.is` определяет перезапуск. Честные зависимости обязательны — иначе stale closure.
- Cleanup-функция освобождает подписки, таймеры и AbortController перед повторным запуском и при размонтировании.
- `useLayoutEffect` синхронен до paint (для измерений DOM); `useEffect` асинхронен после paint.
- StrictMode вызывает эффект дважды в dev — это выявляет проблемы с очисткой, а не баг.
- Один эффект — одна ответственность; производные данные вычисляйте в рендере, а не в `useEffect`.
- В React 19 для загрузки данных предпочтительнее `use()` + `<Suspense>`, а не `useEffect` + `useState`.
```

**Что улучшилось:** объединены смежные пункты, убраны микро-детали, каждый тезис — законченная мысль.

### 3.2. Точечные и повторяющиеся вопросы

**Типичная проблема:** вопросы проверяют знание одного факта, дублируют друг друга или тезисы.

**Пример плохих вопросов:**
```yaml
questions:
  - "Когда срабатывает useEffect"
  - "Чем useEffect отличается от useLayoutEffect"
  - "Что такое массив зависимостей"
  - "Как работает Object.is в зависимостях"
  - "Что такое stale closure"
  - "Зачем нужна cleanup-функция"
  - "Что обязательно чистить в cleanup"
  - "Почему нельзя вызывать async напрямую"
  - "Как StrictMode влияет на useEffect"
  - "Почему производные данные лучше в рендере"
```

**Что не так:** 10 вопросов, многие — про один и тот же аспект (cleanup упоминается дважды), некоторые слишком узкие (`Object.is`), все — фактологические ("что", "когда", "зачем").

**Пример хороших вопросов:**
```yaml
questions:
  - "Как useEffect связан с commit phase и почему зависимости сравниваются через Object.is"
  - "Что такое stale closure в контексте useEffect и как его предотвратить"
  - "Чем useLayoutEffect отличается от useEffect и когда какой выбирать"
  - "Почему StrictMode вызывает эффект дважды и как это помогает найти баги"
  - "Почему производные данные нельзя вычислять в useEffect"
```

**Что улучшилось:** 5 вопросов вместо 10, каждый — концептуальный, покрывает широкую тему, нет повторов.

## 4. Критерии качественных тезисов

### Количество

**5-7 тезисов.** Не больше. Если получается 8+ — значит, есть дублирование или слишком мелкие пункты.

### Содержание

Каждый тезис должен отвечать на вопрос: **"Если бы на интервью спросили 'Расскажите про X из этой статьи', что бы я ответил одним предложением?"**

**Тезис — это:**
- Законченная мысль (не обрывок).
- Ключевая концепция, а не деталь реализации.
- Объединение 2-3 связанных фактов в одно предложение, если они логически связаны.

**Тезис — это НЕ:**
- Пересказ секции статьи.
- Описание одного API-метода или одной строки кода.
- Факт, который можно найти в документации за 10 секунд.

### Формат

- Маркированный список (`-`).
- Каждое предложение — 1-2 строки, не больше.
- Допустимы `code`-вставки для имён API, хуков, типов.
- Не начинать с "Эта статья...", "В статье рассматривается...".

## 5. Критерии качественных вопросов

### Количество

**5-8 вопросов.** Не больше.

### Типы вопросов

Хорошие вопросы проверяют **понимание**, а не **запоминание**:

| Плохо (факт) | Хорошо (понимание) |
|---|---|
| "Что такое useEffect" | "Как useEffect связан с жизненным циклом компонента и commit phase" |
| "Сколько осей у Flexbox" | "Как алгоритм распределения пространства в Flexbox объясняет поведение flex-grow и flex-shrink" |
| "Что делает Partial<T>" | "Как mapped types позволяют создавать utility-типы вроде Partial и Required" |

**Формулы хороших вопросов:**
- "Как X связан с Y и почему это важно"
- "Почему X работает именно так, а не иначе"
- "Чем X отличается от Y в контексте Z"
- "Что произойдёт, если сделать X, и почему"
- "Как X решает проблему Y"

### Покрытие

Вопросы должны покрывать **все основные секции статьи**, а не одну. Проверь: каждый вопрос отсылает к отдельному блоку знания. Если два вопроса можно ответить, процитировав один абзац — они дублируются.

### Отсутствие повторов с тезисами

Тезисы и вопросы **дополняют** друг друга, а не дублируют. Тезис даёт ответ, вопрос — проверяет, понял ли читатель.

**Плохо:**
```markdown
# Тезис:
- Cleanup-функция чистит подписки и таймеры.
# Вопрос:
- "Зачем нужна cleanup-функция"
```

**Хорошо:**
```markdown
# Тезис:
- Cleanup-функция освобождает подписки, таймеры и AbortController перед повторным запуском и при размонтировании.
# Вопрос:
- "Что произойдёт, если не вызвать cleanup-функцию при размонтировании компонента с подпиской"
```

## 6. Алгоритм работы

### Шаг 1. Извлечь нужные блоки

1. Найти строку `## Ключевые тезисы для интервью` (grep).
2. Прочитать от этой строки до следующей `##` (или конца файла).
3. Из frontmatter извлечь `questions`.
4. Из `## Содержание` извлечь заголовки секций.
5. Из `## Заключение` извлечь ключевые выводы.

### Шаг 2. Проанализировать тезисы

1. **Посчитать** текущее количество. Если > 7 — нужно сокращать.
2. **Найти дубликаты** — тезисы, которые говорят об одном и том же разными словами.
3. **Найти микро-пункты** — тезисы про одну деталь (одна строка API, один флаг). Объединить с соседними.
4. **Найти пересказ** — тезисы, которые просто повторяют содержание секции. Заменить на синтез.
5. **Сгруппировать** тезисы по темам (какая тема из статьи закрывается какими тезисами).
6. **Сократить** до 5-7 тезисов, объединяя смежные.

### Шаг 3. Проанализировать вопросы

1. **Посчитать** текущее количество. Если > 8 — нужно сокращать.
2. **Найти повторы** — вопросы, которые можно ответить одним предложением.
3. **Найти фактологические** — "что такое X", "сколько Y". Переформулировать в концептуальные.
4. **Проверить покрытие** — все ли основные секции статьи покрыты вопросами.
5. **Проверить дублирование с тезисами** — если вопрос полностью повторяет тезис, переформулировать.
6. **Сократить** до 5-8 вопросов.

### Шаг 4. Записать изменения

1. **Тезисы:** заменить содержимое секции `## Ключевые тезисы для интервью` в файле.
2. **Вопросы:** заменить массив `questions` во frontmatter.

**Важно:** не менять ничего больше в файле. Только эти два блока.

## 7. Пример трансформации

### Было

**Frontmatter:**
```yaml
questions:
  - "Что такое Event Loop"
  - "Что такое стек вызовов"
  - "Что такое Web API"
  - "Что такое макрозадачи"
  - "Что такое микрозадачи"
  - "Чем setTimeout отличается от queueMicrotask"
  - "Что такое process.nextTick"
  - "Что делает requestAnimationFrame"
  - "Что блокирует Event Loop"
  - "Как Event Loop связан с React"
```

**Тезисы (10 штук):**
```markdown
- Event Loop — это механизм обработки задач в JavaScript.
- Стек вызовов — структура данных для отслеживания выполнения функций.
- Web API — интерфейсы браузера: setTimeout, fetch, DOM.
- Макрозадачи — setTimeout, setInterval, I/O, UI rendering.
- Микрозадачи — Promise, queueMicrotask, MutationObserver.
- Микрозадачи выполняются все до конца перед следующей макрозадачей.
- setTimeout(fn, 0) выполняется не сразу — ждёт освобождения стека и микрозадач.
- process.nextTick в Node.js имеет приоритет выше микрозадач.
- requestAnimationFrame вызывает callback перед repaint.
- Event Loop блокируют длинные синхронные операции.
```

### Стало

**Frontmatter:**
```yaml
questions:
  - "В каком порядке выполняются синхронный код, микрозадачи и макрозадачи, и почему это важно для Promise"
  - "Почему setTimeout(fn, 0) выполняется не сразу и как это связано с Event Loop"
  - "Чем queueMicrotask отличается от setTimeout и когда что использовать"
  - "Что блокирует Event Loop и как это влияет на UI в браузере"
  - "Как Event Loop определяет поведение async/await и хуков React"
```

**Тезисы (6 штук):**
```markdown
- Event Loop обрабатывает задачи в порядке: синхронный код → все микрозадачи (Promise, `queueMicrotask`) → одна макрозадача (`setTimeout`, I/O) → снова микрозадачи.
- `setTimeout(fn, 0)` не выполняется сразу: callback ждёт освобождения стека, завершения всех микрозадач и минимальной задержки (~4 мс).
- `queueMicrotask` имеет приоритет выше `setTimeout`: микрозадачи выполняются до следующей макрозадачи, а `process.nextTick` (Node.js) — ещё выше.
- `requestAnimationFrame` синхронизирует callback с repaint (~60 FPS), поэтому анимации не дёргаются.
- Event Loop блокируют длинные синхронные операции и бесконечные цепочки микрозадач; для тяжёлых задач — Web Workers.
- Event Loop определяет порядок выполнения `async/await` и хуков React: промисы — микрозадачи, поэтому `setState` в `useEffect` batching.
```

## 8. Ограничения

- **Работать с одной статьёй за раз.**
- **Не менять ничего кроме тезисов и вопросов.** Текст статьи, код, примеры, другие секции — не трогать.
- **Не добавлять новую информацию.** Только синтезировать из существующего текста.
- **Не менять frontmatter кроме `questions`.** `title`, `section`, `order`, `tags`, `description` — не трогать.
- **Сохранять язык статьи.** Если статья на русском — тезисы и вопросы на русском.
