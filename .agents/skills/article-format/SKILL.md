# Protocol: Article Format Standardizer

## 1. Обзор

Приводит статьи из `docs/` к единому формату подачи материала. Каждая статья должна следовать чёткой структуре, чтобы читатель мог быстро найти нужную информацию и подготовиться к интервью.

## 2. Идеальная структура статьи

```
---
title: "..."
section: ...
description: "..."
order: N
tags: [...]
questions:
  - "Вопрос 1"
  - "Вопрос 2"
---

# Заголовок

Вводная часть на 2-4 предложения. Кратко описывает о чём статья,
зачем это нужно и что читатель узнает.

## Содержание

1. [Секция 1](#якорь-1)
2. [Секция 2](#якорь-2)
3. ...

---

## Секция 1

Содержимое секции...

## Секция 2

Содержимое секции...

---

## Ключевые тезисы для интервью

- Тезис 1
- Тезис 2
- ...

## Заключение

Краткое резюме статьи (3-7 предложений или нумерованный список ключевых выводов).

## Полезные ссылки

- [Название](url)
- [Название](url)
```

## 3. Требования к каждой секции

### Frontmatter

Не изменять `section`, `order`. Добавление `questions` — разрешено и обязательно. Исправление `tags` — обязательно, если текущие теги некорректны.

**Поле `title`** - обязательное.

**Правила:**
- Должно кратко отражать суть статьи
- Не более 6 слов
- Легко считываться визуально и лексически

**Запрещено:**
- Применение шаблонных фраз вроде "Глубокое погружение", "Глубокое понимание", "Руководство для..."
- Применение слишком коротких заголовков из 1-2 слов, не отражающих сути статьи
- Применение излишне длинных заголовков более 8 слов

**Примеры:**

Хорошо ✅

- XSS: анатомия атаки и методы защиты
- Аутентификация и авторизация во фронтенде
- useTransition и useDeferredValue

Плохо ❌

- Гидратация — Глубокое погружение
- Руководство для начинающего Frontend-разработчика
- Next.js как монолит: прямое обращение к базе данных без отдельного API
- Fiber

**Поле `description`** — особое. Это описание для Astro (meta description, карточки, превью). Требования:
- Должно быть осмысленным текстом (1-3 предложения), описывающим тему статьи.
- НЕ должно содержать TOC-подобный контент (`1. [Секция](#якорь)`, списки ссылок).
- НЕ должно быть пустым.
- Если `description` содержит мусор (TOC, ссылки, пустая строка) — **переписать** на основе содержания статьи.
- Максимум ~160 символов (для SEO meta description).

### Теги (`tags`)

Массив строк в frontmatter. Ключевые концепции и технологии статьи — то, по чему читатель ищет нужный материал.

**Правила:**
- 3–6 тегов. Каждый тег — одно ключевое слово или устойчивый термин (дефисы допустимы).
- Теги — это **существительные и технические термины**: названия хуков, API, паттернов, инструментов, концепций.
- Первый тег — главная тема статьи (то, о чём статья в первую очередь).
- Остальные теги — связанные ключевые концепции, технологии, паттерны, которые разбираются в статье.

**Запрещено:**
- Разбивать заголовок на отдельные слова (`"передача", "данных", "через", "дерево"` — мусор).
- Использовать шаблонные фразы: `"глубокое", "погружение"`, `"полное", "руководство"`, `"основы"`, `"продвинутая"`, `"три кита"`.
- Использовать предлоги, глаголы, прилагательные общего характера (`"через"`, "становится", "большие", "клиентских").
- Дублировать section (`section: react` — не значит, что нужен тег `"react"` в каждой статье раздела).

**Примеры:**

Плохо ❌
```
tags: ["usecontext", "передача", "данных", "через", "дерево"]
tags: ["глубокое", "погружение", "data", "fetching", "nextjs"]
tags: ["безопасность", "веб-приложений", "глубокое", "понимание", "фронтендера"]
```

Хорошо ✅
```
tags: ["usecontext", "createcontext", "context", "prop-drilling", "provider"]
tags: ["data-fetching", "nextjs", "ssr", "ssg", "isr"]
tags: ["xss", "csp", "csrf", "sanitization", "vue", "react"]
```

**Алгоритм генерации тегов:**
1. Выделить 1–2 главные технологии/концепции, которым посвящена статья.
2. Выделить 2–4 связанные концепции, паттерны или инструменты, которые разбираются в статье (по заголовкам секций и ключевым терминам в тексте).
3. Каждый тег проверить: если бы читатель искал эту тему, он бы ввёл это слово в поиск? Если нет — тег мусорный.

### Заголовок (H1)

Один H1 в файле. Должен совпадать с `title` из frontmatter.

### Вводная часть

- 2-4 предложения сразу после H1.
- Отвечает на вопросы: **что** это за тема, **зачем** она нужна, **что** читатель узнает.
- Если вводная отсутствует — написать на основе содержания статьи.
- Если вводная есть, но слишком короткая — дополнить.
- Не начинать вводную с определения в стиле «X — это...». Лучше с контекста или проблемы.

### Содержание (TOC)

- Заголовок `## Содержание`.
- Нумерованный список с якорными ссылками на основные секции (##).
- Якоря формируются из текста заголовка: lowercase, пробелы → дефисы, спецсимволы убираются.
- Не включать подсекции (###) в содержание.
- Разделитель `---` после содержания.

### Основное содержание

- Секции уровня `##` — основные разделы статьи.
- Подсекции уровня `###` — внутри секций.
- Каждая секция должна быть самодостаточной.
- Разделитель `---` между крупными секциями (опционально, если секции большие).

### Ключевые тезисы для интервью

- Заголовок `## Ключевые тезисы для интервью`.
- Маркированный список из 6-12 тезисов.
- Каждый тезис — одно предложение, сжатая выжимка ключевого понятия.
- Тезисы должны покрывать всю статью, а не одну секцию.
- Формат: краткое утверждение, без «Эта статья рассказывает о...».

### Вопросы для самопроверки

- Поле `questions` во frontmatter — массив строк.
- 5-10 вопросов, проверяющих понимание ключевых концепций статьи.
- Вопросы должны покрывать всю статью, а не одну секцию.
- Формат: вопрос или проблемное утверждение, на которое читатель должен уметь ответить после прочтения.
- Блок рендерится автоматически из frontmatter — **не добавлять** заголовок `## Вопросы для самопроверки` в тело статьи.
- Если `questions` отсутствует или пуст — **обязательно** добавить.

### Заключение

- Заголовок `## Заключение`.
- 3-7 предложений или нумерованный список ключевых выводов.
- Подводит итог, не добавляет новую информацию.
- Может содержать призыв к практике («Попробуйте...», «Настройте...»).

### Полезные ссылки (опционально)

- Заголовок `## Полезные ссылки`.
- Маркированный список внешних ссылок (MDN, спецификации, официальные доки).
- Формат: `[Название](url)`.
- Если в статье уже есть внешние ссылки — собрать их сюда.
- Если нет — секцию можно пропустить.

## 4. Алгоритм работы

При вызове skill для статьи:

1. **Прочитать статью целиком.** Определить текущую структуру.

2. **Составить чеклист отсутствующих секций:**
   - [ ] Вводная часть
   - [ ] Содержание с якорями
   - [ ] Ключевые тезисы для интервью
   - [ ] Вопросы для самопроверки (во frontmatter)
   - [ ] Заключение
   - [ ] Полезные ссылки
   - [ ] Валидный `description` во frontmatter (не TOC, не пустой)
   - [ ] Корректные `tags` во frontmatter (ключевые термины, не разбитый заголовок)

3. **Переструктурировать статью:**
   - Сохранить весь существующий контент (текст, код, примеры).
   - Переместить секции в правильном порядке.
   - Не удалять информацию — только перорганизовать.
   - Переименовать секции если нужно (например «Best practices» → часть основной структуры).

4. **Добавить отсутствующие секции:**
   - Вводная — написать на основе содержания.
   - TOC — сгенерировать из заголовков ##.
   - Тезисы — извлечь из каждой секции ключевые мысли.
   - Вопросы — сформулировать 5-10 вопросов по ключевым концепциям статьи, записать в frontmatter.
   - Заключение — обобщить выводы.
   - Ссылки — собрать из статьи или добавить релевантные MDN/спеки.
   - Description — если содержит мусор (TOC, ссылки, пустое), переписать как краткое описание темы (1-3 предложения, до 160 символов).
   - Tags — если теги мусорные (разбитый заголовок, шаблонные фразы, предлоги/глаголы), перегенерировать по правилам раздела «Теги».

5. **Проверить:**
   - Якоря в TOC совпадают с реальными заголовками.
   - Нет дублирующегося контента.
   - Тезисы покрывают всю статью.
   - Вопросы для самопроверки присутствуют во frontmatter и покрывают ключевые концепции.
   - `description` во frontmatter — осмысленный текст, не TOC и не пустой.
   - `tags` во frontmatter — ключевые термины и концепции, не разбитый заголовок и не шаблонные фразы.
   - Frontmatter не изменён (кроме добавления `questions`, исправления `description` и `tags`, если они были мусорными).

## 5. Правила якорных ссылок

```
Заголовок                          → Якорь
Что такое BFC                      → #что-такое-bfc
Blue-Green Deployment              → #blue-green-deployment
margin collapse                    → #margin-collapse
box-sizing                         → #box-sizing
CSS Grid Layout                    → #css-grid-layout
```

- Только lowercase.
- Пробелы → дефисы.
- Убрать: кавычки, двоеточия, точки, скобки, вопросительные знаки.
- Дефис в слове сохраняется.
- Кириллица транслитерится или оставляется как есть (допустимо оба варианта, но в рамках одной статьи — единообразно).

### Стало

```markdown
---
title: "Flexbox в глубину: оси, flex-basis, grow/shrink, alignment"
section: html-css
order: 3
questions:

  - "Как `flex-direction` влияет на главную ось"
  - "Чем `justify-content` отличается от `align-items`"
  - "Как `flex-grow`, `flex-shrink` и `flex-basis` распределяют пространство"

образом. Без этого знания невозможно уверенно верстать адаптивные интерфейсы.

## Ключевые тезисы для интервью

- Flexbox — модель одномерной раскладки: ось главная и поперечная.
- `display: flex` создаёт flex-контейнер, прямые дети — flex-элементы.
- `flex-direction` определяет главную ось.
- `justify-content` выравнивает по главной оси, `align-items` — по поперечной.
- `flex-grow`, `flex-shrink`, `flex-basis` управляют распределением пространства.
- `margin` в flex-контексте не схлопывается.
- `min-width: auto` у flex-элементов мешает переполнению.
```

## 7. Ограничения

- **Не менять frontmatter** (`section`, `order`). Добавление `questions` — разрешено и обязательно. Исправление `title` - разрешено, если значение мусорное. Исправление `description` — разрешено, если текущее значение мусорное (TOC, пустое, нечитаемое). Исправление `tags` — обязательно, если текущие теги мусорные (разбитый заголовок, шаблонные фразы, предлоги).
- **Не удалять контент** — только перемещать и дополнять.
- **Не менять смысл** текста при переписывании вводной или заключения.
- **Не добавлять информацию**, которой не было в статье (кроме вводной, заключения и вопросов для самопроверки, написанных на основе существующего текста).
- **Сохранять код, примеры, таблицы, диаграммы** как есть.
- **Работать с одной статьёй за раз.**
