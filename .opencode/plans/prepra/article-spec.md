# Спецификация статьи PrePra

Единый контракт для всех новых статей. Существующие статьи приводятся к нему
постепенно скиллом `article-editor`, но **новые пишутся сразу по нему**.

> Любая статья перед сдачей проходит `article-editor` в режиме `check`
> (минимум) или `structure` + `focus` (если правила ниже нарушены).

---

## 1. Frontmatter

```yaml
---
title: "Fastify: роутинг, хуки и валидация"   # ≤ 6 слов, без «глубокое погружение»
section: backend                              # строго id из config.ts
description: "Как устроен жизненный цикл запроса в Fastify и почему схема-валидация работает быстрее ручной."  # ≤ 160 символов, без TOC
order: 4                                      # уникален внутри раздела
tags: ["fastify", "middleware", "validation", "zod", "plugins"]  # 3–6 терминов
level: 3                                      # 1–5, см. §2
requires: ["http-fundamentals", "node-runtime"]  # slug'и-предусловия, может быть []
project: "notes-api"                          # spine-проект раздела
market: 34.1                                  # опционально: % вакансий из отчёта
questions:
  - "Чем хук onRequest отличается от preHandler"
answers:
  - "onRequest выполняется до парсинга тела... preHandler — после валидации схемы, когда body уже доступен."
---
```

Правила:
- `section` и `order` — обязательны, `order` не дублируется в разделе;
- `level`, `requires`, `project`, `market` — новые опциональные поля схемы,
  backfill существующих статей отдельной задачей, не блокирует контент;
- `questions`: 5–8 штук, покрывают всю статью, а не одну секцию;
- `answers`: ровно столько же, 1–2 предложения, только по содержанию статьи,
  без пересказа вопроса;
- `description`: осмысленный текст, не список ссылок, ≤ 160 символов;
- `tags`: существительные/термины, первый тег — главная тема.

## 2. Пять уровней (`level`)

Уровни — внутренние метки сложности для `requires`, треков и фильтров.
**На сайте они не отображаются** и не создают секций README.

| level | Метка | Объём | Задача статьи | Признак готовности |
|---|---|---|---|---|
| 1 | Зачем | 600–900 слов | мотивация, место темы в системе, что спрашивают на интервью | читатель понимает, зачем читать дальше |
| 2 | Основы | 1500–2200 | минимальный рабочий уровень, без которого не читается код | можно писать простой код по теме |
| 3 | Практика | 2000–2800 | ежедневные задачи, основной код, типичные ошибки | можно делать фичу в продакшене |
| 4 | Эксплуатация | 2000–2800 | отказы, нагрузка, безопасность, наблюдаемость, миграции | можно эксплуатировать и чинить |
| 5 | Экспертиза | 2000–2500 | трейд-оффы, кейсы «как бы ты спроектировал», сравнение подходов | можно защитить решение на интервью |

Правила уровней:
- в разделе уровни идут по возрастанию `order`, без прыжков 1 → 4;
- `requires` не должен ссылаться на статью с большим или равным `level`;
- L5 не вводит новые базовые понятия — только усложняет и сравнивает;
- если тема не тянет на L4/L5 — лучше 3 хорошие статьи, чем 5 водянистых.

**Целевой объём новых статей — 2–2.5k слов** (текущая средняя по репозиторию
3.3k). Бэкенд-темы лучше работают как плотный текст + код + задача.

## 3. Структура тела

```markdown
# <title>

Вводная: 2–4 предложения. Не начинать с «X — это...».

## Содержание

1. [Секция](#секция)
2. ...

---

## Секция

...

## Практика

**Проект:** `notes-api` · **Шаг:** 04 · **Ветка:** `step-04-fastify`

Что сделать, в 3–7 пунктах. Критерии готовности: что должно работать,
какой запрос/тест подтверждает.

## Ключевые тезисы для интервью

- 5–7 тезисов, по одному предложению.

## Заключение

3–7 предложений или нумерованный список выводов. Без новой информации.

## Полезные ссылки

- [Название](https://...)
```

Блок `## Практика` — единственное разрешённое расширение канона, он должен
попасть в TOC. Скилл `article-editor` сохраняет его при нормализации структуры.

Требования к коду:
- рабочий пример, не псевдокод; версии указывать (`Node 22`, `Fastify 5`);
- на L3–L5 минимум 2 блока кода: «как делают» и «как ломается»;
- никаких `// TODO` и заглушек в примерах;
- SQL — в верхнем регистре ключевых слов, с реальными именами таблиц проекта.

## 4. README раздела

Три секции — устоявшееся деление, менять его нельзя:

```markdown
# Node.js и API

Один абзац: что раздел даёт и зачем он фронтендеру.

## Начни с базы            <!-- level 1–2 -->
1. **[Зачем фронтендеру Node](./why-node-for-frontend.md)** — ...
2. ...

## Углубись в детали       <!-- level 3–4 и обязательные level 5 -->
- **[Fastify: роутинг, хуки и валидация](./fastify-basics.md)** — ...

## Не будет лишним         <!-- опциональное, нишевое, устаревающее -->
- ...
```

Соответствие уровней и секций:

| Секция README | `level` | Что туда попадает |
|---|---|---|
| Начни с базы | 1–2 | мотивация и минимальный рабочий уровень |
| Углубись в детали | 3–4 | основной рабочий материал и production-темы |
| Углубись в детали | 5 | только обязательные senior-темы: кейсы System Design, code review |
| Не будет лишним | 5 | опциональное и нишевое: микрофронтенды, HOC, Preact, React Native |

`level` — это метаданные сложности для фильтров и треков, они **не создают
новых секций README**. Если сомневаешься, куда положить статью — клади по
маршруту чтения, а не по формальному уровню.

Правила README:
- нумерация в «Начни с базы» = порядок чтения, совпадает с `order`;
- каждая ссылка — на существующий файл, иначе `parseSectionReadme` потеряет статью;
- описание статьи в README ≠ `description` из frontmatter (можно короче);
- README — часть навигации: статьи, которых нет в README, видны только в конце
  страницы раздела.

## 5. Чеклист перед сдачей статьи

- [ ] `title` ≤ 6 слов, H1 совпадает с `title`
- [ ] `description` ≤ 160 символов, без TOC
- [ ] `tags` 3–6 терминов, без разбитого заголовка
- [ ] `level` и `requires` заполнены
- [ ] TOC покрывает все `##`, якоря рабочие
- [ ] есть `## Практика` со ссылкой на spine-проект
- [ ] 5–7 тезисов, покрывают всю статью
- [ ] `questions` 5–8, `answers` столько же, оба непустые
- [ ] 2+ блока кода на L3–L5, версии указаны
- [ ] нет ссылок на несуществующие файлы
- [ ] статья добавлена в README раздела в правильную секцию
- [ ] прогнан skill `article-editor` (режим `check` минимум)
- [ ] `npm run build` зелёный

---

## 6. Чего не делать

- не писать «ещё один обзор фреймворка» без задачи и практики;
- не пересказывать официальную документацию — давать решение и ловушку;
- не добавлять раздел, пока нет минимум 3 статей (пустая коллекция ломает сборку);
- не менять `section`/`order` существующих статей без записи в плане фазы;
- не оставлять `answers` пустыми «на потом» — мок-интервью их не подхватит.
