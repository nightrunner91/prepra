# Стратегии рендеринга, SSG, CDN и Edge

Выбор стратегии рендеринга определяет, где и когда собирается HTML: в браузере, на сервере при запросе или заранее при сборке. CDN и Edge Functions добавляют ещё один слой — логику и кэш ближе к пользователю. Статья разбирает компромиссы CSR, SSR, SSG, ISR и PPR с точки зрения деплоя, объясняет, как работают CDN и Edge Functions, и показывает, как Cache-Control управляет кэшированием.

## Почему важна стратегия рендеринга

Когда пользователь открывает страницу, HTML может появиться на экране тремя путями:

- Уже готовый на сервере или CDN — пользователь видит контент сразу.
- Генерируется на сервере в момент запроса — небольшая задержка, но контент актуальный.
- Собирается в браузере из JavaScript — долгая первая загрузка, но максимальная интерактивность после старта.

Выбор стратегии влияет на:

- **SEO** — поисковые роботы предпочитают готовый HTML.
- **Производительность** — время до первого контента и интерактивности.
- **Стоимость инфраструктуры** — серверный рендеринг стоит дороже статики.
- **Актуальность данных** — как часто пользователь видит свежий контент.
- **Сложность деплоя** — не все хостинги поддерживают SSR и ISR.

## Методы рендеринга: краткая сводка

> Подробное сравнение CSR, SSR, SSG, ISR, RSC, Streaming SSR, Static Export и PPR — в статье [Методы рендеринга в Next.js](../performance/rendering-methods.md).

| Метод | Где рендерится | Когда | SEO | Скорость | Актуальность | Сложность деплоя |
|-------|---------------|-------|-----|----------|--------------|------------------|
| CSR   | Браузер       | При запросе | Плохо | Медленная FCP | Всегда | Низкая |
| SSR   | Сервер        | При запросе | Отлично | Быстрая | Всегда | Средняя |
| SSG   | Сервер сборки | При `build` | Отлично | Максимальная | При сборке | Низкая |
| ISR   | Сервер сборки + фон | При `build` и фоново | Отлично | Максимальная | Периодически | Средняя |
| RSC   | Сервер        | При запросе / сборке | Отлично | Максимальная | Зависит от данных | Средняя |
| PPR   | Статическая оболочка + динамические части | Сборка + запрос | Отлично | Высокая | Всегда (динамические части) | Высокая |

### Основные компромиссы

- **CSR** — простой деплой, но плохой SEO и долгая первая загрузка.
- **SSR** — актуальные данные и хороший SEO, но нагрузка на сервер.
- **SSG** — максимальная скорость и дешевизна, но контент устаревает до следующей сборки.
- **ISR** — баланс скорости SSG и актуальности SSR через фоновую регенерацию.
- **RSC** — меньше JS на клиенте, прямой доступ к backend-ресурсам.
- **PPR** — статическая оболочка + динамические `Suspense`-границы.

## CDN — Content Delivery Network

### Что это

CDN — сеть серверов, размещённых по всему миру, которая отдаёт статический контент с ближайшей к пользователю точки. Вместо того чтобы запрашивать HTML из дата-центра в США, пользователь из Москвы получает его из Москвы или Франкфурта.

```
┌─────────────┐         ┌─────────────────────────────────────────┐
│ Пользователь│         │              CDN                        │
│  из Москвы  │ ──────► │  Москва ──► Франкфурт ──► Лондон ──►   │
│             │         │  origin-сервер (если нет в кэше)        │
└─────────────┘         └─────────────────────────────────────────┘
                                ▲
                                │
                         ┌─────────────┐
                         │   Origin    │
                         │  (основной  │
                         │   сервер)   │
                         └─────────────┘
```

### Что кэширует CDN

- Статические файлы: JS, CSS, шрифты, изображения.
- Сгенерированные HTML-страницы.
- API-ответы — если правильно настроены заголовки.

### Преимущества

- **Низкая задержка** — контент ближе к пользователю.
- **Разгрузка origin-сервера** — повторные запросы не доходят до него.
- **Высокая доступность** — CDN выдерживает пиковые нагрузки.
- **Защита от DDoS** — многие CDN фильтруют вредоносный трафик.

### Популярные CDN

- Cloudflare
- Fastly
- AWS CloudFront
- Vercel Edge Network
- CloudFront (AWS)
- KeyCDN

## Edge Functions и Edge Runtime

### Что это

Edge Functions — это небольшие функции, которые выполняются не на основном сервере, а на узлах CDN, ближе к пользователю. Они запускаются в легковесном runtime, обычно на основе V8 Isolates.

```
┌─────────────┐      ┌─────────────────┐      ┌─────────────┐
│  Пользователь│ ───► │  Edge Location  │ ───► │  Edge       │
│             │      │  (CDN-узел)     │      │  Function   │
└─────────────┘      └─────────────────┘      └──────┬──────┘
                                                     │
                                                     ▼
                                              ┌─────────────┐
                                              │  Origin /   │
                                              │  API        │
                                              └─────────────┘
```

### Отличие от обычных serverless-функций

| Характеристика | Edge Functions | Serverless Functions |
|----------------|----------------|----------------------|
| Расположение | CDN-узлы по миру | Один или несколько регионов |
| Холодный старт | ~0-5 мс | ~100-500 мс |
| Runtime | V8 Isolate (ограниченный) | Node.js (полный) |
| Размер бандла | 1-4 MB | Больше |
| Память | 128 MB | 512 MB - несколько GB |
| API | Web API | Node.js API |

### Когда использовать Edge Functions

- Middleware: аутентификация, геолокация, редиректы.
- A/B тестирование.
- Персонализация на уровне edge.
- Кратковременные API-эндпоинты с низкой задержкой.

### Когда НЕ использовать

- Тяжёлые вычисления.
- Работа с файловой системой.
- Большие зависимости.
- Долгие операции.

### Пример middleware в Next.js

```tsx
// middleware.ts
import { NextResponse } from 'next/server'

export function middleware(request: Request) {
  const country = request.geo?.country || 'US'

  if (country === 'RU') {
    return NextResponse.redirect(new URL('/ru', request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'],
}
```

### Пример в Nuxt

```ts
// middleware/geo.global.ts
export default defineNuxtRouteMiddleware((to, from) => {
  const headers = useRequestHeaders()
  const country = headers['cf-ipcountry'] || 'US'

  if (country === 'RU' && to.path !== '/ru') {
    return navigateTo('/ru')
  }
})
```

## HTTP-заголовки и кэширование

### Cache-Control

Заголовок `Cache-Control` управляет тем, как долго и где хранится ответ.

```http
Cache-Control: public, max-age=0, must-revalidate
```

Значения директив:

| Директива | Значение |
|-----------|----------|
| `public` | Можно кэшировать и в браузере, и на CDN |
| `private` | Кэшировать только в браузере |
| `no-store` | Не кэшировать вообще |
| `no-cache` | Кэшировать, но каждый раз ревалидировать у origin |
| `max-age` | Сколько секунд ответ считается свежим в браузере |
| `s-maxage` | Сколько секунд ответ считается свежим на CDN |
| `must-revalidate` | После истечения срока обязательно проверять свежесть |
| `stale-while-revalidate` | Можно отдавать устаревший ответ, фоново обновляя |

### Примеры

**Статические ассеты с длинным кэшем:**

```http
Cache-Control: public, max-age=31536000, immutable
```

**ISR-страница:**

```http
Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate
```

**Персонализированная страница:**

```http
Cache-Control: private, no-store
```

### ETag и Last-Modified

Для условных запросов сервер может вернуть:

- `ETag` — хэш содержимого.
- `Last-Modified` — время последнего изменения.

Браузер при повторном запросе отправляет `If-None-Match` или `If-Modified-Since`. Если ресурс не изменился, сервер отвечает `304 Not Modified`.

## Как выбрать стратегию

| Сценарий | Рекомендуемая стратегия |
|----------|------------------------|
| Блог, документация, лендинг | SSG или Static Export |
| Маркетинговый сайт с редкими обновлениями | SSG |
| E-commerce | ISR или SSR с кэшем |
| Новостной сайт | ISR или SSR |
| Личный кабинет, дашборд | CSR |
| Персонализированные страницы | SSR или PPR |
| Глобальное приложение с низкой задержкой | SSG + CDN + Edge Functions |
| Админка внутри компании | CSR |

### Практический пример архитектуры

```
┌─────────────────────────────────────────────────────────────┐
│                         Пользователь                         │
└────────────────────┬────────────────────────────────────────┘
                     │
                     ▼
            ┌─────────────────┐
            │   Edge Function │  <- аутентификация, A/B, geo
            │   (middleware)  │
            └────────┬────────┘
                     │
                     ▼
            ┌─────────────────┐
            │       CDN       │  <- кэш статики и ISR
            └────────┬────────┘
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
   ┌─────────┐  ┌─────────┐  ┌─────────┐
   │  SSG    │  │  ISR    │  │  SSR    │
   │  страницы│  │  страницы│  │  страницы│
   └─────────┘  └─────────┘  └─────────┘
        │            │            │
        └────────────┼────────────┘
                     │
                     ▼
            ┌─────────────────┐
            │   API / БД      │
            └─────────────────┘
```

## Ключевые тезисы для интервью

- CSR — простой деплой, но плохой SEO и долгая первая загрузка: весь рендеринг происходит в браузере.
- SSR — актуальные данные и хороший SEO, но нагрузка на сервер при каждом запросе.
- SSG — максимальная скорость и дешевизна: HTML готов при сборке и раздаётся с CDN без участия сервера.
- ISR — баланс SSG и SSR: страница генерируется один раз, фоново обновляется по истечении `revalidate`.
- CDN кэширует не только JS/CSS/изображения, но и HTML-страницы, снижая нагрузку на origin-сервер.
- Edge Functions выполняются на CDN-узлах (~0–5 мс холодный старт) в ограниченном V8 Isolate без Node.js API.
- Middleware (аутентификация, геолокация, A/B-тесты) — типичный сценарий для Edge Functions, не для тяжёлой логики.
- `s-maxage` управляет кэшированием на CDN, `max-age` — в браузере; `stale-while-revalidate` позволяет отдавать устаревший ответ, фоново обновляя его.
- `immutable` в Cache-Control говорит браузеру никогда не перепроверять файл — применяется для ресурсов с хэшем в имени.

## Заключение

Выбор стратегии рендеринга — это компромисс между скоростью, актуальностью, стоимостью и сложностью.

**Ключевые выводы:**

1. **CSR** — для интерактивных приложений без SEO.
2. **SSR** — для персонализации и актуальных данных.
3. **SSG** — для быстрых, дешёвых, SEO-оптимизированных сайтов.
4. **ISR** — для баланса скорости и актуальности.
5. **CDN** — ускоряет доставку любого статического контента.
6. **Edge Functions** — добавляют логику ближе к пользователю, но не заменяют полноценный сервер.

На собеседовании важно не просто назвать аббревиатуры, а объяснить, в каких сценариях что применять и какие компромиссы возникают.
