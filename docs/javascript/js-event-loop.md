# Цикл событий и стек вызовов

Ты написал обработчик клика, который пересчитывает таблицу на сто тысяч строк. Кнопка перестала реагировать, спиннер замер, а в консоли логи идут не в том порядке, в котором ты их написал. Всё это один и тот же механизм: цикл событий. JavaScript выполняет в каждый момент только одну операцию, и всё, что происходит «параллельно», на самом деле ждёт своей очереди. Понимание этой очереди нужно для `async/await`, промисов, хуков React и отладки производительности, а на собеседованиях по порядку вывода спрашивают почти всегда.

## Стек вызовов

Стек вызовов — это место, где JavaScript отслеживает, какая функция сейчас выполняется. Вызвали функцию — она легла на вершину стека. Завершилась — её сняли.

```js
function first() {
  console.log('First');
}

function second() {
  first();
  console.log('Second');
}

function third() {
  second();
  console.log('Third');
}

third();
// First
// Second
// Third
```

Пока на стеке лежит долгая функция, браузер ничего не может сделать: не обработает клик, не нарисует кадр, не примет ответ сервера. Именно поэтому в трассировке ошибки видно «застрявший» стек, а интерфейс «завис». Стек — это единственное место, где выполняется твой код, и он один.

---

## Web API и C++ API

Таймеры, HTTP-запросы и DOM-события не выполняются на стеке. Браузер (или Node.js через C++ API) берёт их на себя и следит за ними сам. Когда операция завершилась, её колбэк ставится в очередь и ждёт, пока стек освободится.

```js
console.log('Start');

setTimeout(() => {
  console.log('Timeout');
}, 1000);

console.log('End');
// Start
// End
// Timeout (через ~1 сек)
```

Здесь `setTimeout` не «заснул» в стеке. Он передал таймер браузеру и сразу вернулся. Через секунду колбэк встал в очередь, а цикл событий, увидев пустой стек, выполнил его.

---

## Макрозадачи

**Макрозадачи** (macrotasks) — это элементы очереди, которые цикл берёт по одному: колбэки `setTimeout` и `setInterval`, `setImmediate` в Node.js, I/O, события UI вроде `click` и `scroll`.

```js
setTimeout(() => console.log('A'), 0);
setTimeout(() => console.log('B'), 0);
// A
// B
```

Макрозадачи идут в порядке поступления. Между двумя макрозадачами цикл может выполнить микрозадачи и при необходимости перерисовать экран.

---

## Микрозадачи

**Микрозадачи** (microtasks) — это более приоритетная очередь. Туда попадают колбэки `.then`, `.catch`, `.finally`, `queueMicrotask` и `MutationObserver`. Главное правило: цикл опустошает очередь микрозадач **полностью** до следующей макрозадачи, включая те, что появились по ходу дела.

```js
console.log('Start');

setTimeout(() => {
  console.log('Timeout');
}, 0);

Promise.resolve().then(() => {
  console.log('Promise');
});

console.log('End');
// Start
// End
// Promise
// Timeout
```

Промис вывелся раньше таймера с нулевой задержкой, хотя таймер был поставлен первым. Таймер ждёт своей макрозадачи, а колбэк промиса уже стоит в микрозадачах, которые выполняются сразу после синхронного кода.

Отсюда следствие, которое стоит помнить: микрозадачи, которые создают новые микрозадачи, не выпускают цикл. Если каждая новая микрозадача ставит следующую, очередь никогда не опустеет, и ни таймеры, ни рендер не получат управления.

## Алгоритм цикла событий

Упрощённо цикл работает так:

1. Выполнить одну макрозадачу из очереди (или весь скрипт при первом запуске).
2. Выполнить **все** микрозадачи, включая появившиеся во время выполнения.
3. Если пора, перерисовать экран (обычно около 60 раз в секунду).
4. Повторить с первого шага.

```js
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

console.log('4');
// 1
// 4
// 3
// 2
```

Синхронный код дал `1` и `4`. Очередь микрозадач дала `3`. Макрозадача дала `2`. Если запомнить эту последовательность, большинство вопросов про порядок вывода решаются за минуту.

Схематично это выглядит так:

```
Стек вызовов ──► пуст? ──► микрозадачи (все) ──► макрозадача ──► рендер (если пора)
     ▲                                                                  │
     └──────────────────────────────────────────────────────────────────┘
```

## Таймер с нулевой задержкой

Многие думают, что `setTimeout(fn, 0)` означает «выполнить сейчас». На деле это «положить callback в очередь макрозадач, как только можно».

```js
console.log('Start');
setTimeout(() => console.log('Timeout'), 0);
console.log('End');
// Start
// End
// Timeout
```

Колбэк запустится, когда синхронный код закончится, все микрозадачи выполнятся и цикл дойдёт до его макрозадачи. Поэтому `setTimeout(..., 0)` часто используют, чтобы отложить работу до конца текущего шага: например, дать браузеру обновить DOM перед тем, как читать размеры элемента.

Задержка тоже не бывает нулевой. Браузер считает вложенность таймеров, и после пяти уровней минимальная задержка становится около 4 мс.

## Рендер и requestAnimationFrame

Браузер обновляет экран примерно 60 раз в секунду. Перед каждым кадром он вычисляет стили, layout, paint и composite. Рендер — это не очередь задач в том же смысле, что макро- и микрозадачи, а шаг цикла, который случается, если задачи успели выполниться и пора рисовать.

`requestAnimationFrame` (rAF) просит браузер вызвать callback перед отрисовкой следующего кадра:

```js
function animate() {
  // обновить позицию элемента
  requestAnimationFrame(animate);
}

requestAnimationFrame(animate);
```

Почему это важно. Анимация на `setTimeout(fn, 16)` приходит в свой момент, который может попасть в середину кадра, и результат выглядит дёрганым. rAF привязан к кадру: callback вызывается ровно перед отрисовкой, а не когда-то рядом с ней. Кроме того, rAF получает `timestamp` и не работает в скрытых вкладках, что экономит батарею.

## queueMicrotask и process.nextTick

### queueMicrotask

`queueMicrotask` ставит функцию в очередь микрозадач явно. Это удобно, когда действие нужно выполнить после текущего синхронного кода, но раньше любых таймеров:

```js
console.log('Start');

queueMicrotask(() => {
  console.log('Microtask');
});

console.log('End');
// Start
// End
// Microtask
```

### process.nextTick (Node.js)

В Node.js есть своя очередь `nextTick`, и она стоит **выше** промисов:

```js
console.log('Start');

process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('Promise'));

console.log('End');
// Start
// End
// nextTick
// Promise
```

Порядок фаз Node.js такой: timers, pending callbacks, poll, check (`setImmediate`), close callbacks. Между колбэками цикл Node очищает сначала `nextTick`, потом микрозадачи. Таймер выполняется раньше I/O-колбэка, только если уже созрел к фазе timers, поэтому порядок относительно I/O не фиксирован. А `setImmediate` внутри I/O-колбэка выполнится раньше таймера, потому что фаза check идёт сразу после poll. А вот порядок `setTimeout(fn, 0)` и `setImmediate` в главном модуле не гарантирован.

Злоупотреблять `nextTick` опасно: если каждый колбэк ставит ещё один, очередь промисов и I/O голодает так же, как с промисами в браузере.

## Что блокирует цикл

Любой долгий синхронный код блокирует цикл, и интерфейс замирает вместе с ним:

```js
// плохо: цикл не выходит никогда
while (true) {}

// плохо: миллионы элементов обрабатываются за один кадр
const huge = Array(10_000_000).fill(0);
huge.map((x) => x * x);
```

Что делать:

- разбивать большую работу на части и отдавать управление между ними через `setTimeout` или `requestIdleCallback`;
- выносить тяжёлые вычисления в Web Workers, у которых свой поток;
- для анимаций использовать `requestAnimationFrame`;
- не создавать бесконечные цепочки микрозадач.

Рабочий приём для длинного списка: обрабатывать по несколько тысяч элементов за шаг, а между шагами отдавать управление браузеру. Пользователь будет видеть прогресс вместо зависшей вкладки.

## async/await и порядок выполнения

Здесь находится основная часть вопросов с собеседований, поэтому разберём механику явно.

`await` делит функцию на две части. Всё, что до первого `await`, выполняется синхронно, сразу при вызове функции. Всё, что после, становится микрозадачей:

```js
async function run() {
  console.log(1);
  await null;
  console.log(2);
}

run();
console.log(3);
// 1
// 3
// 2
```

Вызов `run()` печатает `1` и доходит до `await`. Управление возвращается в вызывающий код, который печатает `3`. Продолжение функции (`2`) ждёт в очереди микрозадач.

Из этого следуют несколько правил, которые часто проверяют:

- **Executor промиса выполняется синхронно.** Код внутри `new Promise((resolve) => ...)` вызывается сразу, а вот колбэки `then` всегда асинхронны, даже если промис уже разрешён.
- **`async` без `await` тоже асинхронен снаружи.** Тело выполнится сразу, но возвращённый промис разрешён, и его `then` попадёт в микрозадачи.
- **Каждый `await` — отдельная микрозадача.** В цикле с `await` каждая итерация продолжается в своей микрозадаче, поэтому вывод перемежается с синхронным кодом только до первого `await`.
- **`finally` и `return` после `await` выполняются в микрозадаче.** Порядок вывода зависит от того, где стоит синхронный `console.log` относительно `await`.
- **Отклонённый промис в `await` попадает в `catch` в микрозадаче.** Синхронный код после вызова `run()` выполнится раньше `catch`.

```js
new Promise((resolve) => {
  console.log(2);
  resolve();
}).then(() => console.log(3));

console.log(4);
// 2
// 4
// 3
```

Executor сработал сразу (`2`), `then` стоит в очереди (`3`) после синхронного `4`. Если ты разбираешь такой пример, сначала выдели синхронные строки, потом микрозадачи, потом макрозадачи.

## Event Loop и React

React 18 использует конкурентный режим: рендер можно прервать и продолжить, чтобы срочные обновления (ввод, клик) не ждали тяжёлого списка. Для этого React сам разбивает работу на части и отдаёт управление циклу событий. Инструменты `useTransition` и `useDeferredValue` помечают обновления как менее срочные.

С `useEffect` важно не путать порядок. Эффекты запускаются **после** того, как React закоммитил изменения в DOM, и обычно после отрисовки браузером. Они ставятся в отдельную очередь задач React, а не в микрозадачи. Поэтому внутри `useEffect` уже можно читать размеры элемента, которые отрисованы на экране.

Обновления состояния из промисов в React 18 батчатся так же, как и в обработчиках событий. Один `setState` внутри `then` не вызывает синхронной перерисовки, а попадает в общую очередь обновлений.

## Ключевые тезисы для интервью

- Порядок вывода: синхронный код, затем все микрозадачи (включая появившиеся по ходу), затем одна макрозадача; поэтому промис выводится раньше `setTimeout(fn, 0)`.
- `setTimeout(fn, 0)` ставит callback в очередь макрозадач: он выполнится, когда стек пуст и микрозадачи выполнены. Это способ отложить работу, а не ускорить её.
- `new Promise` вызывает executor синхронно, а колбэки `then` всегда асинхронны, даже для уже разрешённого промиса.
- Долгий синхронный код и бесконечные микрозадачи блокируют и интерфейс, и таймеры; длинную работу разбивают на части или выносят в Web Workers.
- `requestAnimationFrame` вызывается перед отрисовкой кадра и подходит для анимаций; `setTimeout` на анимации даёт рывки.
- В Node.js `process.nextTick` идёт раньше промисов, а фазы цикла выполняются в своём порядке: timers, poll, check.

## Заключение

Цикл событий объясняет, почему JavaScript кажется непредсказуемым, хотя работает строго по правилам. Стек выполняет один код за раз, таймеры и I/O ждут в своих очередях, микрозадачи выполняются целиком перед следующей макрозадачей, а рендер случается между ними. Если держать эту модель в голове, порядок вывода, поведение `await` и зависания страницы перестают быть загадкой. Главная практическая мысль: не давай ни одному синхронному шагу и ни одной бесконечной очереди занимать цикл дольше, чем нужно.
