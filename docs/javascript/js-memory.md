# Память и производительность

Редактор кода работает полчаса, и вкладка начинает тормозить. Ты открываешь Memory и видишь, что памяти в три раза больше, чем должно быть. Больших массивов в коде нет, и вроде бы всё очищается. Утечка есть, но она не выглядит как утечка: ни одна строка не делает ничего явно неправильного. Чтобы такое найти, нужно понимать одно правило сборщика мусора: объект удаляется, только когда до него уже нельзя дойти. Всё остальное в этой статье — следствие этого правила.

## Стек и куча

Модель из двух областей, стека и кучи, помогает думать о памяти. Это именно модель: спецификация JavaScript о ней не говорит, и каждый движок устроен по-своему. Для поиска утечек важнее другое, поэтому не стоит запоминать, какие значения физически лежат где.

Стек хранит вызовы функций и их локальные переменные. Когда функция завершается, её кадр уходит вместе с переменными:

```js
function calc() {
  let a = 10;
  let b = 20;
  return a + b;
}

calc(); // после вызова кадр функции больше не нужен
```

Куча нужна для объектов и массивов, которые живут дольше одного вызова:

```js
function createUser(name) {
  return { name };
}

const user = createUser('Alice');
```

После выхода из `createUser` параметр `name` исчезает, а объект остаётся, потому что на него ссылается `user`. Именно эта ссылка определяет, жив объект или нет.

Размер стека ограничен. В V8 это порядка мегабайта, и бесконечная рекурсия исчерпывает его:

```js
function infinite() {
  infinite();
}

infinite(); // RangeError: Maximum call stack size exceeded
```

Куча больше, но её тоже можно исчерпать, и почти всегда причина в накапливающихся ссылках.

## Сборка мусора

**Сборка мусора** (Garbage Collection, GC) — это процесс, который находит память, которая программе больше не нужна, и возвращает её движку. В Chrome и Node.js это V8, в Firefox SpiderMonkey, в Safari JavaScriptCore.

Правило одно: **объект живёт, пока до него можно дойти от корней**. Корни — глобальный объект, стек вызовов и регистры. Замыкание корнем не является. Оно удерживает объекты потому, что его функция достижима и хранит ссылки на свою область видимости.

```js
let user = { name: 'Alice' };
user = null;

// объект { name: 'Alice' } больше не достижим, GC может его освободить
```

Явно запустить сборку нельзя. В Node.js есть `global.gc()`, но он доступен только с флагом `--expose-gc` и нужен для диагностики, а не для работы в продакшене.

Из правила следует важный вывод. Сборщик не ошибается и не «пропускает» мусор. Если объект не освободился, значит, до него всё ещё можно дойти. Задача разработчика — найти, какая ссылка это делает.

## Поколения и алгоритм Mark-and-Sweep

Большинство объектов живут недолго: временные массивы, промежуточные результаты, объекты внутри одной функции. Поэтому современные движки делят кучу на поколения.

**Молодое поколение** чистится часто и быстро, обычно алгоритмом Scavenge. Большая часть объектов умирает именно здесь, и это дешёвая операция.

**Старое поколение** содержит объекты, которые пережили несколько циклов. Для него используется Mark-and-Sweep:

1. **Mark.** Движок обходит граф от корней и помечает всё, что достижимо.
2. **Sweep.** Непомеченное считается мусором, и его память возвращается в пул.

Полная сборка старого поколения иногда приостанавливает выполнение кода. Это пауза stop-the-world. Современные движки уменьшают её, разбивая работу на части и выполняя её параллельно, но сам факт паузы никуда не делся.

Отсюда практичный вывод: создание лишних объектов в горячих циклах и хранение ненужных данных увеличивают нагрузку на сборщик. Для кэшей и подписок лучше слабые коллекции, о которых пойдёт речь ниже.

## Типичные утечки памяти

Утечка — это объект, который уже не нужен программе, но до которого ещё можно дойти. Сборщик здесь бессилен: он делает ровно то, что ему положено. Ниже шесть ситуаций, где такая ссылка появляется почти незаметно.

### 1. Глобальные переменные

Данные, которые сохранили в `window` для отладки, живут до закрытия вкладки:

```js
function loadReport() {
  window.report = new Array(10_000_000).fill('x');
}
```

`window` — корень, поэтому массив не освободится, даже если на странице о нём никто не помнит. Ту же проблему создаёт неявная глобальная переменная в нестрогом режиме: присвоили `total = 0` без `let`, и переменная стала свойством глобального объекта. Решение: `let` и `const`, strict mode и отказ от глобального хранилища для временных данных.

### 2. Слушатели на долгоживущих целях

Частая ошибка выглядит безобидно. Компонент монтируется, подписывается на изменение окна, и никто не снимает подписку:

```js
function mountPanel() {
  const panel = document.getElementById('panel');

  window.addEventListener('resize', () => {
    panel.style.width = `${window.innerWidth / 2}px`;
  });
}
```

Панель удалена из DOM, но `window` всё ещё держит обработчик. Обработчик ссылается на `panel`, поэтому узел остаётся в памяти. Сам по себе элемент никто не удерживает, его держит подписка.

Решение: снимать подписку при удалении компонента. Удобнее всего `AbortController`, потому что одним `abort()` снимаются все слушатели, привязанные к его сигналу:

```js
function mountPanel() {
  const panel = document.getElementById('panel');
  const controller = new AbortController();

  window.addEventListener(
    'resize',
    () => {
      panel.style.width = `${window.innerWidth / 2}px`;
    },
    { signal: controller.signal },
  );

  return () => controller.abort();
}

const unmount = mountPanel();
// при удалении панели:
unmount();
```

### 3. Замыкания, которые захватывают лишнее

Замыкание удерживает переменные из своей области видимости. В V8 переменные, которые захватывает хотя бы одно замыкание, живут в общем контексте функции. Поэтому один захваченный объект удерживает все переменные этого контекста:

```js
function setup() {
  const big = new Array(1_000_000).fill('data');

  window.onclick = () => console.log('clicked');

  function sizeOfBig() {
    return big.length;
  }
}
```

Обработчик `onclick` не использует `big`, но `sizeOfBig` захватил эту переменную, и массив остаётся в памяти, пока жив `window.onclick`. Решение: не объявлять лишние вложенные функции с захватом больших данных, а тяжёлое держать только там, где оно нужно.

### 4. Таймеры и интервалы

Интервал, который никто не останавливает, держит своё замыкание навсегда:

```js
const data = { value: 'important' };

setInterval(() => {
  console.log(data.value);
}, 1000);
```

Пока интервал работает, `data` и колбэк живут. В компоненте это особенно коварно: интервал продолжает тикать после того, как компонент размонтирован. Решение: `clearInterval` и `clearTimeout` в момент размонтирования.

### 5. Отсоединённые DOM-узлы

Удаление элемента из страницы не освобождает его, если в коде осталась ссылка:

```js
const element = document.getElementById('node');
element.remove();

// пока переменная element жива, узел в памяти
```

Такие узлы в инструментах DevTools называют detached. Они выглядят как пропавшие с экрана, но память под ними занята. Решение: не хранить ссылки на узлы, которые удалены из страницы, или обнулять их.

### 6. Кэши без ограничений

Кэш, который только добавляет записи, растёт без предела:

```js
const cache = new Map();

function getData(key) {
  if (cache.has(key)) return cache.get(key);

  const data = fetchData(key);
  cache.set(key, data);
  return data;
}
```

`Map` держит ключи и значения сильно, поэтому записи никогда не уходят. Решения две. Первое: ограничить размер и вытеснять давно неиспользуемые записи (LRU). Второе: если ключи — объекты, брать `WeakMap`. Тогда запись исчезает, когда объект-ключ становится недостижимым.

## Инструменты для поиска утечек

### Chrome DevTools — Memory

Вкладка Memory даёт три инструмента:

- **heap snapshot** — снимок кучи, по которому видно, что занимает память;
- **allocation timeline** — запись выделений во времени, чтобы понять, когда память растёт;
- **allocation sampling** — лёгкое профилирование выделений.

Чаще всего нужен один приём: сравнение снимков. Порядок такой:

1. Открой приложение и сделай первый снимок.
2. Повтори подозрительное действие несколько раз, например открой и закрой модалку пять раз.
3. Сделай второй снимок и выбери сравнение.
4. Посмотри, что растёт. Если после закрытия модалки остаются её компоненты или detached-узлы, модалка течёт.

### Node.js — `--inspect`

```bash
node --inspect index.js
```

После этого можно подключить Chrome DevTools к процессу Node и снимать его снимки кучи тем же способом.

## `WeakRef` и `FinalizationRegistry`

`WeakRef` и `FinalizationRegistry` появились для случаев, когда нужна слабая ссылка на объект. Они не держат объект живым, но и не гарантируют, что он останется.

### `WeakRef`

`WeakRef` хранит слабую ссылку. Прочитать объект можно через `deref()`, и если его уже собрали, результат будет `undefined`:

```js
let user = { name: 'Alice' };
const ref = new WeakRef(user);

user = null;

setTimeout(() => {
  const obj = ref.deref();
  console.log(obj ? obj.name : 'Object was garbage collected');
}, 1000);
```

Практичное применение: кэш больших объектов, которые можно пересоздать. Если сборщик освободил объект, ты просто создашь его заново.

### `FinalizationRegistry`

`FinalizationRegistry` регистрирует callback, который вызовется после сборки объекта:

```js
const registry = new FinalizationRegistry((name) => {
  console.log(`${name} was garbage collected`);
});

let user = { name: 'Alice' };
registry.register(user, 'Alice');

user = null;
// позже может появиться: Alice was garbage collected
```

Здесь важно «может». Момент вызова callback не определён, и он может не случиться вовсе, например если вкладку закрыли раньше. Поэтому `FinalizationRegistry` подходит для логирования и метрик, но не для освобождения файловых дескрипторов или сетевых соединений. Их закрывают явно, через `close()` или `AbortController`.

## Ключевые тезисы для интервью

- Объект освобождается, когда до него нельзя дойти от корней; утечка — это забытая ссылка, а не недостаток сборщика.
- Типичные источники утечек во фронтенде: глобальные переменные, слушатели на `window` и `document`, таймеры, которые никто не остановил, detached DOM-узлы в переменных, кэши без лимита.
- Слушатель снимают через `removeEventListener` или `AbortController`: одна подписка на долгоживущей цели удерживает всё, что захватило её замыкание.
- В V8 переменные, захваченные хотя бы одним замыканием, живут в общем контексте, поэтому лишние вложенные функции могут удерживать большие данные.
- `WeakMap` и `WeakSet` позволяют держать записи, не продлевая жизнь ключам; `WeakRef` даёт слабую ссылку, которую можно проверить через `deref()`.
- `FinalizationRegistry` вызывает callback в неопределённый момент, поэтому для критичных ресурсов его не используют.
- Находить утечки помогает сравнение двух heap snapshot после повторения одного и того же действия.

## Заключение

Автоматическая память не отменяет ответственности за утечки. Сборщик освобождает ровно то, до чего нельзя дойти, и поэтому утечка почти всегда означает ссылку, о которой забыли: в глобальном объекте, в подписке, в замыкании, в таймере или в кэше. Поиск начинается с вопроса «кто ещё держит этот объект», а инструменты DevTools отвечают на него через сравнение снимков. Для кэшей с объектными ключами подходит `WeakMap`, но подписки и таймеры это не спасает: их снимают явно, через `AbortController` или `clearInterval`, в момент, когда они больше не нужны.
