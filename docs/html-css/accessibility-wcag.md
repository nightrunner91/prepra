# Доступность: WCAG 2.2, дерево доступности и аудит

Доступность часто воспринимают как «галочку» перед релизом: прогнали Lighthouse, поправили контраст — готово. На практике UI Engineer отвечает за другое: за то, чтобы интерфейс был управляемым с клавиатуры, понятным скринридеру, читаемым при увеличении и не ломался на мобильном экране. WCAG задаёт планку, дерево доступности объясняет, что видит вспомогательная технология, а аудит показывает разрыв между задумкой и реальностью.

В этой статье разберём уровни и структуру WCAG 2.2, новые критерии, дерево доступности и вычисление accessible name, разницу между `aria-hidden` и `inert`, требования к фокусу, контрасту и reflow, а также практический протокол аудита, который занимает 30 минут и даёт список конкретных дефектов.

## Глубокий разбор

### Что такое WCAG и зачем UI Engineer её знать

**WCAG (Web Content Accessibility Guidelines)** — рекомендации W3C, которые описывают, как сделать веб-контент доступным для людей с нарушениями зрения, слуха, моторики, речи, когнитивными особенностями и другими ограничениями. WCAG не диктует дизайн: она формулирует проверяемые требования к контенту, разметке, поведению компонентов и восприятию.

Для UI Engineer WCAG — рабочий инструмент по трём причинам:

- **Контракт с дизайном.** Требования к контрасту, размеру цели и фокусу влияют на токены и компоненты, а не на «последний полишинг».
- **Контракт с разработкой.** Критерии вроде Name, Role, Value или Focus Visible проверяются в code review и автоматизируются в CI.
- **Контракт с бизнесом.** Законодательство (например, European Accessibility Act) и закупочные требования обычно ссылаются на уровень AA, поэтому «сделаем позже» превращается в юридический риск.

Исходная статья раздела — [Семантический HTML и доступность](./html-semantics-accessibility.md) — отвечает на вопрос «с чего начать». Эта статья идёт дальше: как читать стандарт, как устроена модель доступности в браузере и как проверять результат.

### POUR и уровни соответствия

Все критерии WCAG группируются по четырём принципам — **POUR**:

| Принцип | Что означает | Примеры критериев |
|---|---|---|
| **Perceivable** | Информацию можно воспринять хотя бы одним чувством | `alt` (1.1.1), контраст (1.4.3), субтитры (1.2.2) |
| **Operable** | Интерфейсом можно управлять разными способами | клавиатура (2.1.1), видимый фокус (2.4.7), target size (2.5.8) |
| **Understandable** | Поведение и текст понятны | язык страницы (3.1.1), ошибки (3.3.1), предсказуемость (3.2.x) |
| **Robust** | Работает с вспомогательными технологиями | Name, Role, Value (4.1.2), status messages (4.1.3) |

Внутри POUR критерии разделены на три уровня:

- **A** — базовый минимум. Без него часть пользователей не сможет выполнить задачу: нет имён у кнопок, нет клавиатуры, нет `alt`.
- **AA** — продуктовый стандарт. Включает A и добавляет контраст 4.5:1, видимый фокус, reflow, размер цели, доступную аутентификацию.
- **AAA** — расширенный уровень: контраст 7:1, усиленный фокус, отсутствие когнитивных тестов при входе. На всём продукте достигается редко и обычно применяется точечно.

Уровни вложены: соответствие AA означает, что выполнены и все критерии A. Нельзя «выбрать AAA только для контраста» и игнорировать остальное — уровень присваивается странице целиком.

**Соответствие (conformance)** — это не свойство компонента. WCAG требует:

1. Указать уровень (A, AA или AAA).
2. Выполнить требования на **всех полных страницах** продукта, а не на отдельных блоках.
3. Пройти **все шаги процессов** — например, оформление заказа целиком, а не только страницу оплаты.
4. Использовать только **accessibility-supported** технологии: если скринридер не поддерживает технику, её нельзя считать выполнением критерия.
5. Не мешать: контент, который не поддерживается, не должен ломать доступность остального.

Отсюда практическое правило: «наш компонент доступен» ничего не значит, пока не проверен сценарий «открыл страницу → выбрал товар → оформил заказ → получил подтверждение».

### WCAG 2.2: что изменилось

WCAG 2.2 опубликована в октябре 2023 года. В ней девять новых критериев и удалён один старый.

| Критерий | Уровень | Суть |
|---|---|---|
| **2.4.11 Focus Not Obscured (Minimum)** | AA | Сфокусированный элемент не должен быть полностью скрыт контентом автора: sticky-хедером, баннером, cookie-панелью |
| **2.4.12 Focus Not Obscured (Enhanced)** | AAA | Сфокусированный элемент не должен быть скрыт частично |
| **2.4.13 Focus Appearance** | AAA | Фокус-индикатор толщиной не меньше 2 px по периметру и с изменением контраста 3:1 |
| **2.5.7 Dragging Movements** | AA | Действие перетаскиванием должно иметь альтернативу одним указателем без drag |
| **2.5.8 Target Size (Minimum)** | AA | Цель не меньше 24×24 CSS px, с исключениями для inline-ссылок и essential-случаев |
| **3.2.6 Consistent Help** | A | Механизмы помощи (чат, телефон, email) в одинаковом относительном порядке на страницах |
| **3.3.7 Redundant Entry** | A | Не заставляйте вводить одну и ту же информацию повторно: подставьте или дайте выбрать |
| **3.3.8 Accessible Authentication (Minimum)** | AA | Никаких когнитивных тестов при входе: разрешите paste и password managers |
| **3.3.9 Accessible Authentication (Enhanced)** | AAA | Более строгая версия: альтернатива для распознавания объектов и т. п. |

Удалён **4.1.1 Parsing**: валидность HTML больше не отдельный критерий, потому что браузеры научились восстанавливать дерево. Это не значит, что разметку можно не проверять — за корректность ролей и имён по-прежнему отвечает **4.1.2 Name, Role, Value**.

Что это меняет для UI Engineer:

- **Sticky-хедер и cookie-баннеры стали юридическим риском.** `scroll-padding-top` и проверка фокуса при прокрутке — теперь не «улучшение», а требование AA.
- **Размер кликабельной области проектируется вместе с иконкой.** 24×24 — минимум, а на touch лучше сразу закладывать 44×44.
- **Drag-and-drop без альтернативы — дефект.** Sortable-список, слайдер, загрузка файлов перетаскиванием нуждаются в кнопках или числовом вводе.
- **Формы нельзя строить на повторном вводе.** «Введите адрес доставки ещё раз» и «подтвердите email» без autocomplete — потенциальное нарушение 3.3.7.
- **Аутентификация без вставки пароля — дефект.** Запрет paste, OTP только с камеры и капча-головоломка ломают 3.3.8.

### Дерево доступности

Браузер не отдаёт скринридеру DOM напрямую. Он строит **accessibility tree** — упрощённое представление документа, где у каждого значимого узла есть:

- **role** — что это (кнопка, ссылка, заголовок, диалог, список);
- **name** — как это называется;
- **description** — дополнительное описание;
- **state** — состояние (`expanded`, `checked`, `disabled`, `invalid`);
- **value** — значение (для полей, слайдеров, прогресса);
- **properties** — связи (`labelledby`, `describedby`, `controls`).

Дерево доступности — не копия DOM. Из него выпадают презентационные элементы, скрытый контент и узлы без семантики:

| Что в DOM | Попадает ли в дерево |
|---|---|
| `<button>Отправить</button>` | Да: role `button`, name «Отправить» |
| `<div>текст</div>` | Обычно нет отдельного узла — только текстовое содержимое |
| `display: none`, `visibility: hidden`, `hidden` | Нет |
| `aria-hidden="true"` | Нет, включая поддерево |
| `opacity: 0` | **Да** — визуально скрыт, но доступен |
| Элемент, сдвинутый за экран через `position: absolute; left: -9999px` | **Да** — это распространённый способ скрыть текст только визуально |
| `<div role="button">` | Да, но только если роль валидна и есть имя |

Это объясняет два частых бага:

1. **«Невидимая» кнопка остаётся в tab-порядке.** `opacity: 0` или `transform: translateX(-200%)` не убирают элемент из дерева доступности. Для действительно скрытого контента нужны `hidden`, `display: none` или `inert`.
2. **`aria-hidden` на контейнере с кнопкой создаёт фантом.** Кнопка исчезает из дерева, но остаётся фокусируемой — пользователь скринридера «проваливается в пустоту».

Посмотреть дерево можно в DevTools: вкладка **Elements → Accessibility** (Chrome/Edge) или **Accessibility Inspector** (Firefox/Safari). В Chrome полезно включить **Full-page accessibility tree** — тогда видно не только выбранный узел, но и всю структуру.

### Доступное имя и описание

**Accessible name** — то, что скринридер произносит, когда пользователь попадает на элемент. Именно имя, а не визуальный текст, определяет, поймёт ли пользователь назначение кнопки.

Упрощённый порядок вычисления по [AccName](https://www.w3.org/TR/accname-1.2/):

1. `aria-labelledby` — ссылки на id других элементов (может собрать имя из нескольких узлов).
2. `aria-label` — строка прямо на элементе.
3. Нативные источники: `<label for>`, `alt` у изображения, `<legend>` у `fieldset`, `<caption>` у таблицы, `<figcaption>`.
4. Текстовое содержимое элемента — для кнопок, ссылок и других ролей, где name from content разрешён.
5. `title` — крайний fallback.
6. Для полей ввода HTML-AAM допускает `placeholder` как последний fallback, но это плохая практика.

**Описание** вычисляется отдельно: `aria-describedby` → `title`. Описание читается после имени и роли, поэтому туда стоит выносить подсказки и текст ошибок, а не название элемента.

Несколько следствий:

- `aria-labelledby` **сильнее** `aria-label`. Если оба заданы, победит `aria-labelledby`.
- `aria-label` **перекрывает** видимый текст. Критерий 2.5.3 Label in Name требует, чтобы видимая подпись входила в доступное имя: кнопка с текстом «Отправить» не должна иметь `aria-label="Submit"`, иначе пользователь голосового управления не сможет сказать «нажми Отправить».
- **Иконочная кнопка без текста обязана иметь имя.** Иконка с `aria-hidden="true"` и `aria-label` на кнопке — рабочий вариант.
- **`title` — не замена видимой подписи.** Он появляется только по наведению, недоступен на touch и часто игнорируется скринридерами при наличии других источников.

```html
<!-- Иконочная кнопка: имя на кнопке, иконка скрыта -->
<button type="button" aria-label="Закрыть диалог">
  <svg aria-hidden="true" focusable="false" width="20" height="20">...</svg>
</button>

<!-- Ссылка с видимым текстом и дополнительным контекстом -->
<a href="/cart">
  Корзина
  <span aria-hidden="true">(3)</span>
  <span class="visually-hidden">, 3 товара</span>
</a>

<!-- Поле с явной меткой и подсказкой -->
<label for="phone">Телефон</label>
<input id="phone" type="tel" autocomplete="tel" aria-describedby="phone-hint">
<p id="phone-hint">В формате +7 999 123-45-67</p>
```

`visually-hidden` — не `display: none`. Класс скрывает элемент визуально, но оставляет его в дереве доступности:

```css
.visually-hidden {
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;
  border: 0;
}
```

### ARIA: роли, состояния и свойства

ARIA — это способ дополнить дерево доступности там, где HTML не хватает. У неё есть три категории атрибутов:

- **Роли** (`role="dialog"`, `role="tab"`, `role="combobox"`) — что это за элемент.
- **Состояния** (`aria-expanded`, `aria-selected`, `aria-checked`, `aria-invalid`, `aria-busy`) — меняются во времени.
- **Свойства** (`aria-labelledby`, `aria-describedby`, `aria-controls`, `aria-haspopup`) — стабильные связи и характеристики.

Первое правило ARIA: **не используйте ARIA, если есть нативный элемент с нужной семантикой и поведением.** `<button>` уже даёт роль, фокус, активацию `Enter`/`Space` и состояние `disabled`. `<dialog>` даёт роль `dialog`, модальность и focus trap. `<details>`/`<summary>` дают раскрывающийся блок.

Второе правило: **ARIA меняет только семантику, но не поведение.** `<div role="button" tabindex="0">` не станет кнопкой: придётся вручную добавить обработку `Enter` и `Space`, состояние `aria-pressed`, видимый фокус и запрет активации в `disabled`.

Типичные ошибки с ARIA:

```html
<!-- Плохо: роль без поведения -->
<div role="button" onclick="save()">Сохранить</div>

<!-- Плохо: состояние объявлено, но не обновляется -->
<button aria-expanded="true">Фильтры</button>

<!-- Плохо: aria-label перекрывает видимый текст -->
<button aria-label="Submit">Отправить</button>

<!-- Хорошо: нативный элемент и честное состояние -->
<button type="button" aria-expanded="false" aria-controls="filters">Фильтры</button>
```

Отдельно стоит запомнить **live regions** — механизм объявления динамических изменений:

- `role="status"` — вежливое объявление (`aria-live="polite"`): «Файл загружен».
- `role="alert"` — срочное (`aria-live="assertive"`): «Не удалось сохранить изменения».
- `aria-atomic="true"` — читать весь регион целиком, а не только изменившийся фрагмент.

Live-регион должен существовать в DOM **до** изменения текста. Если создать контейнер и текст одновременно, скринридер может не успеть подписаться и промолчит. И не стоит вешать `aria-live` на всё приложение — это превращает интерфейс в поток случайных объявлений.

### aria-hidden vs inert

Это одна из самых частых точек путаницы на интервью. Оба атрибута скрывают контент от вспомогательных технологий, но делают это по-разному.

| Поведение | `aria-hidden="true"` | `inert` |
|---|---|---|
| Удаляет поддерево из дерева доступности | Да | Да |
| Убирает из tab-порядка | **Нет** | Да |
| Блокирует клики и события указателя | **Нет** | Да |
| Блокирует выделение и поиск по странице | Нет | Да |
| Тип | ARIA-атрибут | HTML-булев атрибут |
| Поддержка | Широкая | Baseline с 2023 года |

Практический вывод:

- **Фон модального окна** изолируют через `inert`, а не `aria-hidden`. Иначе кнопки под оверлеем остаются в tab-порядке и пользователь клавиатуры уходит в невидимый интерфейс.
- **Нативный `<dialog>` с `showModal()`** делает остальной документ inert автоматически — вручную ничего вешать не нужно.
- **`aria-hidden`** уместен для декоративных иконок, дублирующего текста и скрытых панелей, где **нет фокусируемых элементов**.
- **`aria-hidden` на фокусируемом элементе** — почти всегда ошибка. Если элемент нужен визуально, но не должен быть доступен, используйте `inert` или `hidden`.

```html
<!-- Плохо: фон скрыт от скринридера, но остаётся в tab-порядке -->
<div aria-hidden="true">
  <button>Удалить аккаунт</button>
</div>

<!-- Хорошо: фон полностью изолирован -->
<main inert>
  <button>Удалить аккаунт</button>
</main>
```

`inert` не заменяет управление фокусом. После открытия диалога фокус всё равно нужно перевести внутрь, а после закрытия — вернуть на элемент, который его открыл. `inert` лишь гарантирует, что фон не перехватит фокус.

### Фокус: видимость, порядок и перекрытие

Фокус — главный интерфейс для клавиатуры и скринридеров. В WCAG за него отвечают несколько критериев:

- **2.1.1 Keyboard (A)** — всё, что работает мышью, работает и с клавиатуры.
- **2.1.2 No Keyboard Trap (A)** — из любого места можно выйти клавиатурой.
- **2.4.3 Focus Order (A)** — порядок фокуса сохраняет смысл и последовательность.
- **2.4.7 Focus Visible (AA)** — у фокуса есть видимый индикатор.
- **2.4.11 Focus Not Obscured (Minimum) (AA)** — элемент не скрыт полностью.
- **2.4.13 Focus Appearance (AAA)** — усиленные требования к толщине и контрасту индикатора.

Базовые правила:

1. **Не убирайте `outline` без замены.** `:focus-visible` даёт видимый фокус только для клавиатуры и не раздражает мышиных пользователей.
2. **Не используйте `tabindex` больше нуля.** Положительные значения перестраивают порядок и почти всегда ломают логику.
3. **Один `tabindex="0"` на группу.** В составных виджетах (tabs, menu) используется roving tabindex: активный элемент `0`, остальные `-1`.
4. **Диалог удерживает фокус.** При открытии — внутрь, при закрытии — обратно на триггер.
5. **Skip link** — первый фокусируемый элемент страницы, позволяющий перейти к основному контенту.

```css
/* Видимый и контрастный фокус */
:focus-visible {
  outline: 2px solid var(--color-focus);
  outline-offset: 2px;
}

/* Плохо: пользователь не понимает, где находится */
button:focus {
  outline: none;
}
```

Отдельная проблема — **перекрытие фокуса**. Sticky-хедер, плавающая панель или cookie-баннер могут полностью закрыть сфокусированный элемент. Лечится не только уменьшением слоёв, но и прокруткой:

```css
:root {
  --header-height: 4rem;
}

/* Компенсация sticky-хедера при прокрутке к якорю и фокусу */
html {
  scroll-padding-top: calc(var(--header-height) + 1rem);
}

:target,
[tabindex="-1"]:focus {
  scroll-margin-top: calc(var(--header-height) + 1rem);
}
```

Если элемент скрыт **частично**, это допустимо для AA (2.4.11), но не для AAA (2.4.12). На практике лучше проектировать так, чтобы фокус никогда не оказывался под панелью.

### Визуальные требования: контраст, zoom, reflow, target size

Доступность — не только ARIA. Визуальные параметры проверяются так же строго.

**Контраст (1.4.3 AA, 1.4.6 AAA, 1.4.11 AA):**

| Что | AA | AAA |
|---|---|---|
| Обычный текст | 4.5:1 | 7:1 |
| Крупный текст (≥24 px или ≥19 px bold) | 3:1 | 4.5:1 |
| Нетекстовые элементы: иконки, границы полей, состояния | 3:1 | — |

Контраст считают между текстом и фоном **с учётом прозрачности и градиентов**. Полупрозрачный текст на изображении — частая причина провала. Для проверки подходят WebAIM Contrast Checker, DevTools color picker и axe.

**Zoom и reflow (1.4.4 AA, 1.4.10 AA, 1.4.12 AA):**

- Текст масштабируется до **200%** без потери контента и функциональности.
- При ширине **320 CSS px** (эквивалент 1280 px при 400% zoom) нет двумерной прокрутки, кроме таблиц, карт, видео и подобных исключений.
- При увеличении межстрочного интервала до 1.5, отступа после абзаца до 2em, межбуквенного до 0.12em и межсловного до 0.16em ничего не обрезается.

Практически это означает: никаких `width: 960px`, `min-width` у гридов без `minmax(0, 1fr)`, горизонтальных меню без переноса и `position: absolute` для основного контента. И никогда — `user-scalable=no` в meta viewport.

**Размер цели (2.5.8 AA, 2.5.5 AAA):**

- Минимум **24×24 CSS px** для интерактивных целей.
- Исключения: inline-ссылки в тексте, элементы, размер которых задаёт браузер, essential-случаи и цели, вокруг которых остаётся свободная окружность 24 px.
- **44×44** — комфортный touch-размер и требование AAA.

```html
<!-- Плохо: отключает масштабирование -->
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no">

<!-- Хорошо -->
<meta name="viewport" content="width=device-width, initial-scale=1">
```

```css
.icon-button {
  display: inline-grid;
  place-items: center;
  min-inline-size: 24px;
  min-block-size: 24px;
  padding: 0.25rem;
}

@media (pointer: coarse) {
  .icon-button {
    min-inline-size: 44px;
    min-block-size: 44px;
  }
}
```

### Формы и ошибки

Формы — место, где доступность ломается чаще всего, потому что здесь сходятся семантика, фокус, динамика и текст.

Минимальный контракт доступного поля:

1. **Видимая метка**, связанная через `<label for>`; placeholder — не метка.
2. **Правильный `type` и `inputmode`** — чтобы на мобильном открывалась нужная клавиатура.
3. **`autocomplete`** — критерий 1.3.5 требует идентифицировать назначение поля; это же помогает autofill и людям с когнитивными особенностями.
4. **Ошибка текстом**, а не только цветом.
5. **Связь ошибки с полем** через `aria-invalid` и `aria-describedby`.
6. **Фокус на ошибке** после неудачной отправки — на summary или первое невалидное поле.
7. **Группы** (radio, checkbox) — в `<fieldset>` с `<legend>`.

```html
<label for="email">Email</label>
<input
  id="email"
  name="email"
  type="email"
  autocomplete="email"
  aria-invalid="true"
  aria-describedby="email-error"
>
<p id="email-error">Введите email в формате name@example.com</p>
```

Важные нюансы:

- **`aria-invalid` не заменяет текст ошибки.** Он сообщает состояние, но не причину.
- **`aria-errormessage`.** Атрибут существует, но поддержка скринридерами нестабильна; `aria-describedby` на текст ошибки остаётся практичным выбором.
- **`aria-describedby` читается вместе с полем**, поэтому текст должен быть коротким и конкретным.
- **Ошибка в `role="alert"`** объявляется сразу, но при асинхронной проверке это может перебивать пользователя. Для ошибок после submit часто достаточно error summary с фокусом.
- **Error summary** — блок со списком ошибок и ссылками на поля. Он полезен в длинных формах: пользователь видит картину целиком, а не прыгает по одному полю.
- **Redundant Entry (3.3.7)** — не просите повторно то, что уже введено: адрес доставки = адрес оплаты; повторное подтверждение email вводом оправдано только реальными требованиями безопасности.
- **Accessible Authentication (3.3.8)** — разрешайте вставку пароля и OTP, поддерживайте password managers и passkeys, не используйте капчу-головоломку как единственный способ входа.

### Motion и системные настройки

Анимация сама по себе не нарушает WCAG, но может сделать интерфейс недоступным:

- **2.2.2 Pause, Stop, Hide (A)** — движущийся контент дольше 5 секунд должен иметь паузу или остановку.
- **2.3.1 Three Flashes (A)** — не более трёх вспышек в секунду.
- **2.3.3 Animation from Interactions (AAA)** — анимация от взаимодействия должна отключаться.
- **2.5.4 Motion Actuation (A)** — управление наклоном/встряхиванием должно иметь альтернативу.

Даже если 2.3.3 — AAA, `prefers-reduced-motion` стоит поддерживать по умолчанию: вестибулярные расстройства — реальная проблема, а не теоретическая.

```css
@media (prefers-reduced-motion: reduce) {
  .carousel__track {
    transition: none;
  }

  .dialog {
    animation: fade-in 120ms ease-out;
  }

  /* Смысловая загрузка остаётся, но становится спокойнее */
  .spinner {
    animation-duration: 2s;
  }
}
```

Глобальный сброс `animation-duration: 0.01ms !important` — грубая заплатка: он ломает индикаторы загрузки и переходы, которые несут смысл. Лучше отключать конкретные декоративные анимации и заменять движение на fade или мгновенное состояние.

Отдельно проверяйте **forced-colors mode** (Windows High Contrast): фон и тени могут исчезнуть, поэтому границы и состояния не должны держаться только на цвете фона.

### Аудит: инструменты и 30-минутный протокол

Аудит — это не «запустить Lighthouse». Это последовательность слоёв, каждый из которых ловит свой класс проблем.

**Инструменты:**

- **axe DevTools / @axe-core/playwright** — автоматические проверки: имена, `alt`, ARIA-связи, часть контраста, структура.
- **Lighthouse** — быстрый смоук, но использует подмножество axe и даёт общую оценку.
- **Accessibility Insights for Web** — Fast Pass с пошаговым ручным чек-листом.
- **WebAIM Contrast Checker** — точечная проверка контраста.
- **NVDA + Firefox** (Windows), **VoiceOver + Safari** (macOS/iOS), **TalkBack** (Android) — реальные скринридеры.
- **Playwright** — клавиатурные сценарии и регрессия.

**Протокол на 30 минут:**

| Время | Шаг | Что проверять |
|---|---|---|
| 0–5 мин | Автоматика | axe/Lighthouse на 2–3 ключевых экранах; ошибки имён, `alt`, landmarks, `lang`, контраст |
| 5–15 мин | Клавиатура | Skip link, порядок `Tab`, видимый фокус, ловушки, меню, диалоги, `Esc` |
| 15–20 мин | Масштаб | Zoom 200% и 400%, ширина 320 px, text spacing, горизонтальный скролл |
| 20–25 мин | Скринридер | Список заголовков, landmarks, имена полей, ошибки, live-объявления |
| 25–30 мин | Формы и состояния | Пустой и невалидный submit, autofill, ошибки не только цветом, target size |

Результат — не «оценка 87/100», а список дефектов:

```md
1. [AA 2.4.11] Sticky-хедер полностью перекрывает сфокусированную ссылку «Оформить».
   Шаги: Tab до ссылки в карточке → фокус уходит под хедер.
   Фикс: scroll-padding-top + проверка порядка слоёв.

2. [AA 1.4.3] Серый текст подсказки #9AA0A6 на белом — 2.8:1.
   Фикс: затемнить до 4.5:1 или увеличить кегль до крупного.

3. [A 4.1.2] Иконочная кнопка закрытия без доступного имени.
   Фикс: aria-label + aria-hidden на svg.
```

Важно: автоматика не проверяет **осмысленность**. axe не знает, что `alt="image1.png"` бесполезен, что порядок фокуса в форме нелогичен и что ошибка «Что-то пошло не так» ничего не объясняет. Поэтому ручной проход обязателен даже при зелёном CI.

## Практические примеры

### Пример 1. Доступные имена для иконочных кнопок и ссылок

```html
<nav aria-label="Основная навигация">
  <a href="/">Главная</a>
  <a href="/catalog">Каталог</a>
</nav>

<button type="button" aria-label="Открыть корзину">
  <svg aria-hidden="true" focusable="false" width="24" height="24">
    <use href="#icon-cart" />
  </svg>
</button>

<a href="/cart">
  Корзина
  <span aria-hidden="true">(3)</span>
  <span class="visually-hidden">, 3 товара</span>
</a>
```

Здесь:

- у навигации есть имя, чтобы при нескольких `<nav>` скринридер различал их;
- SVG скрыт от дерева доступности, чтобы не читались пути и `id`;
- счётчик товаров не дублируется в имени ссылки: визуальная цифра скрыта, а полный текст добавлен через `visually-hidden`;
- `focusable="false"` нужен для старых версий IE/Edge, но безопасен и сейчас.

### Пример 2. Модальный диалог: `showModal`, `inert` и возврат фокуса

```html
<button type="button" id="delete-trigger">Удалить файл</button>

<dialog id="confirm-dialog" aria-labelledby="confirm-title" aria-describedby="confirm-desc">
  <h2 id="confirm-title">Удалить файл?</h2>
  <p id="confirm-desc">Файл будет удалён без возможности восстановления.</p>
  <form method="dialog">
    <button value="cancel" data-autofocus>Отмена</button>
    <button value="confirm">Удалить</button>
  </form>
</dialog>

<script>
  const dialog = document.querySelector('#confirm-dialog');
  const trigger = document.querySelector('#delete-trigger');

  trigger.addEventListener('click', () => {
    dialog.showModal();
    dialog.querySelector('[data-autofocus]').focus();
  });

  dialog.addEventListener('close', () => {
    // При showModal() браузер сам возвращает фокус на элемент,
    // который открыл диалог. Явный вызов полезен для кастомных реализаций.
    trigger.focus();
  });
</script>
```

Что важно:

- `showModal()` делает остальной документ **inert автоматически** — не нужно вручную вешать `aria-hidden` на `body` или `main`.
- `aria-labelledby` связывает диалог с заголовком, `aria-describedby` — с описанием.
- `method="dialog"` позволяет закрыть диалог кнопкой без ручного JS; значение кнопки попадёт в `dialog.returnValue`.
- Фокус переводится на безопасное действие (обычно «Отмена»), чтобы случайный `Enter` не удалил данные.
- Для кастомного диалога (портал, drawer) фон изолируют через `main.inert = true`, а после закрытия снимают `inert` и возвращают фокус на триггер.

### Пример 3. Форма с error summary и `aria-describedby`

```html
<form id="signup" novalidate>
  <div id="error-summary" role="alert" tabindex="-1" hidden>
    <h2>Проверьте поля</h2>
    <ul></ul>
  </div>

  <div class="field">
    <label for="email">Email</label>
    <input
      id="email"
      name="email"
      type="email"
      autocomplete="email"
      aria-describedby="email-error"
    >
    <p id="email-error" hidden>Введите email в формате name@example.com</p>
  </div>

  <div class="field">
    <label for="password">Пароль</label>
    <input
      id="password"
      name="password"
      type="password"
      autocomplete="new-password"
      aria-describedby="password-hint password-error"
    >
    <p id="password-hint">Минимум 8 символов</p>
    <p id="password-error" hidden>Пароль слишком короткий</p>
  </div>

  <button type="submit">Создать аккаунт</button>
</form>
```

```js
const form = document.querySelector('#signup');
const summary = document.querySelector('#error-summary');

form.addEventListener('submit', (event) => {
  event.preventDefault();

  const fields = [...form.elements].filter(
    (el) => el.willValidate && !el.checkValidity(),
  );

  form.querySelectorAll('[aria-invalid="true"]').forEach((el) => {
    el.removeAttribute('aria-invalid');
  });
  summary.hidden = true;
  summary.querySelector('ul').replaceChildren();

  if (fields.length === 0) {
    form.submit(); // или fetch
    return;
  }

  const list = summary.querySelector('ul');

  for (const field of fields) {
    field.setAttribute('aria-invalid', 'true');

    const error = document.querySelector(`#${field.id}-error`);
    if (error) error.hidden = false;

    const item = document.createElement('li');
    const link = document.createElement('a');
    link.href = `#${field.id}`;
    link.textContent = field.labels?.[0]?.textContent ?? field.name;
    item.append(link);
    list.append(item);
  }

  summary.hidden = false;
  summary.focus(); // tabindex="-1" делает блок программно фокусируемым
});
```

Почему так:

- ошибки привязаны к полям через `aria-invalid` и `aria-describedby`;
- текст ошибки виден, а не только подчёркнут красным;
- summary даёт обзор и ссылки на проблемные поля;
- фокус переходит на summary — пользователь скринридера сразу слышит, что не так;
- `hidden` на ошибке снимается только после взаимодействия.

Тонкость: `role="alert"` + перемещение фокуса на тот же блок может привести к двойному объявлению в некоторых скринридерах. Альтернатива — `role="group"` с `aria-labelledby` для summary и `role="alert"` только на инлайновых ошибках. Выбор зависит от того, насколько критично немедленное объявление.

### Пример 4. Sticky header, focus not obscured и target size

```css
:root {
  --header-height: 4rem;
  --color-focus: #1a5fb4;
}

html {
  scroll-padding-top: calc(var(--header-height) + 1rem);

:focus-visible {

  }

```

Проверка: пройдите страницу клавиатурой и убедитесь, что ни один сфокусированный элемент не исчезает под хедером. Затем включите zoom 400% и проверьте, что кнопки не наезжают друг на друга и остаются кликабельными.

### Пример 5. Автотесты и клавиатурный сценарий в Playwright

```ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test.describe('checkout accessibility', () => {
  test('нет нарушений axe на уровне WCAG A/AA', async ({ page }) => {
    await page.goto('/checkout');

    const { violations } = await new AxeBuilder({ page })
      .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
      .analyze();

    expect(violations, JSON.stringify(violations, null, 2)).toEqual([]);
  });

  test('клавиатура: skip link, диалог и возврат фокуса', async ({ page }) => {
    await page.goto('/checkout');

    await page.keyboard.press('Tab');
    await expect(
      page.getByRole('link', { name: /к содержанию/i }),
    ).toBeFocused();

    await page.getByRole('button', { name: /удалить/i }).click();
    await expect(page.getByRole('dialog')).toBeVisible();
    await expect(
      page.getByRole('button', { name: /отмена/i }),
    ).toBeFocused();

    await page.keyboard.press('Escape');
    await expect(
      page.getByRole('button', { name: /удалить/i }),
    ).toBeFocused();
  });
});
```

Что покрывает такой тест:

- отсутствие автоматически обнаружимых нарушений;
- доступность skip link с первой же позиции `Tab`;
- наличие диалога и перемещение фокуса внутрь;
- закрытие по `Escape` и возврат фокуса на триггер.

Чего он **не** покрывает: осмысленность текста, удобство порядка фокуса, объявления скринридера и визуальное перекрытие фокуса. Поэтому e2e — дополнение к ручному аудиту, а не замена.

## Типичные ошибки и антипаттерны

- **`outline: none` без замены.** Пользователь клавиатуры теряет ориентацию. Используйте `:focus-visible` с контрастным индикатором.
- **`aria-hidden="true"` на контейнере с фокусируемыми элементами.** Получаются «фантомные» фокусы. Для фона модалки — `inert` или нативный `<dialog>`.
- **`div` с `role="button"`.** Без `tabindex`, обработки `Enter`/`Space` и состояний это не кнопка. Сначала ищите нативный элемент.
- **`aria-label`, перекрывающий видимый текст.** Ломает 2.5.3 Label in Name и голосовое управление.
- **`placeholder` вместо `<label>`.** Исчезает при вводе, плохо контрастен, не является меткой.
- **Ошибки только цветом.** Красная рамка без текста бесполезна для скринридера и части пользователей с нарушениями цветовосприятия.
- **`tabindex="1"` и выше.** Перестраивает порядок фокуса и почти всегда создаёт хаос.
- **Модалка без focus trap и возврата фокуса.** Фокус уходит в фон, пользователь теряет контекст.
- **`aria-expanded`/`aria-selected`, которые не обновляются.** Скринридер сообщает ложное состояние — это хуже, чем отсутствие ARIA.
- **`aria-live` на большом контейнере.** Каждое изменение читается целиком, интерфейс становится шумным.
- **Отключение zoom через `user-scalable=no`.** Ломает 1.4.4 и 1.4.10.
- **Фиксированные ширины и горизонтальные меню без переноса.** Провал reflow на 320 px.
- **Цели меньше 24×24.** Особенно больно на touch и при треморе.
- **Автоплей карусели без паузы.** Нарушает 2.2.2 и отвлекает.
- **Глобальный сброс всех анимаций при `prefers-reduced-motion`.** Ломает индикаторы загрузки и смысловые переходы.
- **Аудит только через Lighthouse.** Оценка 100 не означает доступность: автоматика не проверяет смысл и клавиатурные сценарии.
- **Скрытие контента через `opacity: 0` или сдвиг за экран.** Элемент остаётся в дереве доступности и tab-порядке.

## Ключевые тезисы для интервью

- **WCAG — это проверяемые требования, а не рекомендации по вкусу.** POUR задаёт четыре принципа, уровни A/AA/AAA — планку, а conformance проверяется на полных страницах и сквозных процессах.
- **AA — продуктовый стандарт.** A — минимум, AAA — точечно; законодательство и закупки обычно требуют AA.
- **В WCAG 2.2 девять новых критериев.** Для UI Engineer критичны Focus Not Obscured (sticky-хедеры), Target Size 24×24, Dragging Movements, Redundant Entry и Accessible Authentication.
- **Скринридер работает не с DOM, а с деревом доступности.** Узлы описываются ролью, именем, описанием, состоянием и значением; скрытые и презентационные узлы в дерево не попадают.
- **Accessible name вычисляется по приоритету источников.** `aria-labelledby` → `aria-label` → нативные метки → содержимое → `title`; `aria-label` перекрывает видимый текст, поэтому важен Label in Name.
- **`aria-hidden` скрывает от скринридера, но не убирает из tab-порядка.** `inert` убирает из дерева доступности, tab-порядка и блокирует указатель — именно он нужен для фона модалок.
- **Фокус — часть функциональности.** Видимый индикатор, логичный порядок, отсутствие ловушек, возврат фокуса и защита от перекрытия sticky-элементами.
- **Визуальные требования измеримы.** Контраст 4.5:1/3:1, reflow на 320 px, zoom 200%, target size 24×24, text spacing.
- **Ошибка формы должна быть текстом и связью.** `aria-invalid` + `aria-describedby` + error summary + фокус на проблеме; ошибки показывают после взаимодействия.
- **Автотесты не заменяют ручной аудит.** axe и Lighthouse ловят часть дефектов; клавиатура, скринридер и zoom проверяются руками, а в CI остаются линтеры, axe и клавиатурные e2e.

## Практическое задание и code review-чеклист

### Аудит страницы за 30 минут

Возьмите любой реальный экран — например, страницу оформления заказа или форму регистрации — и пройдите пять шагов:

1. **Автоматика (5 мин).** Запустите axe DevTools и Lighthouse. Зафиксируйте все violations с критерием и селектором.
2. **Клавиатура (10 мин).** Начните с адресной строки и нажимайте только `Tab`, `Shift+Tab`, `Enter`, `Space`, стрелки, `Esc`. Проверьте skip link, порядок, видимый фокус, ловушки, работу меню и диалогов.
3. **Масштаб (5 мин).** Включите zoom 200% и 400%, эмуляцию 320 px, проверьте горизонтальный скролл и обрезку. Отдельно проверьте text spacing.
4. **Скринридер (5 мин).** Включите NVDA + Firefox или VoiceOver + Safari. Пройдите по заголовкам, landmarks, полям и ошибкам. Убедитесь, что динамические сообщения объявляются.
5. **Формы и состояния (5 мин).** Отправьте пустую и невалидную форму. Проверьте фокус, текст ошибок, autofill, target size, reduced motion и forced-colors.

**Результат:** список из 10 проблем в формате «критерий → шаги → ожидаемое поведение → фикс → severity».

### Чек-лист code review

- [ ] У каждого интерактивного элемента есть роль, доступное имя и корректное состояние.
- [ ] Нативные элементы использованы там, где они есть; ARIA не дублирует семантику.
- [ ] Все действия доступны с клавиатуры, порядок фокуса логичен, ловушек нет.
- [ ] Фокус видим, контрастен и не перекрывается sticky-элементами.
- [ ] `aria-hidden` не навешан на фокусируемые элементы; фон модалки изолирован через `inert`.
- [ ] Модальные окна переводят фокус внутрь и возвращают его на триггер.
- [ ] У полей есть `<label>`, корректный `type`, `autocomplete`, `aria-invalid` и `aria-describedby`.
- [ ] Ошибки выражены текстом и не только цветом.
- [ ] Контраст текста и нетекстовых элементов соответствует AA.
- [ ] Цели не меньше 24×24 CSS px; на touch — ближе к 44×44.
- [ ] Страница проходит reflow на 320 px и zoom 400%.
- [ ] `prefers-reduced-motion` и `prefers-contrast` учтены; автоплей имеет паузу.
- [ ] Live-регионы существуют заранее и не используются для всего приложения.
- [ ] Есть автоматические проверки (axe/lint) и хотя бы один клавиатурный e2e-сценарий.
- [ ] Проведён ручной проход клавиатурой и скринридером.

## Заключение

Доступность — это не набор атрибутов, а модель взаимодействия. WCAG задаёт планку и vocabulary, дерево доступности объясняет, что реально получает скринридер, а фокус, контраст, reflow и размер цели превращают требования в измеримые параметры интерфейса. WCAG 2.2 усилила именно практические зоны боли: sticky-элементы, маленькие цели, drag-and-drop, повторный ввод и вход без копирования.

Для UI Engineer важно держать три уровня проверки: **семантика** (роль, имя, состояние), **взаимодействие** (клавиатура, фокус, диалоги) и **восприятие** (контраст, масштаб, motion). Автотесты закрывают регрессию, но не заменяют ручной аудит. Поэтому следующий шаг — не читать стандарт целиком, а взять один экран и пройти 30-минутный протокол: список найденных дефектов даст больше, чем ещё один чек-лист в отрыве от продукта.

Продолжение темы — клавиатурные паттерны и ARIA-виджеты в следующей статье раздела, а Vue-специфика разобрана в [Доступные компоненты во Vue](../vue/accessibility.md).
