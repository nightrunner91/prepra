# Паттерны промптинга

Промптинг — это не магия и не интуиция. Это набор устоявшихся паттернов с предсказуемым эффектом: правильно сформулированная задача даёт стабильный, управляемый результат. Для разработчика, который работает через агентов, промптинг — это **язык требований**: как превратить задачу в инструкцию, которую модель выполнит надёжно. Эта статья — о паттернах формулирования, которые вы используете каждый день в спецификациях для агентов.

## Анатомия промпта: system / user / assistant

### Три роли в разговоре

**System prompt** — инструкции, которые задают поведение модели на уровне сессии: роль, ограничения, формат вывода. Это привилегированный слот: модель обучена следовать системным инструкциям строже, чем пользовательским.

**User** — сообщения от пользователя или от приложения: конкретная задача, данные, уточнения.

**Assistant** — сообщения модели. В истории хранятся прошлые ответы.

### Что куда класть

```ts
// Системный промпт: неизменное поведение для всей сессии
const system = `Ты — ассистент по code review.
Пиши замечания кратко, по одному на пункт.
Всегда указывай номер строки.
Не предлагай изменений за пределами переданного кода.`;

// User message: конкретная задача с данными
const userMessage = `Проверь этот компонент:

\`\`\`tsx
${componentCode}
\`\`\``;
```

Для работы с агентами это правило применимо напрямую: **постоянные инструкции — в AGENTS.md / system prompt, конкретная задача — в текущем сообщении**.

### Порядок сообщений имеет значение

Из статьи о ментальной модели: модели лучше обрабатывают начало и конец контекста. Практическое следствие: критические ограничения — в начало (system prompt), конкретное задание — в конец (текущее сообщение). История в середине прочитывается, но с меньшим вниманием.

## Zero-shot, one-shot, few-shot

### Zero-shot: задача без примеров

Работает хорошо для распространённых задач, которые модель «видела» в обучении. Проблема: модель сама интерпретирует формат вывода — результат может быть «нейтральная», «Нейтральная», «Тональность: нейтральная», «Это смешанный отзыв...». Всё это требует разного парсинга.

### One-shot: один пример

Один пример резко сужает пространство интерпретаций и задаёт формат:

```text
Определи тональность. Отвечай одним словом: positive / negative / neutral.

Отзыв: "Отличный товар, рекомендую!"
Тональность: positive

Отзыв: "Быстрая доставка, но упаковка помята"
Тональность:
```

Модель почти наверняка ответит `neutral` — формат задан примером.

### Few-shot: несколько примеров

Few-shot работает лучше в задачах с неочевидной логикой классификации или специфичным доменом — когда нужно показать модель граничные случаи.

**Правило качества примеров**: плохой пример вреднее, чем его отсутствие. Если примеры противоречат друг другу или содержат исключения без объяснения — модель обучается на противоречии.

### Когда few-shot реально помогает

1. **Нестандартный формат вывода** — нужна специфическая структура
2. **Доменная специфика** — внутренние категории, которых нет в общем обучении
3. **Граничные случаи** — примеры именно для неоднозначных входных данных

## Chain-of-thought

### Проблема: сложные рассуждения без промежуточных шагов

Если спросить модель напрямую «Если куплю 3 яблока по 7 рублей и 5 груш по 11, сколько сдачи со 100?» — она нередко ошибается. Если попросить «рассуждай пошагово» — точность резко возрастает. Причина: модель генерирует токены последовательно; при прямом ответе у неё нет «места» для промежуточных вычислений — они должны появиться в тексте.

### Применение

```text
// Без CoT: модель даёт ответ напрямую
Определи, есть ли в этом коде утечка памяти: <код>

// С CoT: инструкция думать вслух
Определи, есть ли в этом коде утечка памяти.
Рассуждай пошагово:
1. Определи все подписки, таймеры и слушатели событий
2. Проверь, есть ли cleanup для каждого из них
3. Сделай вывод

Код: <код>
```

Для работы с агентами CoT полезен в задачах анализа и отладки: «проанализируй, затем реши» даёт лучший результат, чем «реши сразу».

### Когда CoT НЕ помогает

- **Простые факты** — рассуждение только тратит токены
- **Творческие задачи** — CoT ограничивает свободу
- **Задачи с очевидным ответом** — избыточное рассуждение может снизить точность

## Prompt chaining

### Когда одного промпта недостаточно

Сложные задачи плохо решаются одним запросом: слишком много требований одновременно, конкурирующие цели, задача слишком длинная для одного вывода. Prompt chaining — разбиение на последовательность более простых шагов, где вывод одного становится входом следующего.

```text
// Одним запросом: перегружен, плохой результат
Проанализируй код, найди баги, исправь их, задокументируй,
напиши тесты и обнови README

// Цепочка: каждый шаг фокусирован
Шаг 1: Проанализируй код и опиши проблемы
Шаг 2: Исправь баги на основе анализа
Шаг 3: Напиши тесты на основе исправленного кода
```

### Паттерн: генерация + проверка

Второй распространённый случай: генерируем результат первым вызовом, проверяем корректность вторым («генерация + проверка»).

```text
Шаг 1: Реализуй функцию по спецификации: <спецификация>
Шаг 2: Проверь, соответствует ли этот код спецификации.
Спецификация: <спецификация>
Код: <код>
Ответь: "ok" если соответствует, иначе — список несоответствий.
```

Это ключевой паттерн для работы с агентами: **не принимать результат агента без проверки**. Независимая проверка — второй вызов с другим фокусом — ловит то, что первый пропустил.

### Когда цепочки не нужны

Prompt chaining добавляет latency и стоимость. Если задача решается одним промптом с приемлемым качеством — это лучший вариант. Современные модели справляются с многошаговыми задачами лучше, чем год назад.

## Антипаттерны и типичные ошибки

### Избыточная вежливость

```text
// Плохо: токены на вежливость — это деньги и latency
Пожалуйста, не могли бы вы любезно помочь мне, если вас не затруднит,
проанализировать этот код?

// Хорошо: директивный тон
Проанализируй код. Укажи проблемы и улучшения.
```

Модели не обижаются. Вежливые обороты занимают токены и размывают инструкции.

### Противоречивые инструкции

Если инструкции конфликтуют, приоритет зависит от модели и контекста — результат непредсказуем. Решение: согласованные инструкции или явный приоритет в system prompt.

### Негативные инструкции без позитивной альтернативы

```text
// Хуже: только запрет
Не используй markdown. Не пиши заголовки. Не делай списки.

// Лучше: явно желаемый формат
Отвечай простым текстом, сплошными абзацами, без форматирования.
```

«Не делай X» менее эффективно, чем «делай Y» — модель должна знать, что делать, а не только чего избегать.

### Перегрузка одного промпта

```text
// Плохо: слишком много задач одновременно
1. Найди все баги
2. Перепиши на TypeScript
3. Добавь тесты
4. Оптимизируй производительность

// Хорошо: одна чёткая задача
Найди все баги в этом коде. Для каждого: строка, описание, уровень критичности.
```

### Неясный критерий качества

```text
// Плохо: «хорошо» — субъективно и неизмеримо
Напиши хороший компонент для формы входа.

// Хорошо: конкретные критерии
Напиши React-компонент формы входа:
- Поля: email, password
- Валидация на submit: email format, password min 8 символов
- Сообщения об ошибках под каждым полем
- Disabled-состояние кнопки во время запроса
- TypeScript, без сторонних библиотек для форм
```

## Ключевые тезисы для интервью

- Промпт состоит из трёх ролей: system (поведение сессии), user (конкретная задача), assistant (история ответов).
- Few-shot — примеры в промпте для калибровки формата и логики; качество примеров важнее их количества.
- Chain-of-Thought вынуждает модель генерировать промежуточные шаги рассуждения в тексте — повышает точность на сложных многошаговых задачах.
- Prompt chaining — декомпозиция сложной задачи на последовательные вызовы; паттерн «генерация + проверка» — независимая проверка результата вторым вызовом.
- Негативные инструкции («не делай X») менее эффективны, чем позитивные («делай Y»).
- Один промпт — одна задача; конкретные критерии качества лучше абстрактного «напиши хорошо».

## Заключение

Промптинг — это инженерная дисциплина, а не интуиция. Несколько принципов, которые работают всегда:

- Чёткие инструкции побеждают длинные. Конкретный формат лучше общего «напиши хорошо».
- Примеры эффективнее объяснений. One-shot часто даёт лучший результат, чем развёрнутая инструкция без примера.
- Промежуточные шаги — это токены в тексте. CoT работает потому, что рассуждение буквально записывается в ответе.
- Один промпт — одна задача. Сложное разбивается на цепочку.
- Результат агента проверяется. Паттерн «генерация + проверка» — второй вызов с независимым фокусом.

Для разработчика, работающего через агентов, эти паттерны — не теория, а повседневный язык: как превратить задачу в спецификацию, которую агент выполнит без догадок.
