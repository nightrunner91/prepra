# Паттерны промптинга

Промптинг — это не магия и не интуиция. Это набор устоявшихся паттернов с предсказуемым эффектом: правильно сформулированный промпт даёт стабильный, управляемый результат. Понимание этих паттернов — разница между «иногда работает» и «работает надёжно». Статья строится на фундаменте предыдущей — понимание токенов, контекстного окна и температуры здесь подразумевается.

## Анатомия промпта: system / user / assistant

### Три роли в разговоре

Современные чат-модели принимают входные данные в виде массива сообщений, каждое из которых имеет роль. Понимание роли каждого слота — основа грамотного промптинга.

```ts
const response = await client.messages.create({
  model: "claude-sonnet-4-6",
  system: "...",       // системный промпт — отдельный параметр
  messages: [
    { role: "user",      content: "..." },
    { role: "assistant", content: "..." },
    { role: "user",      content: "..." }, // текущий запрос
  ],
});
```

**System prompt** — инструкции, которые задают поведение модели на уровне сессии: роль, ограничения, формат вывода, контекст. Технически это привилегированный слот: модель обучена следовать системным инструкциям строже, чем пользовательским.

**User** — сообщения от пользователя или от приложения, действующего от имени пользователя. Здесь размещают конкретные задачи, данные для обработки, уточнения.

**Assistant** — сообщения модели. В истории диалога хранят прошлые ответы. Можно также «подставить» начало ответа, чтобы направить модель в нужном направлении (prefill).

### Что куда класть

```ts
// Системный промпт: неизменное поведение для всей сессии
const system = `Ты — ассистент по code review.
Пиши замечания кратко, по одному на пункт.
Всегда указывай номер строки.
Не предлагай изменений за пределами переданного кода.`;

// User message: конкретная задача с данными
const userMessage = `Проверь этот компонент:

\`\`\`tsx
${componentCode}
\`\`\``;

// Prefill: принудительный старт ответа в нужном формате
const assistantPrefill = "## Замечания\n\n";
```

Prefill — мощный, но недооценённый приём: если вы хотите, чтобы модель начала ответ с `{`, она с высокой вероятностью продолжит JSON. Если начать с `## `, модель продолжит markdown-заголовком.

### Порядок сообщений имеет значение

Из предыдущей статьи: модели лучше обрабатывают начало и конец контекста. Из этого следует практика:

```ts
// Менее оптимально: задача погребена в истории
const messages = [
  { role: "user",      content: "Задача: отрефактори функцию" },
  { role: "assistant", content: "Хорошо, покажи код" },
  { role: "user",      content: "<500 строк кода>" },
  { role: "assistant", content: "Вижу несколько проблем..." },
  { role: "user",      content: "Исправь только функцию parseDate" }, // важное — в конце ✓
];

// Лучше: конкретизация задачи в последнем сообщении
// Ключевые ограничения — в system prompt
```

## Zero-shot, one-shot, few-shot

### Zero-shot: задача без примеров

Zero-shot — самый простой вариант: описываем задачу, не давая примеров. Работает хорошо для распространённых задач, которые модель «видела» в обучении.

```ts
// Zero-shot: только инструкция
const prompt = `Определи тональность отзыва: положительная, отрицательная или нейтральная.

Отзыв: "Быстрая доставка, но упаковка помята"`;

// Модель ответит что-то вроде: "нейтральная" или "смешанная"
```

Проблема zero-shot: модель самостоятельно интерпретирует формат вывода. Результат может быть «нейтральная», «Нейтральная», «Тональность: нейтральная», «Это смешанный отзыв...» — всё это требует разного парсинга.

### One-shot: один пример

Один пример резко сужает пространство интерпретаций и задаёт формат:

```ts
const prompt = `Определи тональность. Отвечай одним словом: positive / negative / neutral.

Отзыв: "Отличный товар, рекомендую!"
Тональность: positive

Отзыв: "Быстрая доставка, но упаковка помята"
Тональность:`;

// Модель почти наверняка ответит: neutral
```

### Few-shot: несколько примеров

Few-shot работает лучше one-shot в задачах, где есть неочевидная логика классификации или специфический домен:

```ts
const prompt = `Определи категорию бага по описанию. 
Категории: ui, performance, data, auth, network.

Описание: "Кнопка не реагирует на клик в Firefox"
Категория: ui

Описание: "Страница загружается 8 секунд при 200 записях"
Категория: performance

Описание: "После обновления токен не обновляется автоматически"
Категория: auth

Описание: "При фильтрации показываются удалённые записи"
Категория: data

Описание: "Форма не отправляется при медленном интернете"
Категория:`;
```

### Когда few-shot действительно помогает

Few-shot эффективен в трёх случаях:

1. **Нестандартный формат вывода** — когда стандартный JSON или prose не подходит, а нужна специфическая структура
2. **Доменная специфика** — классификация по внутренним категориям, которых нет в общем обучении
3. **Граничные случаи** — примеры можно включить именно для неоднозначных входных данных

```ts
// Few-shot для нестандартного формата логов
const examples = [
  {
    input: "TypeError: Cannot read property 'id' of undefined at UserCard.tsx:42",
    output: "[ERROR] UserCard.tsx:42 | TypeError | property access on undefined"
  },
  {
    input: "Warning: Each child in a list should have a unique 'key' prop",
    output: "[WARN] React | missing list key"
  },
];

const fewShotPrompt = examples
  .map(e => `Input: ${e.input}\nOutput: ${e.output}`)
  .join("\n\n");
```

**Правило качества примеров**: плохой пример вреднее, чем его отсутствие. Если примеры противоречат друг другу или содержат исключения без объяснения — модель обучается на противоречии.

## Chain-of-thought и его вариации

### Проблема: сложные рассуждения без промежуточных шагов

Классический эксперимент из исследовательской литературы: если спросить модель напрямую «Если я куплю 3 яблока по 7 рублей и 5 груш по 11 рублей, сколько останется сдачи со 100 рублей?», она нередко ошибается. Если попросить «рассуждай пошагово», точность резко возрастает.

Причина: модель генерирует токены последовательно. При прямом ответе у неё нет «места», чтобы вычислить промежуточные результаты — они должны появиться в тексте.

### Базовый Chain-of-Thought (CoT)

```ts
// Без CoT: модель даёт ответ напрямую
const directPrompt = `Определи, есть ли в этом коде утечка памяти:\n${code}`;

// С CoT: инструкция думать вслух
const cotPrompt = `Определи, есть ли в этом коде утечка памяти.
Рассуждай пошагово:
1. Определи все подписки, таймеры и слушатели событий
2. Проверь, есть ли cleanup для каждого из них
3. Сделай вывод

Код:\n${code}`;
```

CoT особенно эффективен для задач с многошаговой логикой: дебаггинг, анализ кода, принятие архитектурных решений, проверка корректности алгоритма.

### Zero-shot CoT: «Think step by step»

Открытие исследования Kojima et al. (2022): достаточно добавить «Let's think step by step» (или «Рассуждай пошагово») — и модель сама выстраивает промежуточные шаги. Это работает, потому что фраза активирует паттерны из обучающих данных, где рассуждения записывались именно так.

```ts
// Магическая фраза, которая реально работает
const prompt = `${задача}\n\nРассуждай пошагово.`;

// Или более конкретно
const prompt = `${задача}\n\nДавай разберём это по шагам.`;
```

### Self-consistency: несколько путей рассуждения

Вариация CoT для задач с неоднозначным ответом: запускаем несколько независимых цепочек рассуждений (с temperature > 0) и выбираем наиболее частый ответ.

```ts
async function selfConsistency(prompt: string, runs = 5): Promise<string> {
  const results = await Promise.all(
    Array.from({ length: runs }, () =>
      client.messages.create({
        model: "claude-sonnet-4-6",
        max_tokens: 512,
        temperature: 0.7,
        messages: [{ role: "user", content: prompt + "\n\nРассуждай пошагово." }],
      })
    )
  );

  const answers = results.map(r => extractFinalAnswer(r.content[0].text));
  return mostFrequent(answers);
}
```

Self-consistency увеличивает стоимость в N раз, но для критически важных задач (медицина, юридический анализ, финансы) это оправдано.

### Когда CoT НЕ помогает

CoT не универсален:
- **Простые факты**: «Какая столица Франции?» — рассуждение только тратит токены
- **Творческие задачи**: «Напиши стихотворение про осень» — CoT ограничивает свободу
- **Задачи классификации с очевидным ответом**: избыточное рассуждение может даже снизить точность

```ts
// Не нужен CoT — прямой вопрос, прямой ответ
const simple = `Переведи на английский: "Привет, мир"`;

// CoT здесь полезен — нужна многошаговая логика
const complex = `Найди все N+1 проблемы в этом коде и предложи оптимизации:\n${code}`;
```

## Structured output: JSON mode и XML-теги

### Проблема ненадёжного вывода

Без явных ограничений модель самостоятельно выбирает формат ответа. При вызове из кода это создаёт проблему: нужен парсинг, а значит — потенциальные ошибки.

```ts
// Плохо: формат непредсказуем
const response = "Имя: Иван\nВозраст: 25\nГород: Москва";
const response2 = "{ name: 'Иван', age: 25 }";  // не валидный JSON
const response3 = "Пользователь Иван, 25 лет, проживает в Москве.";
```

### JSON mode

Многие провайдеры поддерживают JSON mode — принудительный вывод в формате JSON. Модель гарантирует валидный JSON, но **не гарантирует конкретную схему**.

```ts
// С JSON mode (через tool use у Anthropic)
const response = await client.messages.create({
  model: "claude-sonnet-4-6",
  tools: [{
    name: "extract_user",
    description: "Извлечь данные пользователя",
    input_schema: {
      type: "object",
      properties: {
        name:    { type: "string" },
        age:     { type: "number" },
        city:    { type: "string" },
      },
      required: ["name", "age", "city"],
    },
  }],
  tool_choice: { type: "tool", name: "extract_user" },
  messages: [{ role: "user", content: text }],
});

// Результат в response.content[0].input — типизированный объект
const userData = response.content[0].input;
```

Tool use / function calling — наиболее надёжный способ получить структурированный вывод. Модель «вызывает» инструмент с типизированными аргументами, а не генерирует свободный текст.

### XML-теги: структура без инструментов

Альтернатива, не требующая tool use: попросить модель обернуть нужные части ответа в XML-теги, а затем распарсить тегированный вывод.

```ts
const prompt = `Проанализируй код и ответь в следующем формате:

<bugs>
  <bug>
    <line>номер строки</line>
    <severity>critical|warning|info</severity>
    <description>описание проблемы</description>
  </bug>
</bugs>

<summary>краткий итог проверки</summary>

Код:\n${code}`;

// Парсинг результата
function parseXmlBugs(response: string) {
  const bugsMatch = response.match(/<bugs>([\s\S]*?)<\/bugs>/);
  // ... парсинг XML
}
```

XML-теги работают стабильнее, чем просьба вернуть «чистый JSON» без tool use — модель менее склонна добавлять текст вокруг XML-структуры.

### Вывод с Zod-валидацией

Паттерн для продакшн-кода: описываем схему через Zod и валидируем вывод модели.

```ts
import { z } from "zod";

const BugSchema = z.object({
  line: z.number(),
  severity: z.enum(["critical", "warning", "info"]),
  description: z.string(),
});

const ReviewSchema = z.object({
  bugs: z.array(BugSchema),
  summary: z.string(),
});

async function reviewCode(code: string) {
  const response = await client.messages.create({
    tools: [{ name: "review", input_schema: zodToJsonSchema(ReviewSchema) }],
    tool_choice: { type: "tool", name: "review" },
    // ...
  });

  return ReviewSchema.parse(response.content[0].input);
}
```

## Role prompting

### Как роль влияет на поведение модели

Модели обучены на огромных корпусах текста, где разные типы авторов пишут по-разному: врачи иначе, чем журналисты; старшие инженеры иначе, чем студенты. Назначив роль в system prompt, вы смещаете вероятностное распределение в сторону паттернов соответствующего типа текста.

```ts
// Без роли: модель даёт общий ответ
const genericSystem = "Ты — помощник.";

// С ролью: активируется доменный словарь и стиль
const seniorEngineerSystem = `Ты — старший фронтенд-инженер с 10 годами опыта.
Твои ответы конкретны, включают трейдоффы, не упрощают сложного.
Ты предполагаешь, что собеседник понимает базовые концепции.`;
```

### Практические применения

```ts
// Для code review — строгий рецензент
const strictReviewer = `Ты — педантичный технический рецензент.
Находишь не только баги, но и нарушения принципов чистого кода.
Не хвалишь без причины. Каждое замечание — с объяснением почему это проблема.`;

// Для документации — технический писатель
const techWriter = `Ты — технический писатель, специализирующийся на документации API.
Пишешь ясно, избегаешь пассивного залога.
Каждый параметр описываешь: тип, когда требуется, пример значения.`;

// Для объяснения кода новичку — педагог
const pedagogue = `Ты объясняешь код разработчику с 6 месяцами опыта.
Используешь аналогии из реальной жизни. Избегаешь жаргона без объяснения.
После объяснения задаёшь проверочный вопрос.`;
```

### Ограничения role prompting

Роль — это направление, а не точная настройка. Модель всё равно остаётся моделью: она не «знает больше» из-за назначенной роли, она просто генерирует текст, характерный для этой роли. Это может приводить к более уверенному тону при той же точности.

```ts
// Антипаттерн: роль как замена знаниям
// Модель не станет лучше разбираться в Rust только от того, что вы назначили её
// "экспертом по Rust" — она будет звучать увереннее, но не точнее

// Хорошее применение роли: стиль, формат, уровень детализации
// Плохое применение: попытка «заставить» модель знать то, что она не знает
```

## Prompt chaining

### Когда одного промпта недостаточно

Сложные задачи плохо решаются одним запросом: слишком много требований одновременно, конкурирующие цели или задача слишком длинная для одного вывода. Prompt chaining — разбиение на последовательность более простых шагов, где вывод одного шага становится входом следующего.

```ts
// Одним запросом: перегружен инструкциями, плохой результат
const overloadedPrompt = `
  Проанализируй этот код, найди все баги, 
  исправь их, задокументируй изменения, 
  напиши тесты, и обнови README
`;

// Цепочка: каждый шаг фокусирован
async function processCode(code: string) {
  // Шаг 1: анализ
  const analysis = await analyzeCode(code);

  // Шаг 2: исправление на основе анализа
  const fixedCode = await fixBugs(code, analysis);

  // Шаг 3: тесты на основе исправленного кода
  const tests = await generateTests(fixedCode, analysis);

  return { fixedCode, tests, analysis };
}
```

### Паттерн: декомпозиция + агрегация

```ts
// Обработка длинного документа: разбиваем, обрабатываем части, собираем
async function summarizeLargeDoc(sections: string[]): Promise<string> {
  // Шаг 1: суммаризация каждой части независимо
  const sectionSummaries = await Promise.all(
    sections.map(section =>
      client.messages.create({
        messages: [{ role: "user", content: `Суммаризируй кратко:\n${section}` }],
        // ...
      })
    )
  );

  // Шаг 2: агрегация суммаризаций
  const combinedSummaries = sectionSummaries
    .map(r => r.content[0].text)
    .join("\n\n");

  const finalSummary = await client.messages.create({
    messages: [{
      role: "user",
      content: `На основе этих суммаризаций разделов создай финальное резюме:\n${combinedSummaries}`,
    }],
    // ...
  });

  return finalSummary.content[0].text;
}
```

### Паттерн: генерация + проверка

Второй распространённый случай: генерируем результат первым вызовом, проверяем корректность вторым.

```ts
async function generateWithVerification(spec: string) {
  // Шаг 1: генерация
  const generated = await client.messages.create({
    messages: [{ role: "user", content: `Реализуй функцию по спецификации:\n${spec}` }],
    // ...
  });

  const code = generated.content[0].text;

  // Шаг 2: независимая проверка
  const review = await client.messages.create({
    messages: [{
      role: "user",
      content: `Проверь, соответствует ли этот код спецификации. 
Спецификация:\n${spec}
Код:\n${code}
Ответь: "ok" если соответствует, иначе — список несоответствий.`,
    }],
    // ...
  });

  const reviewText = review.content[0].text.trim();

  if (reviewText === "ok") return code;
  return regenerate(spec, reviewText); // передаём несоответствия для исправления
}
```

### Когда цепочки не нужны

Prompt chaining добавляет latency и стоимость. Не стоит применять его ради красивой архитектуры:

- Если задача решается одним промптом с приемлемым качеством — это лучший вариант
- Для интерактивных интерфейсов каждый лишний вызов — задержка для пользователя
- Современные модели справляются с многошаговыми задачами лучше, чем год назад

## Антипаттерны и типичные ошибки

### Избыточная вежливость

```ts
// Плохо: токены на вежливость — это деньги и latency
const prompt = `Пожалуйста, не могли бы вы любезно помочь мне, если вас не затруднит,
проанализировать этот код и, если возможно, указать на возможные улучшения?`;

// Хорошо: директивный тон
const prompt = `Проанализируй код. Укажи проблемы и улучшения.`;
```

Модели не обижаются. Вежливые обороты занимают токены и могут размывать инструкции.

### Противоречивые инструкции

```ts
// Плохо: система говорит одно, пользователь — другое, задача неясна
const system = "Отвечай кратко, не более 2 предложений.";
const user = "Подробно объясни все аспекты алгоритма сортировки слиянием.";

// Модель попытается как-то примирить противоречие — непредсказуемо
```

Если инструкции конфликтуют, приоритет зависит от модели и контекста. Решение — согласованные инструкции или явный приоритет в system prompt.

### Негативные инструкции без позитивной альтернативы

```ts
// Хуже: только запрет
const system = "Не используй markdown. Не пиши заголовки. Не делай списки.";

// Лучше: явно желаемый формат
const system = "Отвечай простым текстом, сплошными абзацами, без форматирования.";
```

«Не делай X» менее эффективно, чем «делай Y». Модель должна знать, что делать, а не только чего избегать.

### Перегрузка одного промпта

```ts
// Плохо: слишком много задач одновременно
const prompt = `
  1. Найди все баги
  2. Перепиши на TypeScript
  3. Добавь тесты
  4. Сделай код функциональным (без мутаций)
  5. Задокументируй каждую функцию
  6. Оптимизируй производительность
`;

// Хорошо: одна чёткая задача
const prompt = `Найди все баги в этом коде. Для каждого: строка, описание, уровень критичности.`;
```

### Неясный критерий качества

```ts
// Плохо: «хорошо» — субъективно и неизмеримо
const prompt = "Напиши хороший компонент для формы входа.";

// Хорошо: конкретные критерии
const prompt = `Напиши React-компонент формы входа:
- Поля: email, password
- Валидация на submit: email format, password min 8 символов
- Сообщения об ошибках под каждым полем
- Disabled-состояние кнопки во время запроса
- TypeScript, без сторонних библиотек для форм`;
```

### Неправильное использование temperature

```ts
// Плохо: высокая температура для детерминированных задач
const jsonExtraction = await client.messages.create({
  temperature: 0.9, // случайность в JSON = битые данные
  messages: [{ role: "user", content: `Извлеки данные в JSON:\n${text}` }],
});

// Правило: extraction / classification / code → temperature 0
// Brainstorming / creative → temperature 0.7-1.0
```

## Ключевые тезисы для интервью

- Промпт состоит из трёх ролей: system (поведение сессии), user (конкретная задача), assistant (история ответов); prefill — начало ответа для управления форматом.
- Few-shot — примеры в промпте для калибровки формата и логики; качество примеров важнее их количества.
- Chain-of-Thought (CoT) вынуждает модель генерировать промежуточные шаги рассуждения в тексте — это повышает точность на сложных многошаговых задачах, потому что каждый токен может «опираться» на предыдущие.
- Для надёжного структурированного вывода лучше tool use / function calling, а не просьба «верни JSON» — схема задана явно, а не угадывается моделью.
- Role prompting сдвигает стиль и детализацию, но не добавляет знаний — модель не станет точнее только потому, что назначена «экспертом».
- Prompt chaining — декомпозиция сложной задачи на последовательные вызовы; каждый шаг фокусированный, вывод одного — вход следующего.
- Негативные инструкции («не делай X») менее эффективны, чем позитивные («делай Y»).
- Temperature 0 для детерминированных задач (код, JSON, классификация); temperature 0.7+ для творческих.

## Заключение

Промптинг — это инженерная дисциплина, а не интуиция. Несколько принципов, которые работают всегда:

- Чёткие инструкции побеждают длинные. Конкретный формат лучше общего «напиши хорошо».
- Примеры эффективнее объяснений. One-shot часто даёт лучший результат, чем развёрнутая инструкция без примера.
- Промежуточные шаги — это токены в тексте. CoT работает потому, что рассуждение буквально записывается в ответе.
- Структурированный вывод — через схему, не через надежду. Tool use надёжнее, чем «верни JSON».
- Один промпт — одна задача. Сложное разбивается на цепочку.
