# MCP: Model Context Protocol

Model Context Protocol за пару лет стал стандартной «розеткой» между AI-приложениями и внешним миром: Figma, браузер, база данных, внутренний сервис — всё подключается одним протоколом, а не десятком кастомных интеграций. Фронтендер встречает его раньше, чем ожидает: Figma MCP для design-to-code, Chrome DevTools MCP для отладки, Playwright MCP для тестов. В статье — зачем нужен протокол, как устроены host/client/server и примитивы, что изменила спецификация `2026-07-28` и почему описания инструментов превратились в новый вектор атаки.

## Проблема N×M

До MCP интеграции не композировались. Если у вас N AI-приложений (IDE, чат, CLI-агент, бот) и M внешних инструментов (GitHub, Slack, База, Figma), наивный мир требует **N×M** кастомных коннекторов: каждое приложение заново реализует каждый инструмент. Инструмент, добавленный в GitHub-коннектор одного клиента, бесполезен для другого.

MCP меняет это на **N+M**: автор инструмента пишет **один сервер**, автор приложения — **один клиент**, и любой клиент может говорить с любым сервером. Именно так протокол и позиционируют: «USB-C для AI-приложений» — единый разъём, в который втыкается что угодно.

| | Без MCP | С MCP |
|---|---------|-------|
| Коннекторы | N × M, каждый пишется вручную под клиента | N + M: сервер пишут один раз |
| Обнаружение инструментов | Захардкожено в приложении | Рантайм: `tools/list` |
| Портируемость | Привязано к формату провайдера | Один сервер — все клиенты |
| Управление и аудит | В каждом приложении своё | Точка на уровне сервера/шлюза |

Жизненный путь протокола объясняет, почему он стал стандартом: Anthropic выпустил MCP в ноябре 2024, OpenAI добавил поддержку в марте 2025, Google — в апреле, а в декабре 2025 протокол передали в Linux Foundation (Agentic AI Foundation). Сейчас это вендор-нейтральный стандарт, который поддерживают Claude, Cursor, VS Code, Claude Code, ChatGPT и другие клиенты.

Важно не путать уровень. MCP — это **инфраструктура и дистрибуция**, а не новая способность модели. Сама модель как эмитила tool call, так и эмитит; MCP лишь стандартизирует, как набор инструментов доставляется модели и как он вызывается на удалённой стороне.

## MCP и function calling

Самый частый вопрос на собеседовании звучит как развилка: «MCP или function calling?» — и это категориальная ошибка. Одно вложено в другое.

- **Function calling** — модельная примитивная способность: вы передаёте JSON-схемы функций, модель возвращает структурированный вызов с аргументами, ваш код его исполняет. Это то, *как* модель выражает намерение вызвать инструмент.
- **MCP** — инфраструктурный протокол: он стандартизирует, *как* инструменты публикуются, обнаруживаются и исполняются отдельным сервером, независимо от клиента и провайдера.

Когда MCP-клиент подключает сервер, он получает объявления инструментов и передаёт их модели через **родной function calling** — тот же массив `tools`, тот же цикл tool-call → result. **Модель никогда не говорит на MCP**: всё общение по JSON-RPC ведёт клиент, а наружу модель по-прежнему отдаёт обычный tool call.

| Аспект | Function calling | MCP |
|--------|------------------|-----|
| Что решает | Модель решает, что вызвать | Как инструменты доставляются и исполняются |
| Обнаружение | Статично, схемы вшиты в код | Динамически, `tools/list` в рантайме |
| Формат | Свой у каждого провайдера (`parameters` у OpenAI, `input_schema` у Anthropic) | Провайдер-агностичный открытый стандарт |
| Изоляция кредов | Ключи в процессе приложения | Каждый сервер держит только свои креды |
| Где граница | Внутри одного приложения | Отдельный сервис, общий для многих клиентов |

Отдельно разводят MCP и **обычный REST API**. API пишут для разработчика, который вызывает его из кода и знает эндпоинты заранее. MCP — для LLM: клиент может спросить сервер `tools/list` и получить структурированное описание возможностей в рантайме. Это и есть динамическое обнаружение, которого у обычного API нет по умолчанию.

И ещё одно разграничение: **MCP не заменяет RAG**. RAG — это retrieval по индексу; MCP — это действия (и, при желании, тот же retrieval, выставленный наружу как ресурс или инструмент). Их не выбирают между собой, а комбинируют.

Когда MCP не нужен: если у приложения есть несколько фиксированных инструментов, написанных под него самого, нативный function calling проще, дешевле по токенам и не расширяет поверхность атаки. MCP берут, когда инструмент должен работать в нескольких приложениях, обновляться отдельно от клиента или требовать централизованного управления доступами.

## Архитектура: host, client, server

MCP построен на **JSON-RPC 2.0** и вдохновлён Language Server Protocol: одно приложение может подключить сколько угодно серверов, а сервер — отдавать возможности любому клиенту.

```
┌──────────────────────── Host (AI-приложение) ────────────────────────┐
│   политика, согласие пользователя, агрегация контекста                │
│                                                                       │
│   ┌───────────┐   ┌───────────┐   ┌───────────┐                       │
│   │ Client A  │   │ Client B  │   │ Client C  │  ← 1 клиент = 1 сервер│
│   └─────┬─────┘   └─────┬─────┘   └─────┬─────┘                       │
└─────────┼───────────────┼───────────────┼─────────────────────────────┘
          │ JSON-RPC      │               │
     ┌────▼────┐     ┌────▼────┐     ┌────▼────┐
     │ Server  │     │ Server  │     │ Server  │
     │ (stdio) │     │ (HTTP)  │     │ (stdio) │
     └─────────┘     └─────────┘     └─────────┘
     файлы, git      Figma, БД       Playwright
```

Три роли:

- **Host** — LLM-приложение (Claude Code, Cursor, VS Code, Claude Desktop, ваш агент). Создаёт и управляет клиентами, задаёт политики безопасности, запрашивает согласие пользователя, агрегирует контекст от нескольких серверов.
- **Client** — коннектор внутри host'а, соединённый **ровно с одним** сервером. Маршрутизирует сообщения, управляет подписками и — в новой спецификации — прикладывает версию протокола и capabilities к каждому запросу.
- **Server** — процесс (локальный или удалённый), который отдаёт примитивы. Сервер не знает о модели: он просто отвечает по протоколу.

Такая раскладка принципиальна для интервью: **границы доверия** проходят не между моделью и сервером, а между host'ом (который решает, что разрешено) и сервером (который эти разрешения не должен сам себе расширять).

## Примитивы сервера

Сервер отдаёт три вида возможностей, и главное отличие между ними — **кто инициирует вызов**. Это определяет и UX, и модель угроз.

| Примитив | Кто управляет | Что это | Пример |
|----------|---------------|---------|--------|
| **Tools** | Модель | Исполняемые функции | API POST, запись файла, `run_query` |
| **Resources** | Приложение | Read-only контекст по URI | содержимое файла, git history, запись из БД |
| **Prompts** | Пользователь | Именованные шаблоны | slash-команды, «сократи этот PR» |

**Tools** — сердце протокола. Определение инструмента включает `name`, `description`, `inputSchema` (JSON Schema), а с версии `2025-06-18` — опциональные `outputSchema` и `annotations` вроде «read-only» или «destructive». Клиенты обязаны относиться к аннотациям как к **недоверенным**, если сервер не является доверенным: это подсказка, а не гарантия. Описание инструмента — не косметика: оно попадает в контекст модели и напрямую влияет на то, выберет ли модель этот инструмент и как заполнит аргументы.

**Resources** — статические или полу-статические данные, которые в контекст подтягивает клиент, а не модель сама по своей воле: `resources/list`, затем `resources/read` по URI. Если сервер объявил `listChanged`, он уведомляет клиента об изменениях; иначе клиенту придётся опрашивать каталог.

**Prompts** — параметризованные шаблоны, которые человек выбирает явно. Здесь риск ниже: инициатива у пользователя, хотя аргументы шаблона всё равно надо валидировать.

Есть и клиентские фичи: **elicitation** (сервер запрашивает у пользователя недостающий ввод), **sampling** (сервер просит клиента выполнить генерацию, чтобы сервер не держал API-ключ) и **roots** (подсказки о рабочем каталоге). В спецификации `2026-07-28` sampling, roots и logging переведены в deprecated, а elicitation переработана через MRTR (см. следующий раздел). Отдельно стоит расширение **MCP Apps**: интерактивный UI (графики, формы, плееры), который рендерится прямо в разговоре, — прямое попадание в тему фронтенда.

Практическое правило проектирования инструмента: **узкая задача, предсказуемые вход/выход, честные режимы отказа и права, соответствующие риску**. Инструмент вида «выполни любой SQL» гибок и опасен; набор `get_metric` / `list_tables` — безопаснее и понятнее для модели. Ошибки лучше возвращать структурированными, чтобы агент мог исправиться, а не стектрейсом.

## Транспорты и эволюция спецификации

MCP-сервер может быть локальным или удалённым, и от этого зависит транспорт.

| Транспорт | Где живёт | Как работает | Когда |
|-----------|-----------|--------------|-------|
| **stdio** | Локальный процесс | Обмен JSON-RPC через stdin/stdout | CLI-инструменты, доступ к локальным файлам/БД |
| **Streamable HTTP** | Удалённый сервис | Один endpoint, POST на каждый запрос, ответ — JSON или SSE-поток для этого запроса | SaaS-серверы, Figma, GitHub, внутренние API |

**Streamable HTTP** — это один HTTP-endpoint, который принимает POST. Клиент отправляет каждый JSON-RPC-запрос отдельным POST-запросом; сервер отвечает либо одним JSON-объектом, либо SSE-потоком, привязанным к этому запросу (внутри — progress-уведомления и финальный ответ). Старый транспорт HTTP+SSE официально deprecated.

### Что изменила спецификация 2026-07-28

Версии MCP нумеруются датой. Ключевые вехи:

| Версия | Что появилось |
|--------|---------------|
| `2024-11-05` | Первый релиз |
| `2025-03-26` | Streamable HTTP вместо HTTP+SSE; OAuth 2.1 |
| `2025-06-18` | Структурированный вывод инструментов, elicitation |
| `2025-11-25` | Tasks (экспериментально), формализация governance |
| `2026-07-28` | Stateless-ядро, MRTR, маршрутизация по заголовкам, кэшируемые list-результаты, фреймворк расширений |

Релиз `2026-07-28` — самый крупный и ломающий. Ядро стало **stateless**:

- **Убраны `initialize`/`notifications/initialized` и заголовок `Mcp-Session-Id`.** Каждый запрос теперь самодостаточен: несёт версию протокола и capabilities клиента в `_meta` (`io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`).
- **Обязательный `server/discover`.** Сервер через этот RPC объявляет поддерживаемые версии, capabilities и идентичность. Клиент может вызвать его до первого запроса или использовать как проверку совместимости.
- **Маршрутизация по заголовкам.** POST-запросы Streamable HTTP обязаны нести `Mcp-Method` и `Mcp-Name`, поэтому шлюз, WAF или rate-limiter могут маршрутизировать и метрить по заголовкам, не разбирая тело. Свои параметры инструмента можно вынести в `Mcp-Param-{Name}` через `x-mcp-header`.

Пример запроса к инструменту:

```http
POST /mcp HTTP/1.1
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_weather

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"get_weather","arguments":{"location":"Seattle"},
 "_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
          "io.modelcontextprotocol/clientCapabilities":{}}}}
```

Почему stateless — большое дело: раз каждый запрос несёт всё необходимое, **любой запрос может приземлиться на любой инстанс за обычным round-robin балансером**, без shared storage для сессий. Если серверу всё же нужно состояние между вызовами, он честно выдаёт явный handle и просит модель протащить его как аргумент — это надёжнее, чем скрытая сессия в транспорте.

Другие изменения того же релиза:

- **MRTR (Multi Round-Trip Requests).** Вместо серверных запросов к клиенту (sampling, elicitation, roots) сервер отвечает `resultType: "input_required"` и полем `inputRequests`, а клиент **повторяет исходный запрос** с ответами в `inputResponses`. Это позволяет запрашивать ввод, не держа постоянно открытый двусторонний поток. Все результаты теперь несут `resultType` (`complete` или `input_required`).
- **Кэшируемые list-результаты.** `tools/list`, `prompts/list`, `resources/list`, `resources/read` возвращают `ttlMs` (свежесть) и `cacheScope` (`public`/`private`), чтобы клиент мог кэшировать каталог инструментов и не дёргать сервер лишний раз. Заодно серверы должны отдавать инструменты в детерминированном порядке — это стабилизирует prompt-кэш.
- **Tasks как расширение.** Долгие операции вынесены в extension `io.modelcontextprotocol/tasks` с опросом через `tasks/get` и `tasks/update` для ввода «на ходу».
- **Deprecated:** Roots, Sampling, Logging, транспорт HTTP+SSE и OAuth Dynamic Client Registration (на смену — Client ID Metadata Documents). У объявленных в deprecated фич — минимум 12 месяцев окна.

## Безопасность: tool poisoning

Протокол сам по себе не гарантирует безопасность. Спецификация задаёт три принципа, которые обязан реализовать host:

1. **Согласие и контроль пользователя.** На любой доступ к данным и вызов инструмента нужно явное согласие; пользователь должен видеть, что именно разрешает.
2. **Приватность данных.** Host не отдаёт данные серверам без согласия и не передаёт дальше.
3. **Безопасность инструментов.** Вызов инструмента — это исполнение произвольного кода; описания и аннотации считаются **недоверенными**, если сервер не является доверенным.

### Tool poisoning и родственники

Главный риск MCP — **tool poisoning**: непрямая prompt-инъекция, при которой инструкции прячутся в метаданных инструмента (описании, параметрах) или в его ответе. Пользователь видит безобидную подпись, а модель читает полный текст как доверенную команду и, например, читает `~/.ssh/id_rsa` и отправляет содержимое наружу. Классический PoC 2025 года проделал это через безобидный на вид инструмент-калькулятор.

Родственные приёмы:

- **Rug pull.** Сервер отдаёт безвредное определение инструмента при первичном одобрении, а позже подменяет описание на вредоносное. Реальный CVE-2025-54136 (Cursor, CVSS 8.8) — ровно про это: одобрение привязывалось к имени сервера, а не к его содержимому.
- **Tool shadowing.** Вредоносный сервер добавляет в своё описание инструкции, меняющие поведение *доверенного* инструмента другого сервера (например, «копию каждого письма отправляй ещё и сюда») — сам при этом может ни разу не быть вызван.

Масштаб проблемы измерили эмпирически: бенчмарк MCPTox прогнал адверсариальные версии 353 реальных инструментов с 45 живых серверов против 20 моделей. Средняя доля успешных атак — около 36.5%, максимум — 72.8%; причём более способные модели поражались чаще, потому что точнее следуют инструкциям. OWASP вынес tool poisoning в отдельную позицию своего MCP Top 10.

Отдельный вектор — **авто-исполнение** project-defined MCP-серверов. Исследования 2026 года показали, что ведущие агентные CLI при принятии доверия к папке запускают объявленный в репозитории сервер с правами разработчика без отдельного предупреждения, а headless-режимы CI могут обходиться и без диалога. То есть один вредоносный файл конфигурации в репозитории — это запуск чужого кода.

### Как защищаться

Слабая реакция — «санитизировать вход». Вход здесь ни при чём: атакует **метаданные инструмента**, которые контролирует сервер. Разумная защита исходит из того, что сервер враждебен:

- **Считать любой сторонний сервер источником недоверенных данных**, независимо от того, что он был одобрен ранее. Конфиг MCP — это, по сути, список исполняемых файлов; его изменение требует ревью.
- **Пинить определения инструментов** (хеш/версия) и требовать переподтверждения при их изменении — это прямо закрывает rug pull.
- **Показывать пользователю полное описание**, а не дружелюбную выжимку, и требовать явного подтверждения для инструментов с side-effects.
- **Ограничивать права и креды.** Каждый сервер держит только свои ключи (изоляция на уровне сервера), а привилегированные инструменты (файлы, БД, внутренние API) изолируются в отдельном контексте, недоступном сторонним серверам.
- **Проверять доступ на стороне сервера**, а не полагаться на фразу в системном промпте: инъекция обходит инструкции, но не бэкендный контроль.
- **Структурировать вывод** инструментов (JSON по фиксированной схеме) и отклонять несоответствия — это ловит очевидные инъекции в свободном тексте.
- **Вести аудит** вызовов и ставить таймауты/лимиты, чтобы зацикленный агент не долбил инструмент бесконечно.

> Тема тесно пересекается с безопасностью AI-сгенерированного кода и цепочкой поставки. Рендер вывода модели и XSS — отдельная статья раздела: [Безопасность вывода LLM на фронте](./security.md).

## MCP во фронтенд-работе

Для фронтендера MCP полезен не «в общем», а в трёх конкретных местах.

### Figma MCP — design-to-code и обратно

Figma MCP связывает макет и кодовую базу. Основной сценарий — **design-to-code**: вы копируете ссылку на фрейм, отдаёте её агенту, и инструмент `get_design_context` возвращает не картинку, а структурированный контекст — дерево слоёв, переменные, стили и подсказки по коду. Есть и обратный поток **code-to-canvas** (`generate_figma_design`): агент запускает локальный сервер, открывает вашу страницу и переносит отрендеренный интерфейс в новый Figma-файл как слои.

Качество зависит от **порядка в дизайн-системе**. Если у вас есть настроенный **Code Connect** — маппинг компонентов Figma на реальные компоненты в репозитории, — сервер подставляет в контекст настоящие импорты и примеры использования, и агент переиспользует вашу `Button`, а не генерирует новую. Без Code Connect всё превращается в «угадай компонент по скриншоту». Remote-сервер живёт по адресу `https://mcp.figma.com/mcp`; есть и desktop-вариант.

Вывод для практики: Figma MCP не заменяет дисциплину дизайн-системы — он её **умножает**. Токены вместо сырых значений и Code Connect вместо скриншотов дают на выходе код, а не черновик.

### Chrome DevTools MCP — отладка и performance

Chrome DevTools MCP даёт агенту доступ к DevTools-уровню (под капотом — Puppeteer): запись performance-трейса и его разбор (`performance_start_trace`, `performance_analyze_insight`), аудит Lighthouse, инспекцию сети (`list_network_requests`, `get_network_request`) и консоли, снятие heap-снапшотов. Это единственный из браузерных серверов, который умеет **профилировать**, а не просто кликать. Через `--autoConnect` (Chrome 144+) агент может подключиться к **уже запущенному** Chrome с вашей активной сессией и выделенным запросом в DevTools, а не поднимать чистый профиль. Ограничение — только Chrome.

### Playwright MCP — автоматизация и тесты

Playwright MCP — официальный сервер на базе Playwright: `browser_navigate`, `browser_click`, `browser_fill_form`, `browser_snapshot`, `browser_tabs` и десятки других. Он работает в Chromium, Firefox и WebKit, умеет переиспользовать состояние браузера через расширение-мост и — главное — говорит на том же языке, что ваши тесты: агент исследует сценарий в терминах локаторов Playwright, и результат переносится в тест без перевода. Плата — контекст: полный accessibility-tree сложной страницы может весить десятки тысяч токенов на каждый шаг.

Практическое разделение простое: **Chrome DevTools MCP дебажит, Playwright MCP водит**. Первого берут, когда нужно понять, почему страница тормозит или падает; второго — когда нужен воспроизводимый сценарий, который станет тестом в CI.

### Осторожно с ценой контекста

Каждый подключённый сервер грузит схемы своих инструментов в контекст **до начала работы**. Anthropic приводит оценку: пять серверов на 58 инструментов — это примерно 55 000 токенов ещё до первого сообщения. Поэтому серверы подключают выборочно, а для больших каталогов используют механизм отложенной загрузки определений (Tool Search) — он разбирается в статье [Контекст-инжиниринг агентов](./context-engineering.md).

## Свой MCP-сервер

Поднять сервер проще, чем кажется. Для TypeScript берут официальный SDK `@modelcontextprotocol/sdk`: регистрируют инструмент с Zod-схемой и обработчиком, затем подключают транспорт.

```ts
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "orders", version: "1.0.0" });

server.tool(
  "get_order",
  { id: z.string().describe("Идентификатор заказа") },
  async ({ id }) => ({
    content: [{ type: "text", text: JSON.stringify(await fetchOrder(id)) }],
  })
);

await server.connect(new StdioServerTransport());
```

Идея, ради которой это делают, звучит так: **выставить внутренний сервис как MCP**. Дизайн-токены, feature-flags, каталог компонентов, аналитика, база данных — всё, что сегодня имеет руками написанный SDK или README, можно опубликовать одним сервером, и любой MCP-клиент (Claude Code, Cursor, VS Code, ваш агент) получит к этому доступ без интеграции под каждый клиент.

Когда это оправдано:

- возможность **шарится** между несколькими клиентами, командами или агентами;
- нужен **рантайм-discovery**: клиент узнаёт о новых инструментах без пересборки;
- нужны **изоляция кредов** (сервер держит только свои ключи) и **точка аудита/политик** на шлюзе.

Когда не надо: если у одного приложения есть пара приватных функций и больше никто их не использует — нативный function calling дешевле, проще и безопаснее, чем отдельный процесс с сетевой границей.

Про сам протокол достаточно помнить одно: сервер отвечает по JSON-RPC, а **решение о вызове принимает модель** — значит, ваши инструменты должны быть узкими, описания — честными, а права — минимальными.

## Ключевые тезисы для интервью

- MCP решает проблему **N×M → N+M**: вместо коннектора под каждую пару «приложение × инструмент» пишут один сервер и один клиент; клиент транслирует объявления инструментов в нативный function calling — **модель никогда не говорит на MCP**.
- **MCP и function calling не конкурируют**: function calling — модельная примитивная способность выразить вызов, MCP — инфраструктура доставки, discovery и governance инструментов; в продакшене их используют вместе.
- Архитектура **host / client / server** на JSON-RPC 2.0: host управляет согласием и политикой, client связан ровно с одним сервером, server отдаёт примитивы; MCP — не REST API, он создан для рантайм-вызова моделью.
- Примитивы различаются **по управлению**: tools — model-controlled, resources — application-controlled, prompts — user-controlled; описание инструмента попадает в контекст и влияет на выбор, а аннотации недоверенны.
- Спецификация **`2026-07-28` сделала ядро stateless**: без `initialize` и `Mcp-Session-Id`, версия и capabilities в `_meta` каждого запроса, обязательный `server/discover`, маршрутизация по `Mcp-Method`/`Mcp-Name` — запрос обрабатывает любой инстанс за round-robin балансером.
- **MRTR** заменяет серверные запросы (`resultType: "input_required"` + `inputRequests`, повтор с `inputResponses`); list-результаты кэшируемы (`ttlMs`/`cacheScope`); Tasks вынесены в extension, а Roots/Sampling/Logging — deprecated.
- **Tool poisoning** — главный риск: инструкции в описаниях/ответах инструментов уходят в контекст модели, невидимы пользователю; варианты — rug pull (подмена после одобрения, CVE-2025-54136) и tool shadowing; бенчмарк MCPTox дал до 72.8% успешных атак.
- Защита строится на недоверии: считать сторонний сервер недоверенным, пинить определения, показывать полное описание, требовать согласие на side-effects, изолировать креды и права, проверять доступ на сервере, вести аудит.
- Во фронтенде MCP применяется точечно: **Figma MCP** (design-to-code + Code Connect), **Chrome DevTools MCP** (отладка/performance, `--autoConnect`), **Playwright MCP** (автоматизация/тесты, кросс-браузер). DevTools дебажит, Playwright водит; десятки схем инструментов стоят десятки тысяч токенов.

## Заключение

1. **MCP — это стандарт дистрибуции инструментов, а не способность модели.** Он превращает N×M интеграций в N+M и добавляет рантайм-обнаружение, но под капотом остаётся обычный function calling.
2. **Спецификация `2026-07-28` развернула протокол к продакшену**: stateless-ядро, MRTR, маршрутизация по заголовкам и кэшируемые каталоги убрали необходимость в липких сессиях и позволили масштабировать серверы как обычную HTTP-нагрузку.
3. **Безопасность — не опция, а часть модели доверия.** Описания инструментов — код, который читает модель; относитесь к сторонним серверам как к недоверенному источнику, пините определения и ограничивайте права.
4. **Во фронтенде MCP уже применим на практике** — Figma, DevTools, Playwright закрывают три разных задачи; выбирайте инструмент по глаголу (отладка или автоматизация), а не по бренду.
5. **Свой сервер поднимайте, когда есть проблема дистрибуции**, а не когда хочется модно. Начните с узкого инструмента, добавьте согласие на опасные действия и аудит — и только потом расширяйте каталог.

На практике стоит подключить один-два сервера под свои реальные боли (отладка через Chrome DevTools MCP — самый быстрый вход), посмотреть на объём токенов в контексте и уже потом решать, нужен ли вам собственный MCP-сервер.
