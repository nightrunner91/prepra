# AI в рабочем процессе разработчика

AI-ассистент — не замена разработчику, а усилитель. Но усилитель, который работает избирательно: в одних задачах он даёт кратный рост продуктивности, в других — генерирует код, который выглядит правильно, но содержит тонкие ошибки. Разница между эффективным и опасным использованием — в понимании, где AI силён, а где ненадёжен. Эта статья применяет паттерны промптинга из предыдущей статьи к конкретным рабочим задачам: генерации кода, review, рефакторингу, тестам и документации.

## Генерация кода: где работает хорошо, где ломается

### Где AI генерирует надёжно

AI-ассистент наиболее эффективен в задачах с чёткой спецификацией и устоявшимися паттернами. Чем больше примеров подобного кода модель «видела» при обучении, тем выше качество генерации.

**Надёжные задачи:**

- **CRUD-операции и boilerplate**: формы, таблицы, API-клиенты, роутинг — типовые структуры, которые модель воспроизводит точно
- **Утилитарные функции**: форматирование дат, валидация, парсинг, трансформация данных — чистые функции с очевидной логикой
- **Конвертация между форматами**: JSON ↔ TypeScript типы, CSS → inline styles, HTML → JSX
- **Шаблоны по описанию**: «компонент с debounce-поиском и выпадающим списком» — модель знает этот паттерн

```ts
// Задача: debounce-хук с cleanup
// AI генерирует корректный код, потому что паттерн хорошо известен

function useDebounce<T>(value: T, delay: number): T {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebouncedValue(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);

  return debouncedValue;
}
```

Этот код будет рабочим из коробки — паттерн `useDebounce` встречается в обучающих данных тысячи раз.

### Где AI генерирует ненадёжно

**Ненадёжные задачи:**

- **Бизнес-логика с неочевидными правилами**: модели не знают ваших внутренних требований, граничных случаев, доменных ограничений
- **Архитектурные решения с трейдоффами**: выбор между подходами зависит от контекста проекта, который модель не видит целиком
- **Код, зависящий от специфичных версий библиотек**: модель может использовать API, устаревший в вашей версии, или наоборот — ещё не существующий
- **Performance-критичные пути**: AI оптимизирует читаемость, а не производительность; hot path требует ручного анализа

```ts
// Пример ненадёжной генерации: бизнес-логика скидок
// AI не знает, что промокоды не суммируются с корпоративными скидками,
// а для подписчиков — отдельный расчёт с округлением вниз

function calculateDiscount(order: Order): number {
  // AI сгенерирует «разумную» логику, но она будет неполной:
  // - пропустит граничные случаи из вашего домена
  // - не учтёт legacy-ограничения
  // - может нарушить инварианты, о которых не написано в коде
  // ...
}
```

### Паттерн: спецификация перед генерацией

Чем точнее спецификация, тем выше качество. Паттерн из предыдущей статьи — конкретные критерии — здесь работает напрямую:

```ts
// Плохо: абстрактный запрос
const prompt = "Напиши компонент для загрузки файлов";

// Хорошо: конкретная спецификация
const prompt = `Напиши React-компонент FileUpload:
- Drag & drop зона с визуальной обратной связью (подсветка при hover)
- Поддержка множественной загрузки, максимум 5 файлов
- Валидация: только image/* и application/pdf, макс 10MB каждый
- Прогресс-бар для каждого файла во время загрузки
- Обработка ошибок: показать сообщение под файлом, возможность повторить
- API: POST /api/upload, FormData
- TypeScript, без библиотек для drag&drop
- Компонент контролируемый: value и onChange`;
```

Разница в результате — радикальная. Первый промпт даст «общий» компонент с десятком допущений. Второй — код, который можно использовать.

### Паттерн: итеративная генерация

Вместо попытки сгенерировать всё сразу — разбиваем на этажи:

```ts
// Этап 1: скелет компонента с типами
const skeleton = await generate(`
  Создай TypeScript-типы и сигнатуры для FileUpload:
  - Props: value, onChange, accept, maxSize, maxFiles
  - Internal state: файлы, статусы, прогресс, ошибки
  Не пиши реализацию — только типы и пустые функции.
`);

// Этап 2: реализация ключевой логики
const coreLogic = await generate(`
  Реализуй handleFiles для FileUpload:
  - Валидация типа и размера
  - Добавление в state с уникальным id
  - Уведомление через onChange
  ${skeleton}
`);

// Этап 3: UI и UX-детали
const ui = await generate(`
  Реализуй рендер FileUpload:
  - Drop zone с обработчиками drag events
  - Список файлов с прогресс-барами
  - Сообщения об ошибках под каждым файлом
  ${coreLogic}
`);
```

Каждый этап — фокусированная задача с понятным критерием качества. Это прямое применение prompt chaining из предыдущей статьи.

## Code review и объяснение чужого кода

### AI как first-pass рецензент

AI эффективен как первый проход code review — он находит категорию проблем быстро и без усталости. Но его находки — не приговор, а кандидаты на проверку.

```ts
// Промпт для code review с конкретными критериями
const reviewPrompt = `Проанализируй этот код. Для каждой проблемы укажи:
1. Строку или диапазон строк
2. Категорию: bug | performance | security | readability | architecture
3. Уровень: critical | warning | info
4. Описание проблемы
5. Предлагаемое исправление

Не упоминай проблемы, которых нет. Если код корректен — скажи так.

\`\`\`tsx
${code}
\`\`\``;
```

**Что AI находит хорошо:**
- Очевидные баги: обращение к undefined, забытый cleanup в useEffect, missing dependency в массиве зависимостей
- Нарушения идиом: мутация state, прямая модификация props, синхронные операции в async-контексте
- Паттерны безопасности: XSS через dangerouslySetInnerHTML, инъекция через innerHTML, отсутствие валидации

**Что AI находит плохо:**
- Архитектурные проблемы, видимые только в контексте всего проекта
- Нарушение негласных соглашений команды
- Проблемы, требующие знания бизнес-логики
- Тонкие race conditions и concurrency-баги

### Паттерн: review с фокусом

Вместо общего «проверь код» — сузить фокус до конкретной категории:

```ts
// Фокус на производительности
const perfReview = `Проанализируй этот компонент на предмет 
unnecessary re-renders. Укажи:
- Какие пропсы вызывают ре-рендер
- Где не хватает мемоизации (useMemo, useCallback, React.memo)
- Есть ли тяжёлые вычисления в render-функции

\`\`\`tsx
${code}
\`\`\``;

// Фокус на безопасности
const securityReview = `Проанализируй этот код на уязвимости:
- XSS: пользовательский ввод → DOM
- Injection: пользовательский ввод → запросы
- Data leakage: чувствительные данные в логах или URL

\`\`\`tsx
${code}
\`\`\``;
```

Сужение фокуса даёт более глубокий анализ в конкретной области — модель не распыляется на все категории сразу.

### Объяснение чужого кода

Одна из самых сильных сторон AI — объяснение незнакомой кодовой базы. Разработчик, который впервые видит код, тратит часы на понимание. AI даёт первое приближение за секунды.

```ts
const explainPrompt = `Объясни этот код разработчику, который видит его впервые:
1. Что делает этот код в целом (1-2 предложения)
2. Ключевые абстракции и паттерны
3. Поток данных: что входит, что выходит, где трансформируется
4. Неочевидные решения — почему сделано именно так, а не иначе
5. Потенциальные проблемы, которые стоит проверить

\`\`\`tsx
${code}
\`\`\``;
```

Важный нюанс: AI-объяснение — **гипотеза**, а не истина. Модель интерпретирует код на основе паттернов, а не понимания намерений автора. Если код содержит баг, AI может «объяснить» баг как фичу. Всегда проверяйте объяснение against исходным кодом.

### Паттерн: объяснение через вопросы

Вместо пассивного чтения объяснения — активный диалог:

```ts
// Вместо одного большого промпта — серия вопросов
const questions = [
  "Что происходит в useEffect на строке 42?",
  "Почему используется useReducer вместо useState?",
  "Какие условия приводят к re-render этого компонента?",
  "Что произойдёт если props.items будет undefined?",
  "Где в этом коде возможна утечка памяти?",
];

// Каждый вопрос — отдельный вызов с контекстом кода
// Это даёт более глубокие ответы, чем один общий промпт
```

## Рефакторинг под присмотром

### AI как инструмент рефакторинга

AI хорошо справляется с механическими рефакторингами — теми, где правила чёткие, а результат проверяем. Плохо — с семантическими рефакторингами, где нужно сохранить инварианты, невидимые в коде.

**Надёжные рефакторинги:**
- Переименование с изменением структуры (split/merge файлов)
- Конвертация class → hooks, callback → async/await
- Извлечение утилит в отдельные модули
- Приведение к единому стилю (импорты, порядок методов)

**Ненадёжные рефакторинги:**
- Изменение архитектуры state management (Redux → Zustand) — модель не знает всех зависимостей
- Рефакторинг с изменением публичного API — можно сломать потребителей
- Оптимизация производительности без бенчмарков — AI «оптимизирует» по шаблонам, а не по реальным узким местам

### Паттерн: рефакторинг с сохранением поведения

Ключевой принцип — рефакторинг не меняет поведение. AI нужно явно сказать это:

```ts
const refactorPrompt = `Рефакторинг должен сохранить внешнее поведение без изменений.

Задача: конвертируй этот class-компонент в функциональный с хуками.

Требования:
- Сохранить все lifecycle-поведение (mount, update, unmount)
- Сохранить порядок side effects
- Не менять публичные методы, если компонент экспортирует API
- Если есть setState-вызовы в lifecycle — преобразуй в эквивалентные хуки
- Покажи, какие lifecycle-методы каким хукам соответствуют

\`\`\`tsx
${classComponentCode}
\`\`\``;
```

### Паттерн: рефакторинг + тесты

Комбинация рефакторинга с генерацией тестов даёт страховку:

```ts
async function safeRefactor(originalCode: string, task: string) {
  // Шаг 1: сгенерировать тесты на текущее поведение
  const tests = await generate(`
    Напиши тесты, которые фиксируют текущее поведение этого кода.
    Тестируй публичное API, не внутреннюю реализацию.
    
    \`\`\`tsx
    ${originalCode}
    \`\`\`
  `);

  // Шаг 2: выполнить рефакторинг
  const refactored = await generate(`
    ${task}
    
    Исходный код:
    \`\`\`tsx
    ${originalCode}
    \`\`\`
  `);

  // Шаг 3: проверить, что тесты проходят на рефакторенном коде
  // (в реальности — запустить тесты в CI)
  const verification = await generate(`
    Проверь, пройдут ли эти тесты на рефакторенном коде.
    Если нет — укажи, какое поведение изменилось.
    
    Тесты:
    \`\`\`ts
    ${tests}
    \`\`\`
    
    Рефакторенный код:
    \`\`\`tsx
    ${refactored}
    \`\`\`
  `);

  return { refactored, tests, verification };
}
```

Это применение паттерна «генерация + проверка» из предыдущей статьи. Тесты фиксируют поведение, рефакторинг его сохраняет, проверка обнаруживает отклонения.

## Генерация тестов

### Почему генерация тестов — одна из лучших задач для AI

Тесты — задача с идеальной структурой для AI: чёткий формат, конкретный вход, проверяемый выход. Модель генерирует тесты быстро и качественно — при условии правильного промпта.

### Паттерн: тесты по спецификации, а не по коду

Распространённая ошибка — просить «напиши тесты для этого кода». Модель генерирует тесты, которые проверяют **реализацию**, а не **поведение**. Если в реализации баг — тест будет проверять баг.

```ts
// Плохо: тесты по реализации — тестируют то, что код делает
const badPrompt = `Напиши тесты для этой функции:
\`\`\`ts
${implementation}
\`\`\``;

// Хорошо: тесты по спецификации — тестируют то, что код должен делать
const goodPrompt = `Напиши тесты для функции formatDate по спецификации:
- Принимает Date объект и формат-строку (DD.MM.YYYY, YYYY-MM-DD, relative)
- Формат "relative": "только что" (< 1 мин), "N мин назад" (< 1 ч),
  "N ч назад" (< 24 ч), "вчера", "DD.MM.YYYY" (старше 24 ч)
- Часовой пояс: UTC
- Невалидный ввод: возвращает "—"

Не смотри на реализацию — тестируй только спецификацию.`;
```

### Паттерн: граничные случаи

AI хорошо генерирует граничные случаи, если явно попросить:

```ts
const edgeCasesPrompt = `Для функции ${functionName} сгенерируй тест-кейсы 
для следующих категорий:

1. Нормальные входные данные (happy path)
2. Пустые значения: null, undefined, "", [], 0
3. Граничные значения: максимум, минимум, пограничные условия
4. Невалидный ввод: неправильные типы, malformed данные
5. Большие данные: массивы из 1000+ элементов, длинные строки
6. Race conditions: параллельные вызовы, отмена запросов
7. Side effects: мутации входных данных, глобальное состояние

Для каждого кейса: описание, входные данные, ожидаемый результат.`;
```

### Паттерн: тесты + мутации

Продвинутый подход — попросить AI сгенерировать мутации (намеренные баги) и проверить, что тесты их обнаруживают:

```ts
const mutationTesting = `1. Напиши тесты для функции calculateTotal по спецификации:
   ${spec}

2. Предложи 5 мутаций в реализации, которые должны ломать тесты:
   - Изменение оператора (+ на -)
   - Пропуск проверки на null
   - Неправильное условие (< вместо <=)
   - Потеря edge case
   - Неправильный порядок операций

3. Для каждой мутации укажи, какой тест её обнаружит.`;
```

Это даёт двойную проверку: тесты не просто «покрывают код», а действительно валидируют поведение.

### Что AI генерирует плохо в тестах

- **Интеграционные тесты со сложным окружением**: моки баз данных, внешних API, очередей — AI не знает вашей инфраструктуры
- **Тесты на concurrency**: race conditions, deadlock — модель рассуждает о коде линейно
- **E2E-тесты со специфичными selectors**: AI не видит реальный DOM

## Документация и changelogs

### Генерация документации

AI эффективен для генерации документации по коду — JSDoc, README, migration guides. Ключевой паттерн: указать целевую аудиторию и уровень детализации.

```ts
// Для JSDoc — краткий промпт
const jsdocPrompt = `Добавь JSDoc к каждой экспортируемой функции.
Для каждого параметра: тип, описание, обязательный/опциональный.
Для функции: что делает, что возвращает, какие ошибки бросает.
Не описывай очевидное — фокусируйся на неочевидном поведении.

\`\`\`ts
${code}
\`\`\``;

// Для README — с контекстом аудитории
const readmePrompt = `Напиши раздел README для этого модуля.
Аудитория: разработчики, которые будут использовать этот модуль, 
но не видели его код.
Включи: назначение, основной API, пример использования, 
ограничения и известные edge cases.

\`\`\`ts
${code}
\`\`\``;
```

### Генерация changelogs

AI хорошо суммаризирует набор коммитов в changelog — но требует явного формата:

```ts
const changelogPrompt = `Сгенерируй changelog из этих коммитов.

Формат:
## [Версия] — YYYY-MM-DD
### Breaking Changes
### New Features
### Bug Fixes
### Internal

Правила:
- Объединяй связанные коммиты в один пункт
- Пиши с точки зрения пользователя, не разработчика
- Для breaking changes: что было → что стало → миграция
- Не включай: рефакторинг без изменения поведения, форматирование, CI

Коммиты:
${commits}`;
```

### Ограничения AI-документации

AI генерирует документацию, которая **описывает код**, а не **объясняет решения**. Документация «почему» — почему этот API, почему этот подход, почему эти ограничения — остаётся за разработчиком.

```ts
// AI сгенерирует: "Функция formatDate принимает Date и формат-строку"
// Разработчик должен добавить: "Формат-строка — не strftime, 
// а собственный мини-язык, потому что strftime не поддерживает 
// relative-формат, а нам нужен именно он для UI"
```

## Вайбкодинг vs управляемая генерация

### Что такое вайбкодинг

Вайбкодинг (vibe coding) — термин, описывающий стиль работы, при котором разработчик описывает задачу AI на естественном языке и принимает сгенерированный код без глубокого понимания. Название отражает подход: «ловишь вайб», а не контролируешь результат.

```
Вайбкодинг:
  Разработчик → "Сделай дашборд с графиками" → AI → [код] → Деплой
  
Управляемая генерация:
  Разработчик → спецификация → AI → [код] → review → тесты → интеграция
```

### Когда вайбкодинг работает

Вайбкодинг приемлем в трёх ситуациях:

1. **Прототипы и spike**: быстро проверить идею, которую, возможно, выбросите. Здесь не нужна точность — нужна скорость.
2. **Личные проекты**: если вы единственный пользователь и готовы чинить баги сами.
3. **Обучение**: экспериментировать с новыми технологиями, seeing как AI реализует паттерны.

### Когда вайбкодинг опасен

В продакшн-коде вайбкодинг создаёт системные риски:

```ts
// Вайбкодинг сгенерирует что-то вроде:
const Dashboard = () => {
  const [data, setData] = useState([]);
  
  useEffect(() => {
    fetch('/api/dashboard')
      .then(r => r.json())
      .then(setData);
  }, []); // Нет обработки ошибок
  // Нет loading-состояния
  // Нет cleanup (отмена запроса при unmount)
  // Нет retry-логики
  // Нет обработки невалидного ответа
  
  return <Charts data={data} />; // data может быть [] — Charts это учитывает?
};
```

Каждая из этих проблем — не «баг», а архитектурное решение. AI не знает, какие решения приняты в вашем проекте. Разработчик — знает.

### Управляемая генерация: процесс

```ts
// 1. Спецификация ДО генерации
const spec = `
  Dashboard component:
  - Загрузка данных: GET /api/dashboard
  - Loading: скелетон, не спиннер
  - Error: retry-кнопка + сообщение
  - Empty state: "Нет данных" с иллюстрацией
  - Abort запроса при unmount
  - Refetch каждые 30 секунд с visibility check
  - TypeScript strict mode
`;

// 2. Генерация с ограничениями
const code = await generate(spec);

// 3. Проверка against спецификации
const check = await verify(code, spec);

// 4. Тесты по спецификации (не по коду)
const tests = await generateTests(spec);

// 5. Ручной review: архитектурные решения, интеграция, edge cases
```

### Глубокое знание фронтенда как множитель эффективности

Парадокс: чем лучше вы знаете фронтенд, тем эффективнее работаете с AI. Причина не в том, что вы «лучше пишете промпты» — хотя и это тоже — а в том, что вы:

1. **Знаете, что спрашивать**. Вы формулируете спецификацию точно, потому что знаете, какие решения нужно принять.
2. **Видите проблемы в сгенерированном коде**. Вы замечаете missing cleanup, неправильный паттерн, неоптимальный рендер — потому что знаете, как должно быть.
3. **Принимаете архитектурные решения**. AI генерирует код. Вы решаете, какой код нужен в контексте проекта.

```ts
// Junior-разработчик принимает сгенерированный код как есть
// Senior-разработчик видит:
// - useEffect без cleanup → утечка памяти при unmount
// - Нет AbortController → запрос продолжается после навигации
// - setInterval без visibility check → лишние запросы в неактивной вкладке
// - Нет error boundary → весь компонент падает при ошибке одного графика
```

AI — усилитель компетенции. Если компетенция высокая — усиливает продуктивность. Если низкая — усиливает количество багов.

## Ключевые тезисы для интервью

- AI наиболее эффективен для задач с чёткой спецификацией и устоявшимися паттернами: boilerplate, утилиты, конвертация форматов.
- AI ненадёжен в бизнес-логике с неочевидными правилами, архитектурных решениях с трейдоффами и performance-критичных путях.
- Качество генерации пропорционально точности спецификации: конкретные критерии дают рабочий код, абстрактные запросы — код с допущениями.
- AI как first-pass code review находит очевидные баги, нарушения идиом и паттерны безопасности, но пропускает архитектурные проблемы и доменно-специфичные ошибки.
- AI-объяснение чужого кода — гипотеза, а не истина: модель интерпретирует паттерны, а не намерения автора; баг может быть «объяснён» как фича.
- Рефакторинг с AI требует явного указания сохранить поведение; комбинация рефакторинга с генерацией тестов даёт страховку от изменения семантики.
- Тесты нужно генерировать по спецификации, а не по реализации — иначе тесты будут проверять баги вместе с фичами.
- Вайбкодинг допустим для прототипов и обучения, но опасен в продакшне: AI не принимает архитектурных решений, которые знает только разработчик.
- Глубокое знание фронтенда — множитель эффективности AI: вы знаете что спрашивать, видите проблемы в сгенерированном коде и принимаете архитектурные решения.

## Заключение

AI в рабочем процессе — инструмент с чёткой зоной эффективности и чёткой зоной риска:

- **Генерация кода** работает для типовых задач и ломается на бизнес-логике. Спецификация — ключ к качеству.
- **Code review** с AI — первый проход, а не замена рецензента. Фокусированные промпты дают более глубокий анализ.
- **Рефакторинг** требует явного сохранения поведения и тестов как страховки.
- **Тесты** нужно генерировать по спецификации — иначе они закрепляют баги реализации.
- **Документация** описывает «что», но не «почему» — решения остаются за разработчиком.
- **Вайбкодинг** — инструмент прототипирования, а не продакшн-разработки.

AI усиливает существующую компетенцию, а не создаёт новую. Чем глубже вы знаете предметную область, тем больше пользы извлекаете из каждого вызова. Следующая статья — агентные паттерны — показывает, как эти принципы масштабируются от одиночных вызовов до автономных систем.
