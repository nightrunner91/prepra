# AI-агенты в работе фронтендера

Это статья о вашем реальном рабочем цикле. Вы не пишете код руками — вы пишете спецификацию человеческим языком, отправляете её в контекстное окно агенту (Claude Code, OpenCode, Codex) и проверяете результат. Эффективность этого цикла зависит не от знания протоколов LLM, а от трёх вещей: качества спецификации, правил, которые вы задаёте агенту заранее, и дисциплины проверки результата. Разберём каждую.

## Цикл: спецификация → генерация → проверка

Работа через агентов — это не «отдать задачу и получить код». Это цикл, где вы играете роль архитектора и ревьюера, а агент — исполнителя:

```
1. Спецификация  →  что делать, как должно выглядеть, критерии качества
2. Генерация     →  агент пишет код по спецификации
3. Проверка      →  вы проверяете результат против спецификации
4. Итерация      →  несоответствия возвращаются агенту с уточнением
```

### Спецификация — это продукт разработчика

Качество кода агента напрямую определяется качеством спецификации. Абстрактная задача даёт код с допущениями; конкретная — рабочий результат.

```text
// Плохо: абстрактно
Сделай компонент загрузки файлов

// Хорошо: конкретно
Создай React-компонент FileUpload:
- Drag & drop зона с подсветкой при hover
- Поддержка множественной загрузки, максимум 5 файлов
- Валидация: только image/* и application/pdf, макс 10MB каждый
- Прогресс-бар для каждого файла во время загрузки
- Обработка ошибок: сообщение под файлом, возможность повторить
- API: POST /api/upload, FormData
- TypeScript, без библиотек для drag&drop
- Компонент контролируемый: value и onChange
```

Разница радикальная: первый вариант даст «общий» компонент с десятком допущений, второй — код, который можно использовать.

### Спецификация — это и критерии приёмки

В спецификацию включайте не только что делать, но и как проверить, что сделано правильно. Это позволяет передавать результат обратно агенту с точными замечаниями, а не с ощущением «что-то не то».

## AGENTS.md: правила для агента

AGENTS.md (или CLAUDE.md) — файл с постоянными инструкциями для агента в репозитории. Это аналог system prompt: правила, которые действуют для каждой задачи, а не только для текущей.

### Что туда класть

- **Стек и команды**: фреймворк, менеджер пакетов, как запускать тесты и линтер
- **Соглашения**: стиль кода, паттерны, структура каталогов
- **Запреты**: что агент не должен делать без спроса (менять конфиги, ставить зависимости)
- **Стандарты качества**: обязательные проверки перед завершением задачи

```text
# Проект: <имя>

## Стек
- React 18 + TypeScript, Next.js 14 (App Router)
- Менеджер пакетов: pnpm
- Тесты: Vitest, команда `pnpm test`
- Линтер: ESLint + Prettier, команда `pnpm lint`

## Соглашения
- Компоненты — в src/components, стили — CSS Modules
- Типы для API-ответов — в src/types, не дублировать в компонентах
- Все запросы к API — через клиент из src/lib/api.ts

## Запреты
- Не менять конфиги (next.config, tsconfig, eslint) без явного запроса
- Не добавлять зависимости без явного запроса
- Не деплоить и не запускать миграции

## Стандарты качества
- Перед завершением задачи: прогони `pnpm lint` и `pnpm test`
- Не оставлять console.log и TODO в коде
- Каждое публичное API — с JSDoc
```

Эффект: агент не гадает о ваших правилах каждый раз. Один файл заменяет повторение одних и тех же инструкций в каждой задаче.

## Как формулировать задачу

Паттерны промптинга из предыдущей статьи здесь работают напрямую. Основные правила для задач агенту:

### Одна задача — одно сообщение

```text
// Плохо: пять задач в одном запросе
Исправь баг с фильтрацией, добавь сортировку,
перепиши на TS, добавь тесты и обнови README

// Хорошо: фокус на одной задаче
Исправь баг: при фильтрации таблицы показываются удалённые записи.
Критерий: поле isDeleted === false должно отфильтровываться сервером.
```

### Контекст, который агенту неоткуда узнать

Агент не видит ваш проект целиком и не знает внутренних решений. Всё неочевидное — в задачу.

```text
// Плохо: скрытые требования
Сделай скидку в корзине

// Хорошо: явные правила домена
Сделай расчёт скидки в корзине:
- Промокоды НЕ суммируются с корпоративными скидками
- Для подписчиков — отдельный расчёт с округлением вниз
- Применяется только к товарам с ценой > 1000₽
- Максимум одна скидка на позицию
```

### «Рассуждай, потом действуй» для сложных задач

Для анализа и отладки включайте chain-of-thought: «проанализируй, затем реши» даёт лучший результат, чем «реши сразу».

## Управляемая генерация vs вайбкодинг

Вайбкодинг — стиль, при котором разработчик описывает задачу и принимает сгенерированный код без глубокого понимания и контроля. Он опасен в продакшне не из-за отдельных багов, а из-за архитектурных решений, которые AI принимает вместо вас.

```text
Вайбкодинг:
  Разработчик → "Сделай дашборд с графиками" → AI → [код] → Деплой

Управляемая генерация:
  Разработчик → спецификация → AI → [код] → проверка → тесты → интеграция
```

```tsx
// Что сгенерирует агент без спецификации:
const Dashboard = () => {
  const [data, setData] = useState([]);

  useEffect(() => {
    fetch('/api/dashboard')
      .then(r => r.json())
      .then(setData);
  }, []); // Нет обработки ошибок
  // Нет loading-состояния
  // Нет cleanup (отмена запроса при unmount)
  // Нет обработки невалидного ответа

  return <Charts data={data} />; // data может быть [] — Charts это учитывает?
};
```

Каждая из проблем — не «баг», а архитектурное решение. AI не знает, какие решения приняты в вашем проекте. Вы — знаете. **Это и есть причина, по которой спецификация и проверка незаменимы.**

Вайбкодинг приемлем для прототипов, спиков и личных проектов — там, где точность не критична. Для продакшена — нет.

## Проверка результата агента

### Критерии проверки

Проверка — не «пробежать глазами», а сверка против спецификации:

1. **Функциональность** — реализовано ли всё из спецификации?
2. **Крайние случаи** — что при пустых данных, ошибке, медленной сети, unmount?
3. **Соглашения** — соответствует ли код стилю и паттернам проекта?
4. **Качество** — тесты? линтер? типы?

### Паттерн «генерация + проверка»

Не принимайте результат агента на веру. Попросите агента проверить собственную работу вторым вызовом с независимым фокусом:

```text
Шаг 1: Реализуй компонент по спецификации: <спецификация>
Шаг 2: Проверь, соответствует ли этот код спецификации.
Спецификация: <спецификация>
Код: <код>
Укажи все несоответствия. Если соответствует — скажи "ok".
```

Это ловит то, что первый проход пропустил: агент, генерируя код, «влюблён» в свой результат; второй вызов смотрит критически.

### Тесты по спецификации, а не по коду

Просить «напиши тесты для этого кода» — ошибка: агент закрепит реализацию вместе с её багами. Правильно — тесты по спецификации:

```text
// Плохо: тесты по реализации
Напиши тесты для функции formatDate: <код>

// Хорошо: тесты по спецификации
Напиши тесты для formatDate по спецификации:
- Принимает Date и формат-строку (DD.MM.YYYY, YYYY-MM-DD, relative)
- Формат "relative": "только что" (<1 мин), "N мин назад" (<1 ч),
  "N ч назад" (<24 ч), "вчера", "DD.MM.YYYY" (старше 24 ч)
- Часовой пояс: UTC
- Невалидный ввод: возвращает "—"
Не смотри на реализацию — тестируй только спецификацию.
```

## Когда агент врёт и как это ловить

Агент не врёт намеренно — он генерирует правдоподобный текст. Опасность в том, что **уверенность не коррелирует с точностью**.

### Типичные сценарии

1. **Галлюцинированный API** — агент использует метод библиотеки, которого нет в вашей версии, или API, который никогда не существовал. Происходит потому, что модель «знает» много версий, но не знает вашу.

2. **«Уверенно неверно»** — код выглядит корректным, но не компилируется, не проходит тесты или нарушает типы. Агент не запускает код, пока вы его не попросите.

3. **Пропущенные граничные случаи** — агент решает happy path и не видит edge cases вашего домена.

4. **Повторение ошибки по инерции** — в legacy-коде уже есть баг; агент «изучает» его как паттерн и воспроизводит в новом коде.

### Как ловить

- **Запускайте тесты и линтер** — требуйте от агента прогон проверок перед завершением (запишите это в AGENTS.md)
- **Не доверяйте объяснениям агента** — «я сделал всё по спецификации» не заменяет запуск кода
- **Проверяйте против версий** — если агент использует API библиотеки, сверяйте с версией в package.json
- **Тесты по спецификации** — они ловят регрессии, когда агент «закрепляет» баг

## Ключевые тезисы для интервью

- Работа с агентами — цикл «спецификация → генерация → проверка»; спецификация — продукт разработчика, качество кода агента определяется её качеством.
- AGENTS.md (CLAUDE.md) — постоянные инструкции для агента: стек, команды, соглашения, запреты, стандарты качества; аналог system prompt для репозитория.
- Абстрактная задача даёт код с допущениями; конкретная спецификация с критериями приёмки — рабочий результат.
- Вайбкодинг опасен в продакшне не из-за багов, а из-за архитектурных решений, которые AI принимает вместо вас.
- Проверка результата — сверка против спецификации: функциональность, крайние случаи, соглашения, качество (тесты/линтер/типы).
- Паттерн «генерация + проверка» — второй вызов с независимым фокусом ловит то, что первый проход пропустил.
- Тесты генерируются по спецификации, а не по коду — иначе агент закрепит баги реализации.
- Агент может быть уверенно неверным: галлюцинированный API, нерабочий код, пропущенные edge cases; проверка — запуск тестов, сверка с версиями, недоверие объяснениям.

## Заключение

AI-агент — усилитель компетенции, а не замена ей. Ваш вклад в цикл — спецификация (что и зачем делать), правила (AGENTS.md) и проверка (дисциплина сверки с критериями). Агент вносит скорость генерации; вы — точность направления и качество результата.

Чем глубже вы знаете фронтенд, тем эффективнее работаете с агентами: вы знаете, что требовать, видите проблемы в сгенерированном коде и принимаете архитектурные решения. Если компетенция высокая — агент усиливает продуктивность. Если низкая — усиливает количество багов.
