# Ментальная модель LLM

Прежде чем применять AI в разработке, нужно понять, как он устроен изнутри. ## Что такое токен и почему это важно разработчику

### Токены — не слова и не символы

Разработчики часто представляют LLM как что-то, что «читает слова». На самом деле модели работают с **токенами** — подсловными единицами, которые получаются в результате алгоритма токенизации (чаще всего BPE, Byte Pair Encoding).

Токен — это не символ и не слово. Это фрагмент текста, который встречался достаточно часто в обучающем корпусе, чтобы получить собственный идентификатор в словаре. Распространённые слова — один токен. Редкие слова и слова из нескольких морфем — несколько токенов.

```ts
// Примерная токенизация для английского текста
"Hello"         → ["Hello"]                    // 1 токен
"hello"         → ["hello"]                    // 1 токен (регистр важен)
"unprecedented" → ["un", "prece", "dented"]    // 3 токена
"ChatGPT"       → ["Chat", "G", "PT"]          // 3 токена

// Типичные соотношения: 1 токен ≈ 4 символа или ¾ слова в английском
// В русском: 1 токен ≈ 2-3 символа (морфемы длиннее, меньше токенов на слово)
```

### Как токенизация влияет на стоимость

Стоимость запроса к LLM API считается в токенах: входные (prompt) токены + выходные (completion) токены. Выходные обычно дороже — модель должна генерировать каждый последовательно.

```ts
// Типичная структура стоимости (условные числа)
const pricing = {
  inputTokensPer1M: 3.00,   // $3 за миллион входных токенов
  outputTokensPer1M: 15.00, // $5 за миллион выходных токенов — в 5x дороже
};

// Практический расчёт
function estimateCost(promptText: string, responseText: string) {
  const inputTokens = promptText.length / 4;   // грубая оценка
  const outputTokens = responseText.length / 4;
  return (inputTokens / 1_000_000 * pricing.inputTokensPer1M) +
         (outputTokens / 1_000_000 * pricing.outputTokensPer1M);
}
```

Это означает: **длинный системный промпт при каждом запросе — реальные деньги**. Если вы отправляете 5000 токенов системного промпта с каждым из 100 000 запросов в день, это 500 миллионов входных токенов ежедневно.

### Токены и языки

Токенизация исторически оптимизировалась под английский текст. Для других языков соотношение символов на токен хуже:

| Язык | Символов на токен | Токенов на то же содержание |
|------|-------------------|-----------------------------|
| Английский | ~4 | 1× |
| Русский | ~2-3 | ~1.5× |
| Японский | ~1.5 | ~2× |
| Арабский | ~2 | ~1.5× |

На практике это значит: промпт, написанный на русском, обойдётся дороже того же промпта на английском при прочих равных. Не радикально, но заметно в масштабе.

### Токены и код

Код токенизируется иначе, чем проза. Синтаксические символы (`{`, `}`, `=>`, `?.`) часто становятся отдельными токенами. TypeScript-аннотации типов — дополнительные токены поверх JS. Пространство имён с длинными идентификаторами (`SomeVeryLongComponentName`) бьётся на несколько токенов.

```ts
// Этот код ~25 токенов
const x = 1;

// Этот код ~60 токенов (та же логика, но с типами и длинными именами)
const userAuthenticationToken: AuthenticationTokenResponse = getUserToken();
```

Это влияет на лимиты в code-generation задачах и на то, сколько кода влезает в контекстное окно при анализе.

## Контекстное окно: что в него попадает и в каком порядке

### Контекст — это весь разговор за один раз

LLM — **stateless**. Модель не помнит предыдущих запросов. Каждый API-вызов — это отдельный, независимый запрос, в котором передаётся **всё**, что модель должна знать: системный промпт, история диалога, текущее сообщение пользователя.

```ts
// Вот что реально отправляется в API при "продолжении разговора"
const request = {
  model: "claude-sonnet-4-6",
  messages: [
    // Это НЕ первое сообщение — это весь контекст целиком
    { role: "user",      content: "Привет! Как дела?" },
    { role: "assistant", content: "Хорошо, спасибо! Чем могу помочь?" },
    { role: "user",      content: "Расскажи про токены" },
    { role: "assistant", content: "Токены — это..." },
    { role: "user",      content: "А что такое контекстное окно?" }, // текущее
  ],
  system: "Ты — помощник-разработчик...", // системный промпт
};
```

Никакой «памяти» нет. Приложение само хранит историю и вставляет её в каждый запрос. Когда история вырастает за пределы контекстного окна — нужно принимать архитектурное решение: обрезать, сжать или использовать RAG.

### Структура контекста

Контекстное окно — это последовательность токенов с фиксированной позицией. Типичная структура запроса к современной модели:

```
[system prompt] → [user message 1] → [assistant message 1] → ... → [current user message]
```

Всё это вместе называется **контекстом**. Размер контекстного окна — максимальное количество токенов, которое модель может принять + сгенерировать за один запрос.

```
Размер контекстного окна = input tokens + output tokens
```

Если вы хотите получить ответ длиной 4096 токенов, и ваше окно 16 384 токена — у вас останется 12 288 токенов под промпт и историю.

### Почему начало и конец важнее середины

Исследования показывают феномен, который называют **«lost in the middle»**: модели хуже обрабатывают информацию, расположенную в середине длинного контекста, по сравнению с началом и концом.

```
[ начало — высокое внимание ]
[ середина — сниженное внимание ]   ← "lost in the middle"
[ конец — высокое внимание ]
```

На практике это означает:
- **Системный промпт** (начало) — хорошее место для критических инструкций и ограничений
- **Текущее сообщение** (конец) — хорошее место для конкретного задания
- **Середина** (история диалога, документы) — модель прочитает, но может не акцентировать внимание

```ts
// Менее оптимально: критические инструкции в середине истории
const messages = [
  { role: "user", content: "Начнём работу..." },
  { role: "assistant", content: "..." },
  // ... 50 сообщений истории ...
  { role: "user", content: "ВАЖНО: никогда не используй deprecated API" }, // потеряется
  { role: "assistant", content: "..." },
  { role: "user", content: "Напиши функцию для..." },
];

// Лучше: критическое ограничение в system prompt
const system = `Ты — ассистент по коду. 
НИКОГДА не используй deprecated API (componentWillMount, findDOMNode и т.д.).`;
```

### Контекстное окно и архитектурные решения

Размер контекстного окна напрямую влияет на архитектуру LLM-приложения:

| Сценарий | Небольшое окно (4K–16K) | Большое окно (128K–1M) |
|----------|------------------------|------------------------|
| Длинный документ | Нужен RAG или разбиение | Можно вставить целиком |
| История чата | Нужна стратегия сжатия | Дольше помещается как есть |
| Кодовая база | Нужна выборка файлов | Можно вставить больше файлов |
| Стоимость | Дешевле за запрос | Дороже при заполнении |

Большое контекстное окно — не «бесплатный» ответ на все вопросы. Стоимость растёт линейно с размером контекста, а модели с очень большими окнами часто медленнее.

## Температура, top-p и детерминизм

### Как модель выбирает следующий токен

LLM генерирует текст последовательно, токен за токеном. На каждом шаге модель вычисляет распределение вероятностей по всему словарю (~100 000 токенов) и выбирает следующий токен из этого распределения.

```
P("кот") = 0.35
P("пёс") = 0.28
P("хомяк") = 0.15
P("ёж") = 0.08
... (99 996 других токенов)
```

Вопрос — **как именно выбрать** из этого распределения. Здесь работают параметры температура и top-p.

### Температура: управление случайностью

Температура масштабирует логиты (числа перед softmax) перед вычислением вероятностей:

- **temperature = 0**: жадный выбор — всегда берём самый вероятный токен
- **temperature = 1**: выборка из исходного распределения
- **temperature > 1**: распределение становится более равномерным, низковероятные токены получают больше шансов

```ts
// Практические значения температуры
const useCases = {
  // Для задач с единственным правильным ответом
  codeGeneration: { temperature: 0 },
  jsonExtraction: { temperature: 0 },
  factRetrieval: { temperature: 0 },

  // Для задач, где нужна вариативность
  brainstorming: { temperature: 0.8 },
  creativeWriting: { temperature: 1.0 },
  diverseSuggestions: { temperature: 0.7 },
};
```

### top-p (nucleus sampling)

top-p работает иначе: вместо масштабирования вероятностей, мы отбрасываем все токены кроме тех, что в сумме дают p% вероятности.

При top-p = 0.9: выбираем минимальный набор токенов с суммарной вероятностью ≥ 90%, остальные отбрасываем, затем сэмплируем из этого ядра.

```ts
// Как top-p сужает выборку
const distribution = [
  { token: "кот",   prob: 0.35 },  // суммарно 0.35
  { token: "пёс",   prob: 0.28 },  // суммарно 0.63
  { token: "хомяк", prob: 0.15 },  // суммарно 0.78
  { token: "ёж",    prob: 0.08 },  // суммарно 0.86
  { token: "мышь",  prob: 0.06 },  // суммарно 0.92 ← top-p=0.9 отсечёт здесь
  // остальные токены отброшены
];
```

На практике: temperature и top-p используются вместе. Рекомендуемый подход — менять один параметр, оставляя другой по умолчанию (temperature=1, top-p=1).

### Почему температура 0 не гарантирует детерминизм

Распространённое заблуждение: temperature=0 означает одинаковый ответ всегда. На практике это не так:

1. **Параллельная обработка**: современные GPU выполняют операции с плавающей точкой параллельно; порядок суммирования влияет на результат из-за ограниченной точности float
2. **Разное железо**: разные версии GPU и CUDA дают разные результаты при одинаковых вычислениях
3. **Модельные обновления**: провайдеры периодически обновляют модели

```ts
// Не полагайтесь на полный детерминизм даже при temperature=0
const result1 = await model.complete({ prompt, temperature: 0 });
const result2 = await model.complete({ prompt, temperature: 0 });

// result1 и result2 будут ОЧЕНЬ похожи, но могут отличаться
// в мелких деталях — порядке слов, пунктуации, деталях форматирования
```

Если вам нужна воспроизводимость — используйте seed-параметр (если API поддерживает), логируйте фактические ответы и тестируйте на golden dataset, а не на точном совпадении строк.

## Latency: TTFT vs полное время ответа

### Два измерения задержки

Latency LLM-запроса складывается из двух компонент, которые принципиально по-разному влияют на UX:

**TTFT (Time to First Token)** — время от отправки запроса до получения первого токена ответа. Это время, когда пользователь видит «пустой экран» или спиннер.

**Total Latency** — полное время до получения последнего токена. При стриминге пользователь уже читает ответ пока он генерируется.

```
Запрос ─────────────────────────────────────────────────► Время
        │         │                                    │
      отправка  первый токен                    последний токен
        │         │                                    │
        └──TTFT──►│◄────── время генерации ───────────►│
        └─────────────── total latency ────────────────►│
```

### Что влияет на TTFT

TTFT определяется:
- **Размером входного контекста**: модели с prefill-фазой тратят время на обработку входных токенов — длиннее промпт, дольше TTFT
- **Загруженностью сервера**: время в очереди
- **Географией**: сетевая задержка до дата-центра провайдера
- **Размером модели**: большие модели медленнее начинают

```ts
// Оптимизация TTFT: более короткие системные промпты
// Плохо: 2000 токенов системного промпта ради одного запроса
const systemPrompt = `Ты — опытный разработчик TypeScript с 15-летним стажем.
Ты знаешь все паттерны, лучшие практики, историю языка...
[1500 токенов подробного описания]`;

// Лучше: краткий промпт, детали — в user message если нужны
const systemPrompt = `Ты — ассистент по TypeScript. Пиши точно и кратко.`;
```

### Что влияет на полное время

Total latency = TTFT + (количество выходных токенов × время на токен). Время на токен определяется размером модели и аппаратными ресурсами провайдера.

Из этого следствие: **длина ответа — основной рычаг влияния на полное время**. Инструкция «отвечай кратко» — не только про удобство чтения, но и про latency.

```ts
// Параметр max_tokens ограничивает максимальную длину ответа
const response = await client.messages.create({
  model: "claude-sonnet-4-6",
  max_tokens: 256, // ограничиваем выход для задач, где нужна скорость
  messages: [{ role: "user", content: "Объясни в 2 предложениях что такое closure" }],
});
```

### Streaming как UX-решение

Стриминг не ускоряет генерацию — TTFT и total latency те же. Но **воспринимаемое время** резко снижается: пользователь начинает читать сразу после TTFT.

```ts
// Без стриминга: пользователь ждёт 5-10 секунд, потом видит весь ответ
const response = await client.messages.create({ ... });
displayResponse(response.content);

// Со стримингом: пользователь читает с первых 200-500мс
const stream = client.messages.stream({ ... });
for await (const chunk of stream) {
  appendToUI(chunk.delta.text); // обновляем UI каждые ~20мс
}
```

Для большинства пользовательских интерфейсов стриминг — не оптимизация, а обязательное требование к UX.

## Батчинг запросов

### Проблема: N одиночных запросов

Типичный сценарий: нужно классифицировать 500 тикетов поддержки, проанализировать 200 резюме или сгенерировать описания для 1000 товаров. Последовательные запросы медленно, параллельные — ограничены rate limits провайдера.

```ts
// Плохо: последовательно — 500 × 2с = ~16 минут
for (const ticket of tickets) {
  const result = await classify(ticket);
  results.push(result);
}

// Лучше, но упирается в rate limits
const results = await Promise.all(tickets.map(classify));

// Правильно: ограниченный параллелизм
async function processWithConcurrency<T>(
  items: T[],
  handler: (item: T) => Promise<unknown>,
  concurrency = 10,
) {
  const chunks = chunk(items, concurrency);
  const results = [];
  for (const batch of chunks) {
    results.push(...await Promise.all(batch.map(handler)));
  }
  return results;
}
```

### Batch API: асинхронная обработка

Многие провайдеры предоставляют Batch API — механизм передачи большого числа запросов одним вызовом с асинхронным получением результатов. Преимущества:

- **Сниженная стоимость**: обычно 50% скидка от обычного API
- **Высокий throughput**: обходит per-minute rate limits
- **Фоновая обработка**: не блокирует пользователя

```ts
// Пример работы с Batch API (Anthropic)
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

// Создаём батч
const batch = await client.beta.messages.batches.create({
  requests: tickets.map((ticket, i) => ({
    custom_id: `ticket-${i}`,
    params: {
      model: "claude-haiku-4-5-20251001",
      max_tokens: 64,
      messages: [{ role: "user", content: `Classify: ${ticket.text}` }],
    },
  })),
});

// Позже (минуты-часы) забираем результаты
const results = await client.beta.messages.batches.results(batch.id);
for await (const result of results) {
  if (result.result.type === "succeeded") {
    processResult(result.custom_id, result.result.message);
  }
}
```

### Когда батчинг не подходит

Batch API — инструмент для фоновой обработки. Он неприменим там, где нужен синхронный ответ:

| Сценарий | Batch API | Обычный API |
|----------|-----------|-------------|
| Чат-интерфейс | ✗ | ✓ |
| Ночной прогон аналитики | ✓ | ✗ |
| Генерация email в реальном времени | ✗ | ✓ |
| Массовая классификация данных | ✓ | ✗ |
| Ответ на действие пользователя | ✗ | ✓ |

## Ключевые тезисы для интервью

- Токен — базовая единица обработки LLM: не слово и не символ, а подсловный фрагмент текста; стоимость и лимиты API считаются в токенах.
- Выходные токены дороже входных (обычно в 3–5×), поэтому длина ответа влияет на стоимость сильнее, чем длина промпта.
- Токенизация оптимизирована под английский; русский текст занимает ~1.5× больше токенов при том же содержании.
- Модель stateless — нет памяти между запросами; приложение само хранит историю и передаёт её целиком в каждом вызове.
- Феномен «lost in the middle»: модели лучше удерживают внимание к началу и концу контекста — критические инструкции размещать в system prompt или в текущем сообщении.
- Большое контекстное окно не отменяет RAG — стоимость растёт линейно с размером контекста.
- Temperature = 0 даёт почти детерминированный вывод, но не гарантирует абсолютную воспроизводимость из-за параллельных вычислений с плавающей точкой.
- TTFT (Time to First Token) — время до первого токена; зависит от длины входного контекста и загрузки сервера.
- Total latency = TTFT + время генерации; длина ответа — главный рычаг влияния на полное время.
- Стриминг не ускоряет генерацию, но улучшает воспринимаемую скорость — пользователь читает с первых токенов.
- Batch API снижает стоимость ~50% и обходит rate limits, но подходит только для фоновой обработки без синхронного ответа.

## Заключение

Ментальная модель LLM — это не знание математики трансформеров, а понимание нескольких фундаментальных вещей:

- Модель работает с токенами, не со словами. Всё что вы пишете — это деньги и лимиты.
- Каждый запрос к API — это полный снимок состояния: системный промпт + вся история + текущий ввод.
- Результат вероятностный. Температура управляет «разбросом», но детерминизм — иллюзия.
- Задержка — двухкомпонентная. TTFT влияет на ощущение скорости; total latency — на реальное время.
- Батчинг — инструмент для фоновых задач, а не для интерактивного UI.

Это знание позволяет предсказывать поведение модели, выбирать правильные параметры и принимать обоснованные архитектурные решения. Следующая статья — паттерны промптинга — строится именно на этом фундаменте.
