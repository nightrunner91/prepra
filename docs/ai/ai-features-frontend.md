# AI-фичи на фронте: от задачи к реализации

На собеседовании или в реальной работе вам могут дать задачу «сделай чат с ИИ» или «добавь ассистента в продукт». Правильный подход — продуктовый, а не протокольный: определить, что фича должна делать для пользователя, выбрать готовый SDK, спроектировать архитектуру и задать измеримые критерии приёмки. Эта статья — о том, как превратить идею AI-фичи в реализацию без изобретения велосипедов: от продуктовой спецификации до критериев приёмки, с таблицами выбора и разбором, когда фичу можно упростить, а когда без RAG не обойтись.

## Продуктовая спецификация AI-фичи

До выбора технологий определите, что фича делает. Четыре вопроса, на которые нужно ответить до кода:

### 1. Какую задачу решает фича для пользователя?

```text
Плохо: "Сделаем чат с ИИ"
Хорошо: "Пользователь задаёт вопрос по нашим документам и получает
ответ с цитатой-источником, чтобы не искать по 200 страницам вручную"
```

Продуктовое определение — это **проблема пользователя**, а не технология. «Чат с ИИ» — технология, «найти ответ в 200 страницах за секунды» — проблема. Все дальнейшие решения (SDK, архитектура, RAG) зависят от того, как сформулирована проблема.

### 2. Какой тип фичи это?

| Тип | Пример | Где сложность | SDK? |
|-----|--------|---------------|------|
| Чат | Диалог с помощником | UX + серверный route | ✅ Базовый SDK-кейс |
| Ассистент-встраивание | Подсказки в UI, автодополнение форм | Интеграция в существующий UI | ✅/⚠️ |
| Генерация контента | Резюме, описания, заголовки | Один вызов + обработка результата | ⚠️ Можно проще |
| RAG-ассистент | Ответы по базе знаний | Бэкенд: retrieval + эмбеддинги | ✅ чат + бэкенд-сложность |

### 3. Какие состояния и сценарии нужно предусмотреть?

- Загрузка, стриминг, ошибка, пустой ответ
- Прерывание генерации
- Повторная отправка
- Длинные сессии

### 4. Каковы ограничения?

| Ограничение | Вопрос | Влияние |
|-------------|--------|---------|
| Модель | Какая модель достаточна? | Большая не всегда нужна — дешевле и быстрее малая |
| Бюджет | Сколько на токены в месяц? | Влияет на длину промптов и лимиты |
| Latency | Какой TTFT допустим? | Влияет на выбор модели и необходимость стриминга |
| Объём знаний | Сколько контента отвечать по? | Определяет, нужен ли RAG |

Продуктовая спецификация — основа для задания агенту. Отправляйте ему именно её, а не «сделай чат». Подробно про формулирование задач — в статье [AI в рабочем процессе](./ai-dev-workflow.md).

## Выбор SDK

Для чата и AI-фич на фронте не нужно писать интеграцию с LLM API вручную. Стандарт индустрии — **Vercel AI SDK**.

```tsx
// Vercel AI SDK — чат со стримингом из коробки
const { messages, input, handleInput, handleSubmit, isLoading, stop } =
  useChat({ api: "/api/chat" });
```

Что SDK даёт из коробки:

- **Стриминг** — ответ появляется по мере генерации (под капотом: fetch + ReadableStream + парсинг SSE)
- **Состояние** — список сообщений с накопленным текстом
- **Прерывание** — `stop()` (под капотом AbortController)
- **Обработка ошибок** — ошибки помечаются в сообщениях
- **Провайдеры** — OpenAI, Anthropic, Google и др. через единый интерфейс

### SDK vs рукописная интеграция

| Аспект | Vercel AI SDK | Своя реализация |
|--------|---------------|-----------------|
| Стриминг | Из коробки | Писать парсер SSE/потока |
| Прерывание | `stop()` | AbortController вручную |
| Ошибки в потоке | Помечаются в сообщении | Своя логика |
| Провайдеры | Один интерфейс | По SDK на провайдера |
| Время разработки | Дни | Недели |
| Контроль над деталями | Меньше | Полный |

Правило: **если фича — чат или ассистент, берёте AI SDK.** Не потому что SDK «удобный», а потому что парсинг потоков, прерывание и переподключение — решённые задачи, которые незачем решать заново. Своя реализация оправдана только если SDK не поддерживает нужного провайдера или функциональность настолько специфична, что SDK мешает.

## Архитектура: клиент → сервер → LLM API

### Обязательная схема

```
Клиент (React) ──POST /api/chat──► Сервер (Next.js route) ──► LLM API
                                     │
                                     └── API-ключ хранится здесь, НЕ на клиенте
```

Клиент никогда не обращается к LLM API напрямую. Причины:

1. **Безопасность** — API-ключ в клиентском bundle виден всем через DevTools
2. **Контроль** — сервер может логировать, ограничивать, добавлять промпты
3. **Стабильность** — сервер может переключать провайдеров без изменения клиента

### Таблица: что на клиенте, что на сервере

| Задача | Клиент | Сервер |
|--------|--------|--------|
| API-ключ | ❌ Никогда | ✅ Только здесь |
| Промпт/системные инструкции | ⚠️ Отправляет данные | ✅ Собирает и дополняет |
| Логирование, лимиты | — | ✅ |
| Переключение провайдеров | — | ✅ |
| Рендер ответа | ✅ | — |

### Серверный route

```ts
// app/api/chat/route.ts — Next.js App Router
import { streamText } from "ai";
import { anthropic } from "@ai-sdk/anthropic";

export async function POST(req: Request) {
  const { messages } = await req.json();

  const result = streamText({
    model: anthropic("claude-sonnet-4-6"),
    system: "Ты — ассистент. Отвечай кратко, ссылаясь на факты.",
    messages,
  });

  return result.toDataStreamResponse();
}
```

Клиент получает поток через `useChat`, сервер — через `streamText`. Всю техническую работу (SSE, стриминг, обработка ошибок) делают SDK.

## UX-паттерны чата

Обязательный набор UX-паттернов чата со стримингом (индикация генерации, кнопка «Стоп», частичный ответ при ошибке, автоскролл) разобран в статье «Streaming UI». Здесь они не повторяются — но они обязательная часть спецификации, которую вы передаёте агенту или команде. Плюс к ним для диалоговой фичи добавляется **история сессий**: если фича предполагает диалог, нужно хранить и восстанавливать контекст.

### История сессий: отдельный паттерн

| Аспект | Вопрос | Решение |
|--------|--------|---------|
| Хранение | Где живут сессии? | Сервер (БД) для кросс-девайс, localStorage для локальных |
| Восстановление | Как вернуть контекст? | Передать историю в `messages` при инициализации |
| Мультисессия | Можно ли несколько параллельных? | UI: список сессий, переключение |
| Ограничение длины | Как не переполнить окно? | Сжатие/обрезание истории (см. ментальную модель) |

## Критерии приёмки

AI-фича принимается не «когда работает», а когда выполнены измеримые критерии:

### Функциональные
- Первый токен появляется < 1 сек после отправки
- Кнопка «Стоп» прерывает генерацию
- При ошибке в середине потока частичный ответ сохраняется
- Retry переиспользует исходный запрос

### Качество ответов
- Модель следует системному промпту (не выходит за роль)
- Ответы релевантны запросу (проверка на выборке примеров)

### Безопасность и соответствие
- Вывод модели рендерится через санитизацию (не `dangerouslySetInnerHTML` без DOMPurify) — подробно в [Безопасность AI-вывода](./ai-security.md)
- API-ключ только на сервере
- Валидация схемы ввода/вывода

### Инфраструктура
- Обработка rate limits провайдера
- Логирование ошибок и стоимости
- Fallback на случай недоступности модели

### Таблица: критерий → как измерить

| Критерий | Метрика | Как проверить |
|----------|---------|---------------|
| Первый токен | TTFT < 1 сек | Измерить в реальном окружении |
| «Стоп» | Генерация прекращается | Сценарий-тест, замер токенов после клика |
| Ошибка в потоке | Частичный ответ сохранён | Сценарий с оборванным соединением |
| Санитизация | Вывод проходит DOMPurify | Код-ревью + тест с XSS-пейлоадом |
| Rate limits | Обработаны без падения UI | Сценарий с лимитом |

## Когда фичу можно упростить

Не каждая «AI-фича» — чат с RAG и эмбеддингами. Часто достаточно более простого решения:

| Задача | Сложное решение | Простое решение | Когда простое ок |
|--------|-----------------|-----------------|------------------|
| Ответы по документам | RAG: эмбеддинги + retrieval | Вшить ключевые факты в system prompt | Контента мало, он статичен |
| Генерация описаний | Чат с историей | Один вызов + кнопка «Сгенерировать» | Нет диалога |
| Автодополнение | Полный чат-интерфейс | Инлайн-подсказка | Нужен один результат, не беседа |
| Ассистент по API | RAG по документации API | Спецификация в промпт | Документация влезает в окно |

Правило: **начните с самого простого решения, которое решает проблему пользователя.** RAG и мультисессия добавляют сложность — их нужно оправдать объёмом знаний или потребностью в диалоге. Если база знаний влезает в контекстное окно — RAG не нужен.

## Case study: ассистент по базе знаний

Соберём весь процесс на реальной задаче.

**Задача.** Внутренний портал компании, 50 страниц документации. Продукт хочет «поиск по документам обычным текстом, а не по ключевым словам».

**Шаг 1. Продуктовая спецификация.**

```text
Пользователь: сотрудник, который ищет ответ по внутренним правилам.
Задача: задаёт вопрос на естественном языке → получает ответ с цитатой-источником.
Ограничения: 50 страниц, документы меняются раз в неделю.
```

**Шаг 2. Выбор: RAG или промпт?**

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Вшить документы в промпт | Просто, без инфраструктуры | 50 страниц не влезут в окно, обновления раз в неделю = пересборка |
| RAG | Только релевантные фрагменты в контекст | Эмбеддинги, индексация, pipeline |

**Решение:** RAG. Объём знаний превышает окно, документы меняются — retrieval по фрагментам единственный жизнеспособный путь.

**Шаг 3. Архитектура.**

```
Клиент (чат) → POST /api/chat → Сервер: retrieval (поиск фрагментов) → LLM API
                                     │
                                     └── эмбеддинги + индекс документов
```

Фронтенд — тот же чат через `useChat`. Вся сложность (эмбеддинги, индексация, ретрив) — на сервере. Для фронтендера это важно: **RAG меняет бэкенд, но не меняет фронтенд.**

**Шаг 4. Критерии приёмки.**

- Ответ содержит цитату-источник на каждый факт
- Запрос «как оформить отпуск» находит раздел про отпуска (а не просто слова)
- TTFT < 1 сек, «Стоп», частичный ответ при ошибке, санитизация вывода
- Fallback при недоступности модели

**Вывод кейса:** правильная последовательность — продуктовое определение определило тип фичи (RAG), тип фичи определил архитектуру (бэкенд-сложность), а фронтенд остался стандартным чатом. Ни один шаг не был «сначала код, потом разберёмся».

## Ключевые тезисы для интервью

- AI-фича начинается с продуктовой спецификации: задача пользователя, тип фичи, состояния, ограничения — до выбора технологий.
- Чат/ассистент делается через готовый SDK (Vercel AI SDK): стриминг, состояние, `stop()`, ошибки — из коробки; рукописный парсинг SSE не нужен.
- Архитектура обязательная: клиент → сервер → LLM API; API-ключ только на сервере, клиент никогда не держит ключи в bundle.
- Сервер — точка контроля: логирование, лимиты, переключение провайдеров, сборка промптов.
- Типы AI-фич: чат, встраивание, генерация контента, RAG; RAG переносит сложность на бэкенд (retrieval, эмбеддинги), фронтенд остаётся тем же чатом.
- UX-паттерны AI-чата (индикация генерации, «Стоп», частичный ответ при ошибке, автоскролл, история сессий) — часть спецификации; разбор — в статье Streaming UI.
- Критерии приёмки измеримы: TTFT, поведение «Стоп», сохранение контекста при ошибке, безопасность рендера, обработка rate limits.
- Начинайте с самого простого решения: если база знаний влезает в контекстное окно, RAG не нужен — достаточно промпта.

## Заключение

AI-фича на фронте — это продуктовая задача с известным инструментарием. Правильная последовательность: продуктовое определение → выбор SDK → архитектура «клиент → сервер → LLM API» → UX-паттерны → измеримые критерии приёмки. Всю тяжёлую техническую работу (стриминг, прерывание, парсинг) берут на себя SDK — ваша задача спроектировать фичу и проверить результат.

Главное правило — не начинать с кода. Продуктовое определение задаёт тип фичи, тип фичи — архитектуру, архитектура — что покупать из готового (SDK) и что строить (бэкенд-сложность вроде RAG). Если фичу можно упростить — упрощайте: самые дешёвые AI-фичи часто оказываются самым правильным решением.
