# AI-фичи на фронте: от задачи к реализации

На собеседовании или в реальной работе вам могут дать задачу «сделай чат с ИИ» или «добавь ассистента в продукт». Правильный подход — продуктовый, а не протокольный: определить, что фича должна делать для пользователя, выбрать готовый SDK, спроектировать архитектуру и задать критерии приёмки. Эта статья — о том, как превратить идею AI-фичи в реализацию без изобретения велосипедов.

## Продуктовая спецификация AI-фичи

До выбора технологий определите, что фича делает. Четыре вопроса, на которые нужно ответить до кода:

### 1. Какую задачу решает фича для пользователя?

```text
Плохо: "Сделаем чат с ИИ"
Хорошо: "Пользователь задаёт вопрос по нашим документам и получает
ответ с цитатой-источником, чтобы не искать по 200 страницам вручную"
```

### 2. Какой тип фичи это?

| Тип | Пример | Сложность |
|-----|--------|-----------|
| Чат | Диалог с помощником | Базовый SDK-кейс |
| Ассистент-встраивание | Подсказки в UI, автодополнение форм | Средняя |
| Генерация контента | Резюме, описания, заголовки | Простая, без диалога |
| RAG-ассистент | Ответы по базе знаний | Бэкенд: retrieval + эмбеддинги |

### 3. Какие состояния и сценарии нужно предусмотреть?

- Загрузка, стриминг, ошибка, пустой ответ
- Прерывание генерации
- Повторная отправка
- Длинные сессии

### 4. Каковы ограничения?

- Какой модели хватает (большая не всегда нужна)
- Бюджет на токены
- Latency-требования

Продуктовая спецификация — основа для задания агенту. Отправляйте ему именно её, а не «сделай чат».

## Выбор SDK

Для чата и AI-фич на фронте не нужно писать интеграцию с LLM API вручную. Стандарт индустрии — **Vercel AI SDK**.

```tsx
// Vercel AI SDK — чат со стримингом из коробки
const { messages, input, handleInput, handleSubmit, isLoading, stop } =
  useChat({ api: "/api/chat" });
```

Что SDK даёт из коробки:

- **Стриминг** — ответ появляется по мере генерации (под капотом: fetch + ReadableStream + парсинг SSE)
- **Состояние** — список сообщений с накопленным текстом
- **Прерывание** — `stop()` (под капотом AbortController)
- **Обработка ошибок** — ошибки помечаются в сообщениях
- **Провайдеры** — OpenAI, Anthropic, Google и др. через единый интерфейс

Правило: **если фича — чат или ассистент, берёте AI SDK.** Не потому что SDK «удобный», а потому что парсинг потоков, прерывание и переподключение — решённые задачи, которые незачем решать заново.

## Архитектура: клиент → сервер → LLM API

### Обязательная схема

```
Клиент (React) ──POST /api/chat──► Сервер (Next.js route) ──► LLM API
                                     │
                                     └── API-ключ хранится здесь, НЕ на клиенте
```

Клиент никогда не обращается к LLM API напрямую. Причины:

1. **Безопасность** — API-ключ в клиентском bundle виден всем через DevTools
2. **Контроль** — сервер может логировать, ограничивать, добавлять промпты
3. **Стабильность** — сервер может переключать провайдеров без изменения клиента

### Серверный route

```ts
// app/api/chat/route.ts — Next.js App Router
import { streamText } from "ai";
import { anthropic } from "@ai-sdk/anthropic";

export async function POST(req: Request) {
  const { messages } = await req.json();

  const result = streamText({
    model: anthropic("claude-sonnet-4-6"),
    system: "Ты — ассистент. Отвечай кратко, ссылаясь на факты.",
    messages,
  });

  return result.toDataStreamResponse();
}
```

Клиент получает поток через `useChat`, сервер — через `streamText`. Всю техническую работу (SSE, стриминг, обработка ошибок) делают SDK.

## UX-паттерны чата

Для AI-чата обязателен набор UX-паттернов (подробнее — в статье «Streaming UI»):

- **Индикация генерации** — курсор в конце текста, skeleton до первого токена
- **Кнопка «Стоп»** — прерывание генерации, экономит токены
- **Частичный ответ при ошибке** — показать, что успело сгенерироваться, и дать retry
- **Автоскролл с учётом позиции** — не сбивать пользователя, читающего выше
- **История сессий** — если фича предполагает диалог, нужно хранить и восстанавливать контекст

Эти паттерны — часть спецификации, которую вы передаёте агенту или команде. Они не требуют знания протоколов — только понимания, как пользователь воспринимает генерацию.

## Критерии приёмки

AI-фича принимается не «когда работает», а когда выполнены измеримые критерии:

### Функциональные
- Первый токен появляется < 1 сек после отправки
- Кнопка «Стоп» прерывает генерацию
- При ошибке в середине потока частичный ответ сохраняется
- Retry переиспользует исходный запрос

### Качество ответов
- Модель следует системному промпту (не выходит за роль)
- Ответы релевантны запросу (проверка на выборке примеров)

### Безопасность и соответствие
- Вывод модели рендерится через санитизацию (не `dangerouslySetInnerHTML` без DOMPurify)
- API-ключ только на сервере
- Валидация схемы ввода/вывода

### Инфраструктура
- Обработка rate limits провайдера
- Логирование ошибок и стоимости
- Fallback на случай недоступности модели

## Ключевые тезисы для интервью

- AI-фича начинается с продуктовой спецификации: задача пользователя, тип фичи, состояния, ограничения — до выбора технологий.
- Чат/ассистент делается через готовый SDK (Vercel AI SDK): стриминг, состояние, `stop()`, ошибки — из коробки; рукописный парсинг SSE не нужен.
- Архитектура обязательная: клиент → сервер → LLM API; API-ключ только на сервере, клиент никогда не держит ключи в bundle.
- Сервер — точка контроля: логирование, лимиты, переключение провайдеров.
- UX-паттерны AI-чата: индикация генерации, «Стоп», частичный ответ при ошибке, автоскролл, история сессий.
- Критерии приёмки измеримы: TTFT, поведение «Стоп», сохранение контекста при ошибке, безопасность рендера, обработка rate limits.
- Если фича — RAG-ассистент, сложность на бэкенде (retrieval, эмбеддинги); фронтенд остаётся тем же чатом через SDK.

## Заключение

AI-фича на фронте — это продуктовая задача с известным инструментарием. Правильная последовательность: продуктовое определение → выбор SDK → архитектура «клиент → сервер → LLM API» → UX-паттерны → измеримые критерии приёмки. Всю тяжёлую техническую работу (стриминг, прерывание, парсинг) берут на себя SDK — ваша задача спроектировать фичу и проверить результат.
