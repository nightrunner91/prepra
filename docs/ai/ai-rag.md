# RAG-паттерн

Предыдущая статья разобрала streaming UI — технический мост между LLM API и интерфейсом. Но что показывать пользователю, если модель не знает ответа? LLM обучена на данных с cut-off датой и не видит событий после неё. Она может выдумывать факты, ссылки, API-методы — это называется hallucination. RAG (Retrieval-Augmented Generation) — архитектурный паттерн, который даёт модели актуальные знания перед генерацией, извлекая релевантные документы из внешней базы. Эта статья — о том, как устроен RAG от эмбеддингов до оценки качества retrieval.

## Проблема: устаревший контекст и hallucination

### Ограничения обучающих данных

LLM обучена на корпусе текстов с определённой датой среза. Всё, что произошло после — для модели не существует. Даже если модель обучена на свежих данных, она не знает:

- Приватной информации: внутренняя документация компании, база знаний, переписка.
- Динамических данных: курсы валют, погода, состояние API в реальном времени.
- Узкоспециализированных фактов: детали редких библиотек, внутренние фреймворки.

### Hallucination

Когда модель не знает ответа, она не скажет «не знаю» — она сгенерирует правдоподобный текст. Это hallucination: выдуманные факты, несуществующие API-методы, фиктивные ссылки.

```
Пользователь: "Какой метод в библиотеке prepra.js возвращает список модулей?"

Модель без контекста: "Метод prepra.getModules() возвращает массив всех
зарегистрированных модулей. Вызовите prepra.getModules().then(modules => ...)"

Реальность: такого метода не существует. Модель сгенерировала правдоподобный,
но выдуманный ответ.
```

Hallucination — не баг конкретной модели, а следствие архитектуры: LLM предсказывает следующий токен, а не проверяет факты. Модель не различает «я знаю это» и «это звучит правдоподобно».

### Решение: дать модели контекст

Вместо того чтобы надеяться на память модели, мы извлекаем релевантные документы из внешней базы и вкладываем их в промпт. Модель генерирует ответ, опираясь на конкретные факты, а не на вероятностные ассоциации.

Это и есть RAG: **retrieval** (поиск) → **augmentation** (обогащение промпта) → **generation** (ответ модели).

```
Без RAG:
Пользователь → Промпт → LLM → Ответ (из памяти, может быть выдумкой)

С RAG:
Пользователь → Промпт → [Retrieval: поиск документов] →
  Обогащённый промпт (вопрос + найденные документы) → LLM → Ответ (на основе фактов)
```

## Векторные эмбеддинги и семантический поиск

### Что такое эмбеддинг

Эмбеддинг — числовое представление текста в виде вектора (массива чисел). Эмбеддинг-модель (отдельная от LLM) принимает текст и возвращает вектор фиксированной размерности, например 1536 чисел.

```ts
const embedding = await getEmbedding("Как вернуть список модулей?");
// [0.023, -0.041, 0.087, ..., 0.012] — 1536 чисел
```

Семантически близкие тексты получают близкие векторы. «Как вернуть список модулей?» и `getModules()` в API-документации будут иметь похожие эмбеддинги, хотя лексически они разные.

### Почему не обычный поиск

Традиционный полнотекстовый поиск (Elasticsearch, SQLite FTS) ищет по совпадению слов. Запрос «как отменить заказ» не найдёт документ «возврат покупки» — слова разные, хотя смысл один.

Семантический поиск ищет по смыслу. Эмбеддинги кодируют смысл текста в вектор, и расстояние между векторами отражает смысловую близость.

| Запрос | Полнотекстовый поиск | Семантический поиск |
|--------|---------------------|---------------------|
| «как отменить заказ» | Ищет «отменить», «заказ» | Находит «возврат покупки», «отмена заказа» |
| «prepra.js модули» | Ищет «prepra», «модули» | Находит `prepra.getModules()` в документации |
| «ошибка 500 при деплое» | Ищет «ошибка», «500», «деплой» | Находит «HTTP 500 на stage deployment» в changelog |

###相似度: косинусное расстояние

Схожесть между векторами измеряется косинусным расстоянием — косинус угла между двумя векторами. Значение от -1 до 1, где 1 — идентичные направления (максимальная схожесть), 0 — ортогональны (нет связи), -1 — противоположны.

```ts
function cosineSimilarity(a: number[], b: number[]): number {
  let dotProduct = 0;
  let normA = 0;
  let normB = 0;

  for (let i = 0; i < a.length; i++) {
    dotProduct += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }

  return dotProduct / (Math.sqrt(normA) * Math.sqrt(normB));
}

const similarity = cosineSimilarity(embeddingQuery, embeddingDocument);
// 0.87 — высокая семантическая близость
```

### Векторные базы данных

Хранить тысячи векторов и искать ближайших — задача для специализированных баз данных. Они индексируют векторы для быстрого approximate nearest neighbor (ANN) поиска.

Популярные решения:

- **Pgvector** — расширение PostgreSQL, подходит для проектов уже на Postgres.
- **Pinecone** — управляемый сервис, не нужно обслуживать инфраструктуру.
- **Qdrant** — open-source, можно хостить самостоятельно.
- **ChromaDB** — лёгкий, подходит для прототипов и локальной разработки.

```ts
import { Pinecone } from "@pinecone-database/pinecone";

const pc = new Pinecone({ apiKey: process.env.PINECONE_API_KEY! });
const index = pc.index("docs");

// Поиск ближайших векторов
const results = await index.query({
  vector: queryEmbedding,
  topK: 5,
  includeMetadata: true,
});

// results.matches — 5 наиболее семантически близких документов
```

Для большинства задач `topK` от 3 до 10 достаточно. Больше — увеличиваем контекст и стоимость, но diminishing returns: после 10-го документа релевантность падает.

### Эмбеддинг-модели

Эмбеддинг-модель — отдельная от LLM, обучена специально для кодирования текста в вектор. Выбор модели влияет на качество поиска.

Критерии выбора:

- **Размерность вектора** — больше размерность → точнее, но дороже хранение и поиск.
- **Язык** — мультиязычные модели (multilingual-e5, bge-m3) работают с русским и английским; моноязычные — лучше для одного языка.
- **Максимальная длина** — обычно 512 токенов; если chunk больше — обрезается и теряет смысл.

## Chunking: стратегии разбиения документов

### Зачем разбивать

Эмбеддинг-модель имеет лимит входных токенов (обычно 512). Документ на 50 страниц — 40 000 токенов — не влезет. Кроме того, большой документ содержит множество тем, и его эмбеддинг будет «размытым» — не близким ни к одному конкретному запросу.

Разбиение документа на chunk'и решает обе проблемы: каждый chunk — смысловая единица, которая влезает в лимит эмбеддинга.

### Стратегии разбиения

#### Fixed-size chunking

Простейший подход: разбить текст на куски фиксированного размера с перекрытием.

```ts
function chunkBySize(text: string, chunkSize: number, overlap: number): string[] {
  const chunks: string[] = [];
  const words = text.split(/\s+/);

  for (let i = 0; i < words.length; i += chunkSize - overlap) {
    chunks.push(words.slice(i, i + chunkSize).join(" "));
    if (i + chunkSize >= words.length) break;
  }

  return chunks;
}

const chunks = chunkBySize(longDocument, 200, 40);
// 200 слов в chunk, 40 слов перекрытия между соседними
```

Плюсы: просто, предсказуемо. Минусы: может разрезать предложение или абзац пополам, теряя смысл.

#### Sentence-based chunking

Разбиение по предложениям с накоплением до целевого размера.

```ts
function chunkBySentences(text: string, maxTokens: number): string[] {
  const sentences = text.match(/[^.!?]+[.!?]+/g) ?? [text];
  const chunks: string[] = [];
  let current = "";

  for (const sentence of sentences) {
    if (estimateTokens(current + sentence) > maxTokens && current) {
      chunks.push(current.trim());
      current = "";
    }
    current += sentence;
  }

  if (current.trim()) chunks.push(current.trim());
  return chunks;
}
```

Плюсы: chunk не разрывает предложение. Минусы: предложения могут быть очень длинными (юридические тексты) или очень короткими (заголовки).

#### Semantic chunking

Разбиение по смысловым границам: абзацы, секции, заголовки. Использует структуру документа.

```ts
function chunkBySections(markdown: string): { heading: string; content: string }[] {
  const sections: { heading: string; content: string }[] = [];
  const parts = markdown.split(/^## /m);

  for (const part of parts.slice(1)) {
    const [heading, ...rest] = part.split("\n");
    sections.push({ heading, content: rest.join("\n").trim() });
  }

  return sections;
}
```

Плюсы: каждый chunk — законченная смысловая единица с контекстом заголовка. Минусы: работает только для структурированных документов; секции могут быть слишком большими.

#### Recursive chunking

Комбинация стратегий: пробуем разбить по секциям, если секция слишком большая — рекурсивно разбиваем по абзацам, если абзац большой — по предложениям.

```ts
function recursiveChunk(text: string, maxTokens: number): string[] {
  if (estimateTokens(text) <= maxTokens) return [text];

  // Пробуем разбить по секциям (##)
  const sections = text.split(/^## /m);
  if (sections.length > 1) {
    return sections.flatMap(s => recursiveChunk(s, maxTokens));
  }

  // Пробуем разбить по абзацам
  const paragraphs = text.split(/\n\n+/);
  if (paragraphs.length > 1) {
    return paragraphs.flatMap(p => recursiveChunk(p, maxTokens));
  }

  // Фолбэк: разбить по предложениям
  return chunkBySentences(text, maxTokens);
}
```

### Размер chunk'а: компромисс

| Размер | Плюсы | Минусы |
|--------|-------|--------|
| 100–200 токенов | Точный поиск, узкая тема | Много chunk'ов, теряется контекст между ними |
| 300–500 токенов | Баланс точности и контекста | Может захватить несколько тем |
| 500–1000 токенов | Сохраняет широкий контекст | Эмбеддинг «размыт», поиск менее точный |

Практическое правило: **300–500 токенов с перекрытием 10–20%**. Достаточно для сохранения смысла, достаточно узко для точного поиска.

### Перекрытие (overlap)

Перекрытие — общие токены между соседними chunk'ами. Нужно, чтобы информация на границе не потерялась.

```
Chunk 1: [токены 1–200]
Chunk 2: [токены 160–360]   ← перекрытие 40 токенов
Chunk 3: [токены 320–520]
```

Без перекрытия ключевая фраза, попавшая на границу, может оказаться в «обрезанном» виде в одном chunk и потеряться для поиска.

### Метаданные chunk'ов

Каждый chunk хранит метаданные для фильтрации и трассировки:

```ts
interface DocumentChunk {
  id: string;
  content: string;
  embedding: number[];
  metadata: {
    source: string;       // URL или путь к файлу
    title: string;        // Заголовок документа
    section: string;      // Секция/заголовок раздела
    chunkIndex: number;   // Порядковый номер в документе
    createdAt: string;    // Дата индексации
  };
}
```

Метаданные позволяют фильтровать поиск: «искать только в документации v2» или «только в статьях про API».

## Retrieval + Augmentation + Generation — полный цикл

### Архитектура RAG

Полный цикл состоит из двух фаз: **индексация** (оффлайн) и **поиск + генерация** (онлайн).

```
Фаза 1: Индексация (оффлайн, при добавлении/обновлении документов)
─────────────────────────────────────────────────────────────────
Документы → Chunking → Эмбеддинг-модель → Векторная БД

Фаза 2: Поиск + Генерация (онлайн, на каждый запрос пользователя)
─────────────────────────────────────────────────────────────────
Запрос пользователя → Эмбеддинг → Поиск в векторной БД →
  Top-K документов → Формирование промпта → LLM → Ответ
```

### Индексация

```ts
async function indexDocument(source: string, content: string) {
  const chunks = recursiveChunk(content, 400);

  const embeddings = await Promise.all(
    chunks.map(chunk => getEmbedding(chunk))
  );

  const records = chunks.map((content, i) => ({
    id: `${source}#${i}`,
    values: embeddings[i],
    metadata: {
      source,
      content,
      chunkIndex: i,
      createdAt: new Date().toISOString(),
    },
  }));

  await vectorDb.upsert(records);
}
```

Индексация запускается при добавлении нового документа и при обновлении существующего. Старые chunk'и удаляются и заменяются новыми.

### Retrieval

```ts
async function retrieve(query: string, topK = 5): Promise<DocumentChunk[]> {
  const queryEmbedding = await getEmbedding(query);

  const results = await vectorDb.query({
    vector: queryEmbedding,
    topK,
    includeMetadata: true,
  });

  return results.matches.map(match => ({
    id: match.id,
    content: match.metadata.content,
    source: match.metadata.source,
    score: match.score,
  }));
}
```

### Augmentation: формирование промпта

Найденные документы вставляются в промпт как контекст. Порядок и формат влияют на качество ответа.

```ts
function buildRAGPrompt(query: string, documents: DocumentChunk[]): string {
  const context = documents
    .map((doc, i) => `[Документ ${i + 1}] (${doc.source}):\n${doc.content}`)
    .join("\n\n");

  return `Ты — ассистент, который отвечает на вопросы строго на основе предоставленных документов.
Если ответа нет в документах — скажи "Не нашёл информации в базе знаний".

## Документы:
${context}

## Вопрос:
${query}

## Инструкция:
Ответь на вопрос, используя только информацию из документов выше.
Укажи номер документа в квадратных скобках, если используешь факт из него.`;
}
```

Ключевые принципы augmentation:

- **Явная инструкция** — модель должна знать, что отвечает на основе документов, а не памяти.
- **Фолбэк** — если ответа нет в контексте, модель говорит «не знаю», а не выдумывает.
- **Цитирование** — указание источника позволяет пользователю проверить факт.

### Generation

```ts
async function ragQuery(query: string): Promise<string> {
  const documents = await retrieve(query, 5);
  const prompt = buildRAGPrompt(query, documents);

  const response = await client.messages.create({
    model: "claude-sonnet-4-6",
    max_tokens: 1024,
    messages: [{ role: "user", content: prompt }],
  });

  return response.content[0].text;
}
```

### Re-ranking: улучшение качества retrieval

Первичный поиск по эмбеддингам — approximate. Он быстрый, но может пропустить релевантные документы или вернуть шум. Re-ranking — второй проход, который пересортировывает результаты более точной (но медленной) моделью.

```ts
async function retrieveWithReranking(query: string, topK = 5): Promise<DocumentChunk[]> {
  // Первый проход: быстрый семантический поиск, больше результатов
  const candidates = await retrieve(query, 20);

  // Второй проход: re-ranking более точной моделью
  const reranked = await reranker.rerank(query, candidates.map(c => c.content));

  // Возвращаем top-K после re-ranking
  return reranked
    .slice(0, topK)
    .map(r => candidates[r.index]);
}
```

Re-ranking особенно полезен, когда первичный поиск возвращает много «почти релевантных» документов. Он дороже, но вызывается только для 20 кандидатов, а не для миллионов.

### Гибридный поиск

Комбинация семантического и полнотекстового поиска. Полнотекстовый находит точные совпадения (номера ошибок, названия функций), семантический — смысловую близость.

```ts
async function hybridSearch(query: string, topK = 5): Promise<DocumentChunk[]> {
  // Параллельно: семантический и полнотекстовый поиск
  const [semanticResults, keywordResults] = await Promise.all([
    vectorSearch(query, 20),
    fulltextSearch(query, 20),
  ]);

  // Объединение через Reciprocal Rank Fusion (RRF)
  const scores = new Map<string, number>();

  semanticResults.forEach((doc, rank) => {
    scores.set(doc.id, (scores.get(doc.id) ?? 0) + 1 / (rank + 60));
  });

  keywordResults.forEach((doc, rank) => {
    scores.set(doc.id, (scores.get(doc.id) ?? 0) + 1 / (rank + 60));
  });

  const sorted = [...scores.entries()]
    .sort((a, b) => b[1] - a[1])
    .slice(0, topK);

  return sorted.map(([id]) => findChunkById(id));
}
```

RRF даёт каждому документу_score_ на основе позиции в обоих списках. Документ, который высоко в обоих ранжированиях, получает максимальный суммарный score.

## RAG vs Fine-tuning: когда что

### Fine-tuning

Дообучение модели на специфичных данных. Модель «запоминает» паттерны, стиль, терминологию. После fine-tuning новые знания — часть весов модели.

### Сравнение

| Критерий | RAG | Fine-tuning |
|----------|-----|-------------|
| Актуальность данных | Моментальная — обновил БД | Устаревает — нужно переобучать |
| Стоимость | Плата за retrieval + токены контекста | Плата за обучение (дорого), inference дешевле |
| Источники ошибок | Может не найти нужный документ | Может «забыть» или исказить выученное |
| Приватные данные | Подходит — данные в векторной БД | Рискованно — данные в весах модели |
| Скорость внедрения | Часы — индексация + промпт | Дни-недели — датасет, обучение, валидация |
| Объём знаний | Практически не ограничен (внешняя БД) | Ограничен контекстом обучения |
| Обновление | Добавил документ в БД | Переобучить модель |

### Когда RAG

- **Знания меняются часто** — документация, новости, changelog.
- **Нужна трассировка** — пользователь видит источник факта и может проверить.
- **Данные приватные** — внутренняя документация, которая не должна попасть в веса модели.
- **Объём знаний большой** — тысячи документов, которые не влезут в fine-tuning датасет.

### Когда Fine-tuning

- **Нужен специфический стиль** — тон, формат ответа, терминология компании.
- **Паттерны, а не факты** — модель должна научиться решать задачи определённым способом.
- **Latency критична** — fine-tuned модель не тратит время на retrieval.
- **RAG не справляется** — когда нужно «понимание» предмета, а не поиск по документам.

### Комбинация

На практике RAG и fine-tuning комбинируют: fine-tuning даёт модели предметное понимание и стиль, RAG — актуальные факты.

```
Fine-tuned модель (понимает предметную область, отвечает в нужном стиле)
  + RAG (подаёт актуальные документы как контекст)
  = Точные, стилистически корректные ответы на основе свежих данных
```

## Оценка качества retrieval

### Почему retrieval — слабое звено

Генерация зависит от качества retrieval. Если retrieval вернул нерелевантные документы — модель даст неправильный ответ, даже если сама по себе точна. Ошибки retrieval каскадируют в generation.

### Метрики качества retrieval

#### Recall@K

Доля релевантных документов, найденных среди top-K результатов.

```
Золотой набор: 10 вопрос-ответных пар, для каждой известны релевантные документы.

Для каждого вопроса:
  - Получаем top-K документов из retrieval
  - Считаем: сколько из известных релевантных документов попали в top-K

Recall@5 = (найдено релевантных) / (всего релевантных)

Пример: из 10 релевантных документов нашли 8 в top-5 → Recall@5 = 0.8
```

#### MRR (Mean Reciprocal Rank)

Среднее значение обратной позиции первого релевантного документа.

```ts
function calculateMRR(queries: { relevant: string; retrieved: string[] }[]): number {
  const reciprocalRanks = queries.map(q => {
    const firstRelevantIndex = q.retrieved.indexOf(q.relevant);
    return firstRelevantIndex === -1 ? 0 : 1 / (firstRelevantIndex + 1);
  });

  return reciprocalRanks.reduce((a, b) => a + b, 0) / queries.length;
}

// MRR = 0.75 → в среднем первый релевантный документ на позиции ~1.3
```

#### NDCG (Normalized Discounted Cumulative Gain)

Учитывает не только наличие релевантных документов, но и их порядок. Релевантный документ на первой позиции ценнее, чем на пятой.

### Golden dataset

Набор вопрос-ответных пар с размеченными релевантными документами. Основа для оценки retrieval.

```ts
interface GoldenEntry {
  question: string;
  expectedAnswer: string;
  relevantDocumentIds: string[];
  tags: string[]; // для группировки и фильтрации
}

const goldenDataset: GoldenEntry[] = [
  {
    question: "Как отменить заказ?",
    expectedAnswer: "Отменить заказ можно в разделе «Мои заказы» → «Отменить».",
    relevantDocumentIds: ["docs/orders.md#2", "docs/faq.md#5"],
    tags: ["orders", "ui"],
  },
  // ...
];
```

Как собирать golden dataset:

- **Из реальных запросов** — берём вопросы пользователей, размечаем релевантные документы.
- **Из документации** — для каждой секции генерируем возможные вопросы.
- **От экспертов** — предметные специалисты формулируют вопросы и ответы.

Минимум 50–100 пар для осмысленной оценки. Чем больше — тем надёжнее метрики.

### Автоматическая оценка end-to-end

Оценка не только retrieval, но и генерации:

```ts
async function evaluateRAG(entry: GoldenEntry): Promise<EvalResult> {
  const answer = await ragQuery(entry.question);

  // LLM-as-judge: сравниваем ответ модели с ожидаемым
  const judge = await client.messages.create({
    model: "claude-sonnet-4-6",
    messages: [{
      role: "user",
      content: `Оцени ответ по шкале 1-5:
Вопрос: ${entry.question}
Ожидаемый ответ: ${entry.expectedAnswer}
Полученный ответ: ${answer}

Оцени: точность, полноту, отсутствие выдуманных фактов.
Верни JSON: { "accuracy": N, "completeness": N, "hallucination": bool }`,
    }],
  });

  return parseJudgeResult(judge.content[0].text);
}
```

### Мониторинг в продакшне

Оффлайн-оценка на golden dataset — разовая. В продакшне нужен постоянный мониторинг:

- **Пустые результаты** — retrieval не нашёл ничего. Сигнал: нужно добавить документы или улучшить chunking.
- **Низкий score** — top-1 результат имеет score < 0.7. Сигнал: возможно, запрос не покрыт базой знаний.
- **Отказы модели** — модель отвечает «не нашёл информации». Сигнал: retrieval работает, но документы не содержат ответа.
- **Пользовательский фидбек** — кнопки «полезно / бесполезно» после каждого ответа.

```ts
interface RAGMetrics {
  emptyRetrievals: number;     // запросы без результатов
  lowScoreRetrievals: number;  // top-1 score < 0.7
  modelRefusals: number;       // модель ответила "не знаю"
  userHelpful: number;         // пользователь нажал "полезно"
  userNotHelpful: number;      // пользователь нажал "бесполезно"
}
```

## Ключевые тезисы для интервью

- RAG (Retrieval-Augmented Generation) решает проблему устаревшего контекста и hallucination — извлекает релевантные документы из внешней базы и вкладывает их в промпт перед генерацией.
- Векторные эмбеддинги кодируют смысл текста в числовой вектор; семантический поиск находит по смысловой близости, а не по совпадению слов.
- Косинусное расстояние — основная метрика схожести векторов; 1 = идентичные направления, 0 = нет связи.
- Chunking — разбиение документов на смысловые единицы; стратегии: fixed-size, sentence-based, semantic, recursive. Практическое правило: 300–500 токенов с перекрытием 10–20%.
- Полный цикл RAG: retrieval (поиск top-K документов) → augmentation (формирование промпта с контекстом) → generation (ответ модели с инструкцией использовать только документы).
- Re-ranking — второй проход поиска более точной моделью для пересортировки кандидатов; гибридный поиск комбинирует семантический и полнотекстовый через Reciprocal Rank Fusion.
- RAG подходит для часто меняющихся, приватных и больших объёмов знаний; fine-tuning — для стиля, паттернов и latency-critical сценариев; на практике комбинируются.
- Оценка retrieval: Recall@K, MRR, NDCG на golden dataset (50–100+ размеченных пар); в продакшне — мониторинг пустых результатов, низких score, отказов модели, пользовательского фидбека.
- RAG не решает: не улучшает «понимание» модели (только даёт факты), не исправляет плохой chunking, не помогает если документы противоречивы.

## Заключение

RAG — архитектурный паттерн, который даёт модели актуальные знания без переобучения. Техническая цепочка: документы → chunking → эмбеддинги → векторная БД (индексация), затем запрос → эмбеддинг → поиск → формирование промпта → генерация (онлайн).

Ключевые выводы:

- **RAG решает hallucination и устаревший контекст** — модель отвечает на основе документов, а не памяти.
- **Chunking — критическое решение** — от размера и стратегии зависит качество поиска; 300–500 токенов с перекрытием — рабочая точка старта.
- **Re-ranking и гибридный поиск** повышают точность retrieval, когда первичный семантический поиск возвращает шум.
- **RAG + fine-tuning — не альтернативы, а дополнения** — fine-tuning даёт стиль и понимание, RAG — актуальные факты.
- **Golden dataset обязателен** — без размеченных пар невозможно оценить, работает ли retrieval.
