# Streaming UI

Предыдущая статья разобралась, как работать с AI-агентами. С точки зрения пользователя всё происходит «внутри»: единственное, что он видит — текст, появляющийся на экране. Streaming UI — слой между LLM API и интерфейсом: как доставлять ответ модели токен за токеном и как правильно это выглядит для пользователя. Эта статья — о UX-паттернах потоковых ответов, а не о протоколе: всю техническую часть берёт на себя SDK.

## Почему стриминг нужен

LLM генерирует ответ токен за токеном. Для ответа в 500 токенов при скорости 50 токенов/сек это 10 секунд. Если ждать полного ответа перед показом — пользователь увидит пустой экран 10 секунд, затем весь текст сразу. Воспринимаемая latency = 10 секунд.

Со стримингом пользователь видит первый токен через 300–800 мс (TTFT), а затем текст появляется постепенно. Воспринимаемая latency = 300–800 мс. Содержимое то же самое, но ощущение — мгновенный отклик.

```
Non-streaming:  Клиент → [генерация 10 сек] → весь ответ разом
Streaming:      Клиент → токен₁ → токен₂ → ... → токен₅₀₀
                          ↑ первый токен через ~500мс
```

Ключевой факт: **стриминг не ускоряет генерацию**, он улучшает восприятие. Для большинства пользовательских интерфейсов стриминг — не оптимизация, а обязательное требование к UX.

## Что делает SDK за вас

Техническая реализация стриминга — чтение SSE, парсинг событий, прерывание через AbortController, переподключение — **уже решена в SDK**. Фронтендер не пишет парсинг потоков руками, он использует готовое решение.

```tsx
// Vercel AI SDK — стриминг, состояние, abort и retry из коробки
const { messages, input, handleInput, handleSubmit, isLoading, stop } =
  useChat({ api: "/api/chat" });
```

- `messages` — полный список сообщений с накопленным текстом
- `isLoading` — идёт ли генерация
- `stop()` — прерывание генерации (под капотом — AbortController)
- Ошибки в середине потока SDK помечает в сообщении

Если на собеседовании спрашивают «как реализовать стриминг» — правильный ответ: **«беру Vercel AI SDK / useChat, он сам умеет парсить поток, прерывать и обрабатывать ошибки; под капотом это fetch + ReadableStream + парсинг SSE, и я понимаю, что там происходит, но не пишу это руками»**.

Понимать «что под капотом» нужно на уровне концепций — чтобы знать, что SDK делает и почему, — а не на уровне кода.

## UX-паттерны: индикация, прерывание, retry

### Индикатор генерации

Пользователь должен видеть, что генерация идёт. Три уровня индикации:

```tsx
// 1. Курсор — мигающий символ в конце текста
{isLoading && <span className="cursor animate-pulse">▊</span>}

// 2. Skeleton — плейсхолдер, пока не пришёл первый токен
{isLoading && content === "" && (
  <div className="skeleton">
    <div className="skeleton-line w-3/4" />
    <div className="skeleton-line w-1/2" />
    <div className="skeleton-line w-2/3" />
  </div>
)}

// 3. Индикатор в header — «Модель думает...»
{isLoading && (
  <div className="status-bar">
    <Spinner />
    <span>Генерация ответа...</span>
    <button onClick={stop}>Стоп</button>
  </div>
)}
```

Skeleton особенно важен: без него пользователь видит пустое место и не понимает, идёт ли генерация или произошёл сбой.

### Кнопка «Стоп»

Кнопка прерывания должна быть доступна всегда во время генерации и исчезать сразу после завершения. Переключение «Отправить → Стоп» — стандартный паттерн чат-интерфейсов: кнопка меняет поведение в зависимости от состояния.

```tsx
{isStreaming ? (
  <button onClick={stop}>Остановить</button>
) : (
  <button onClick={send}>Отправить</button>
)}
```

### Автоскролл

При стриминге текст появляется постепенно. Если пользователь находится внизу — скроллим вниз автоматически. Если пользователь отскроллил вверх для чтения — не трогаем.

```tsx
useEffect(() => {
  if (!isUserScrolledUp.current) {
    container.scrollTo({ top: container.scrollHeight, behavior: "smooth" });
  }
}, [messages]);
```

`isUserScrolledUp` — флаг, который обновляется по скроллу: если пользователь дальше 100px от низа — считаем, что он читает, и не сбиваем его.

### Блокировка ввода во время генерации

Пока идёт генерация, новая отправка невозможна — сервер обрабатывает предыдущий запрос. Ввод блокируем, но показываем, что он заблокирован:

```tsx
<textarea
  value={inputValue}
  onChange={handleInput}
  disabled={isStreaming}
  placeholder={isStreaming ? "Дождитесь окончания ответа..." : "Введите сообщение..."}
/>
```

Альтернатива — очередь запросов, но это усложняет серверную часть и редко нужно для LLM-чатов.

## Обработка ошибок в середине потока

### Типы ошибок при стриминге

1. **Ошибка до начала стрима** — HTTP 4xx/5xx, сеть недоступна. Обрабатывается как обычный fetch-error.
2. **Ошибка в середине стрима** — соединение обрывается, сервер возвращает ошибку. Часть ответа уже показана пользователю.
3. **Ошибка LLM** — rate limit, content policy, internal error.

### Принцип: частичный ответ сохраняется

Самый сложный случай: пользователь уже видит часть ответа. Нельзя просто очистить экран — потеряется контекст. Нужно показать то, что успело сгенерироваться, и обозначить ошибку.

```tsx
{message.error && (
  <div className="message-error">
    <span>Ошибка: {message.error.message}</span>
    <button onClick={() => retry(message.id)}>Повторить</button>
  </div>
)}
```

Retry переиспользует промпт пользователя и создаёт новый assistant-message взамен ошибочного. Пользователь видит, что модель успела сгенерировать, и может повторить запрос.

## Ключевые тезисы для интервью

- Streaming снижает **воспринимаемую** latency с полного времени генерации до TTFT (300–800 мс) — сам стриминг не ускоряет генерацию, он улучшает ощущение скорости.
- Техническую реализацию стриминга (парсинг SSE, AbortController, переподключение) берёт на себя SDK — Vercel AI SDK (`useChat`) даёт состояние, `stop()` и обработку ошибок из коробки.
- Индикация генерации — три уровня: курсор, skeleton до первого токена, статус-бар с кнопкой «Стоп».
- Кнопка «Стоп» обязательна: без прерывания сервер продолжает генерировать, расходуя токены и деньги.
- Ошибка в середине потока — частичный ответ остаётся на экране, пользователь может повторить через retry.
- Автоскролл учитывает позицию пользователя: если он отскроллил вверх для чтения — автоскролл не срабатывает.

## Заключение

Streaming UI — мост между LLM API и пользовательским восприятием. Со стороны продукта: индикация генерации, кнопка «Стоп», автоскролл, обработка ошибок без потери контекста. Со стороны кода — готовое решение из SDK, а не рукописный парсер протокола.

Ключевые выводы:

- **Streaming снижает воспринимаемую latency** — содержимое то же, но пользователь получает отклик мгновенно.
- **SDK делает всю техническую работу** — состояние, прерывание, ошибки из коробки.
- **AbortController обязателен** — без него пользователь не может прервать генерацию, а сервер расходует токены впустую.
- **Ошибки в середине потока — нормальное состояние** — частичный ответ сохраняется, пользователь может повторить.
