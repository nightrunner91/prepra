# Streaming UI

С точки зрения пользователя всё «внутри» — единственное, что он видит, это текст, появляющийся на экране. Streaming UI — слой между LLM API и интерфейсом: как доставлять ответ модели токен за токеном и как это правильно выглядит для пользователя. Эта статья — о UX-паттернах потоковых ответов: индикация генерации, прерывание, обработка ошибок, автоскролл и блокировка ввода. Техническую часть (парсинг SSE, AbortController) берёт на себя SDK — здесь она упоминается только как контекст, а фокус на том, как пользователь воспринимает генерацию.

## Почему стриминг нужен

LLM генерирует ответ токен за токеном. Для ответа в 500 токенов при скорости 50 токенов/сек это 10 секунд. Если ждать полного ответа перед показом — пользователь увидит пустой экран 10 секунд, затем весь текст сразу. Воспринимаемая latency = 10 секунд.

Со стримингом пользователь видит первый токен через 300–800 мс (TTFT), а затем текст появляется постепенно. Воспринимаемая latency = 300–800 мс. Содержимое то же самое, но ощущение — мгновенный отклик.

```
Non-streaming:  Клиент → [генерация 10 сек] → весь ответ разом
Streaming:      Клиент → токен₁ → токен₂ → ... → токен₅₀₀
                          ↑ первый токен через ~500мс
```

Ключевой факт: **стриминг не ускоряет генерацию**, он улучшает восприятие. Для большинства пользовательских интерфейсов стриминг — не оптимизация, а обязательное требование к UX.

### Воспринимаемая vs реальная latency

| Метрика | Non-streaming | Streaming |
|---------|---------------|-----------|
| Реальное время генерации | 10 сек | 10 сек (то же) |
| Первый видимый контент | Через 10 сек | Через 300–800 мс |
| Воспринимаемая скорость | Медленно | Мгновенно |
| Возможность читать в процессе | Нет | Да |

Подробнее о TTFT и latency — в статье [Ментальная модель LLM](./ai-mental-model.md).

## Что делает SDK за вас

Техническая реализация стриминга — чтение SSE, парсинг событий, прерывание через AbortController, переподключение — **уже решена в SDK**. Фронтендер не пишет парсинг потоков руками, он использует готовое решение.

```tsx
// Vercel AI SDK — стриминг, состояние, abort и retry из коробки
const { messages, input, handleInput, handleSubmit, isLoading, stop } =
  useChat({ api: "/api/chat" });
```

- `messages` — полный список сообщений с накопленным текстом
- `isLoading` — идёт ли генерация
- `stop()` — прерывание генерации (под капотом — AbortController)
- Ошибки в середине потока SDK помечает в сообщении

### Таблица: что решает SDK, а что остаётся UI

| Задача | SDK | UI (вы) |
|--------|-----|---------|
| Парсинг SSE/потока | ✅ | — |
| Накопление текста в сообщении | ✅ | — |
| Прерывание (AbortController) | ✅ | Кнопка «Стоп» |
| Флаг isLoading | ✅ | Индикаторы на его основе |
| Ошибки в сообщении | ✅ | Рендер ошибки, retry |
| Индикация генерации | — | Курсор, skeleton, статус-бар |
| Автоскролл | — | Логика позиции пользователя |
| Блокировка ввода | — | disabled + плейсхолдер |

Если на собеседовании спрашивают «как реализовать стриминг» — правильный ответ: **«беру Vercel AI SDK / useChat, он сам умеет парсить поток, прерывать и обрабатывать ошибки; под капотом это fetch + ReadableStream + парсинг SSE, и я понимаю, что там происходит, но не пишу это руками»**.

Понимать «что под капотом» нужно на уровне концепций — чтобы знать, что SDK делает и почему, — а не на уровне кода.

## UX-паттерны: индикация, прерывание, retry

### Индикатор генерации

Пользователь должен видеть, что генерация идёт. Три уровня индикации:

```tsx
// 1. Курсор — мигающий символ в конце текста
{isLoading && <span className="cursor animate-pulse">▊</span>}

// 2. Skeleton — плейсхолдер, пока не пришёл первый токен
{isLoading && content === "" && (
  <div className="skeleton">
    <div className="skeleton-line w-3/4" />
    <div className="skeleton-line w-1/2" />
    <div className="skeleton-line w-2/3" />
  </div>
)}

// 3. Индикатор в header — «Модель думает...»
{isLoading && (
  <div className="status-bar">
    <Spinner />
    <span>Генерация ответа...</span>
    <button onClick={stop}>Стоп</button>
  </div>
)}
```

Skeleton особенно важен: без него пользователь видит пустое место и не понимает, идёт ли генерация или произошёл сбой.

### Таблица: три уровня индикации

| Уровень | Когда виден | Что сообщает | Когда нужен |
|---------|-------------|--------------|-------------|
| Курсор | После первого токена | Текст ещё растёт | Всегда при стриминге |
| Skeleton | До первого токена | Генерация началась | Длинный TTFT, пустое место |
| Статус-бар + «Стоп» | Вся генерация | Идёт процесс + есть управление | Длительные ответы |

### Кнопка «Стоп»

Кнопка прерывания должна быть доступна всегда во время генерации и исчезать сразу после завершения. Переключение «Отправить → Стоп» — стандартный паттерн чат-интерфейсов: кнопка меняет поведение в зависимости от состояния.

```tsx
{isStreaming ? (
  <button onClick={stop}>Остановить</button>
) : (
  <button onClick={send}>Отправить</button>
)}
```

Почему «Стоп» обязателен: без прерывания сервер продолжает генерировать, расходуя токены и деньги. Кнопка — это не вежливость к пользователю, а контроль бюджета: пользователь получил нужную часть ответа — он может остановить генерацию и не платить за остальное.

### Автоскролл

При стриминге текст появляется постепенно. Если пользователь находится внизу — скроллим вниз автоматически. Если пользователь отскроллил вверх для чтения — не трогаем.

```tsx
useEffect(() => {
  if (!isUserScrolledUp.current) {
    container.scrollTo({ top: container.scrollHeight, behavior: "smooth" });
  }
}, [messages]);
```

`isUserScrolledUp` — флаг, который обновляется по скроллу: если пользователь дальше 100px от низа — считаем, что он читает, и не сбиваем его.

**Антипаттерн:** автоскролл без учёта позиции. Если пользователь поднялся перечитать прошлый ответ, а стриминг тянет его вниз — это гарантированный способ разозрить. Паттерн «всегда вниз» допустим только для коротких ответов.

### Блокировка ввода во время генерации

Пока идёт генерация, новая отправка невозможна — сервер обрабатывает предыдущий запрос. Ввод блокируем, но показываем, что он заблокирован:

```tsx
<textarea
  value={inputValue}
  onChange={handleInput}
  disabled={isStreaming}
  placeholder={isStreaming ? "Дождитесь окончания ответа..." : "Введите сообщение..."}
/>
```

Альтернатива — очередь запросов, но это усложняет серверную часть и редко нужно для LLM-чатов.

## Обработка ошибок в середине потока

### Типы ошибок при стриминге

1. **Ошибка до начала стрима** — HTTP 4xx/5xx, сеть недоступна. Обрабатывается как обычный fetch-error.
2. **Ошибка в середине стрима** — соединение обрывается, сервер возвращает ошибку. Часть ответа уже показана пользователю.
3. **Ошибка LLM** — rate limit, content policy, internal error.

### Таблица: тип ошибки → поведение UI

| Тип | Когда | Что делает пользователь | Что должен делать UI |
|-----|-------|-------------------------|----------------------|
| До стрима | До первого токена | Видит, что ничего не пришло | Обычный error state + retry |
| В середине | Часть текста уже есть | Уже читает ответ | Сохранить частичный ответ + обозначить ошибку |
| LLM | В любой момент | Может не понять, что случилось | Ошибка с причиной + retry |

### Принцип: частичный ответ сохраняется

Самый сложный случай: пользователь уже видит часть ответа. Нельзя просто очистить экран — потеряется контекст. Нужно показать то, что успело сгенерироваться, и обозначить ошибку.

```tsx
{message.error && (
  <div className="message-error">
    <span>Ошибка: {message.error.message}</span>
    <button onClick={() => retry(message.id)}>Повторить</button>
  </div>
)}
```

Retry переиспользует промпт пользователя и создаёт новый assistant-message взамен ошибочного. Пользователь видит, что модель успела сгенерировать, и может повторить запрос.

### Почему нельзя очищать экран

| Подход | Что чувствует пользователь |
|--------|----------------------------|
| Очистить всё и показать ошибку | «Мой вопрос и ответ исчезли» — потеря контекста, раздражение |
| Сохранить частичный ответ + ошибка | «Модель начала отвечать, что-то оборвалось» — понятно, что делать |
| Ошибка без retry | «Что дальше?» — тупик |

Принцип: **всегда давай путь дальше** — либо retry, либо новый запрос. Пользователь не должен оказываться в состоянии «ответ оборвался и непонятно, что делать».

## Когда стриминг нужен, а когда нет

| Сценарий | Стриминг | Почему |
|----------|----------|--------|
| Чат с моделью | ✅ Обязателен | 10 сек пустого экрана — катастрофа для UX |
| Автодополнение текста | ✅ | Восприятие мгновенного отклика |
| Генерация длинного документа | ✅ | Пользователь читает в процессе |
| Суммаризация короткого текста | ⚠️ | Ответ короткий — можно и целиком, но стриминг не повредит |
| Фоновая генерация без UI | ❌ | Пользователь не видит процесс |
| Извлечение данных/JSON на бэкенде | ❌ | Потребитель — код, а не человек |

Правило: **стриминг решает UX-проблему «пустого экрана во время генерации»**. Если у задачи нет этой проблемы (короткий ответ, фоновый процесс, потребитель — код) — стриминг не нужен.

## Чек-лист: как проверить свой чат

Пройдитесь по сценариям — каждый должен иметь поведение:

- [ ] Ответ появляется через курсор/skeleton сразу после отправки
- [ ] Кнопка «Отправить» превращается в «Стоп» во время генерации
- [ ] После нажатия «Стоп» генерация реально прекращается (нет дорасчёта хвоста)
- [ ] Ввод заблокирован с понятным плейсхолдером, но не сломан
- [ ] Автоскролл следует за потоком, когда пользователь внизу
- [ ] Автоскролл НЕ трогает пользователя, поднявшегося вверх
- [ ] Ошибка до стрима → обычный error state с retry
- [ ] Ошибка в середине → частичный ответ сохранён + кнопка retry
- [ ] Retry переиспользует исходный промпт
- [ ] После ошибки интерфейс возвращается в рабочее состояние (ввод разблокирован)

Этот чек-лист — та же спецификация, которую вы передаёте агенту или команде при разработке чата (см. [AI-фичи на фронте](./ai-features-frontend.md)).

## Case study: ошибка в середине генерации

Разберём реальный сценарий и все решения по ходу.

**Сценарий.** Пользователь задал сложный вопрос, модель начала отвечать, на 70% ответа произошёл rate limit.

**Шаг 1. Что видит пользователь.**

```
Модель: «Синхронизация состояния в React — это про то, когда UI должен
отражать данные из внешнего источника. Основные подходы:
1. Fetch на каждый рендер...
<ошибка: Rate limit exceeded>
```

Пользователь уже прочитал часть ответа. Очищать экран нельзя.

**Шаг 2. Что делает UI.**

```tsx
<div className="message partial">
  <p>{message.content}</p>  {/* 70% ответа осталось */}
  {message.error && (
    <div className="message-error">
      <span>Ошибка: {message.error.message}</span>
      <button onClick={() => retry(message.id)}>Повторить</button>
    </div>
  )}
</div>
```

**Шаг 3. Что происходит при retry.**

- Retry переиспользует исходный промпт пользователя
- SDK создаёт новый assistant-message взамен ошибочного
- Старый частичный ответ остаётся в истории как «оборванный» — контекст диалога не теряется

**Шаг 4. Что было бы без паттерна.**

| Без «частичного ответа» | С паттерном |
|--------------------------|-------------|
| Экран очищен, осталась только ошибка | 70% ответа на месте |
| Контекст вопроса потерян | Вопрос и часть ответа в истории |
| Пользователь переспрашивает то же | Один клик «Повторить» |
| Раздражение, ощущение сломанного продукта | Понятное состояние + путь дальше |

**Вывод кейса:** обработка ошибки в середине потока — это не «показать алерт», а сохранить контекст и дать пользователю путь дальше. Правило «частичный ответ сохраняется» превращает сбой в контролируемое состояние.

## Ключевые тезисы для интервью

- Streaming снижает **воспринимаемую** latency с полного времени генерации до TTFT (300–800 мс) — сам стриминг не ускоряет генерацию, он улучшает ощущение скорости.
- Техническую реализацию стриминга (парсинг SSE, AbortController, переподключение) берёт на себя SDK — Vercel AI SDK (`useChat`) даёт состояние, `stop()` и обработку ошибок из коробки.
- Индикация генерации — три уровня: курсор, skeleton до первого токена, статус-бар с кнопкой «Стоп».
- Кнопка «Стоп» обязательна: без прерывания сервер продолжает генерировать, расходуя токены и деньги; она же — контроль бюджета.
- Ошибка в середине потока — частичный ответ остаётся на экране, пользователь может повторить через retry; очищать экран нельзя — теряется контекст.
- Автоскролл учитывает позицию пользователя: если он отскроллил вверх для чтения — автоскролл не срабатывает.
- Ввод блокируется во время генерации с понятным плейсхолдером; очередь запросов усложняет сервер и редко нужна.
- Стриминг решает проблему «пустого экрана»: нужен для чатов и длинной генерации, не нужен для фоновых процессов и когда потребитель — код.

## Заключение

Streaming UI — мост между LLM API и пользовательским восприятием. Со стороны продукта: индикация генерации, кнопка «Стоп», автоскролл, обработка ошибок без потери контекста. Со стороны кода — готовое решение из SDK, а не рукописный парсер протокола.

Ключевые выводы:

- **Streaming снижает воспринимаемую latency** — содержимое то же, но пользователь получает отклик мгновенно.
- **SDK делает всю техническую работу** — состояние, прерывание, ошибки из коробки.
- **AbortController обязателен** — без него пользователь не может прервать генерацию, а сервер расходует токены впустую.
- **Ошибки в середине потока — нормальное состояние** — частичный ответ сохраняется, пользователь может повторить.

Проверить свой чат можно чек-листом из статьи: каждый сценарий (начало, стриминг, «Стоп», скролл, ошибка, retry) должен иметь предсказуемое поведение. Это и есть спецификация UX для чата, которую передают агенту или команде.
