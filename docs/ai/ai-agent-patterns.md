# Агентные паттерны

Предыдущие статьи показали, как один вызов LLM решает конкретную задачу: написать код, найти баг, сгенерировать тест. Но реальные задачи редко укладываются в один вызов — нужно собрать данные из разных источников, принять промежуточные решения, обработать ошибки, повторить при неудаче. Агентные паттерны — это архитектура, которая превращает модель из функции «запрос → ответ» в систему, способную действовать автономно. Эта статья — о том, как устроены агенты, какие паттерны существуют и когда они оправданы.

## Что такое агент и чем отличается от простого вызова

### Простой вызов: input → output

В предыдущих статьях мы работали с LLM как с функцией: приложение формирует промпт, отправляет модели, получает ответ, использует результат. Один вызов — один ответ. Приложение полностью контролирует поток: что отправить, когда отправить, что делать с результатом.

```ts
// Простой вызов: приложение — дирижёр, модель — инструмент
async function classifyBug(report: string): Promise<string> {
  const response = await client.messages.create({
    model: "claude-sonnet-4-6",
    messages: [{
      role: "user",
      content: `Классифицируй баг: ${report}. Ответь одним словом: ui | api | data | auth`,
    }],
  });
  return response.content[0].text.trim();
}
```

Здесь нет агента. Есть функция, которая вызывает модель и возвращает результат. Вся логика — в коде приложения.

### Агент: цикл «подумал → действовал → наблюдал»

Агент — это система, в которой модель сама определяет, что делать дальше. Она не просто отвечает на вопрос, а выбирает следующие действия на основе предыдущих результатов. Ключевое отличие: **модель принимает решения о потоке выполнения**.

```ts
// Агент: модель решает, какие инструменты вызвать и когда остановиться
async function agentLoop(task: string) {
  const messages: Message[] = [{ role: "user", content: task }];

  while (true) {
    const response = await client.messages.create({
      model: "claude-sonnet-4-6",
      tools: availableTools,
      messages,
    });

    // Модель решила дать текстовый ответ — задача выполнена
    if (response.stop_reason === "end_turn") {
      return response.content[0].text;
    }

    // Модель решила вызвать инструмент — выполняем и возвращаем результат
    if (response.stop_reason === "tool_use") {
      const toolCall = response.content.find(c => c.type === "tool_use");
      const result = await executeTool(toolCall.name, toolCall.input);
      messages.push(
        { role: "assistant", content: response.content },
        { role: "user", content: [{ type: "tool_result", content: result, tool_use_id: toolCall.id }] },
      );
    }
  }
}
```

Цикл продолжается, пока модель не решит, что задача выполнена. Это фундаментальное отличие от простого вызова: количество шагов неизвестно заранее, и модель сама определяет, когда остановиться.

### Три компонента агента

Любой LLM-агент состоит из трёх частей:

1. **Модель (мозг)** — принимает решения, рассуждает о промежуточных шагах, формулирует выводы
2. **Инструменты (руки)** — действия, которые агент может выполнить: поиск в базе данных, вызов API, чтение файла, выполнение кода
3. **Петля (сердце)** — цикл, который связывает модель и инструменты: мысль → действие → наблюдение → новая мысль

Без инструментов модель — просто чатбот. Без петли — просто вызов функции. Агент возникает на пересечении всех трёх.

## ReAct: Reasoning + Acting

### Идея

ReAct (Reasoning + Acting) — паттерн, предложенный Yao et al. (2022). Основная идея: модель чередует рассуждение (thought) и действие (action), наблюдая за результатом каждого действия (observation) перед тем, как сделать следующий шаг.

```
Thought: Нужно найти документацию по API авторизации, чтобы понять, 
         какой формат токенов используется.
Action: search_docs("API авторизации формат токенов")
Observation: [Найдена страница: "Токены доступа — JWT, формат: Bearer <token>"]

Thought: Теперь я знаю формат. Нужно проверить, как текущий код 
         обрабатывает истёкшие токены.
Action: read_file("src/auth/tokenHandler.ts")
Observation: [Содержимое файла: функция refreshToken проверяет exp claim...]

Thought: Вижу проблему — нет обработки случая, когда refresh token 
         тоже истёк. Нужно добавить проверку и редирект на логин.
Action: done("Обнаружена проблема: refreshToken не обрабатывает случай, 
              когда refresh token истёк. Нужно добавить проверку exp и 
              редирект на /login при ошибке.")
```

### Реализация

```ts
interface ReActStep {
  thought: string;
  action: { tool: string; input: Record<string, unknown> } | null;
}

async function reactLoop(
  task: string,
  tools: Tool[],
  maxSteps = 10,
): Promise<string> {
  const messages: Message[] = [
    {
      role: "system",
      content: `Решай задачу пошагово. Каждый шаг:
1. Thought: рассуждение о том, что нужно сделать и почему
2. Action: вызов инструмента (или finished, если задача решена)
3. Наблюдай за результатом и переходи к следующему шагу`,
    },
    { role: "user", content: task },
  ];

  for (let step = 0; step < maxSteps; step++) {
    const response = await client.messages.create({
      model: "claude-sonnet-4-6",
      tools,
      messages,
    });

    if (response.stop_reason === "end_turn") {
      return response.content[0].text;
    }

    const toolUse = response.content.find(c => c.type === "tool_use");
    if (!toolUse) break;

    const result = await executeTool(toolUse.name, toolUse.input);

    messages.push(
      { role: "assistant", content: response.content },
      {
        role: "user",
        content: [{
          type: "tool_result",
          content: JSON.stringify(result),
          tool_use_id: toolUse.id,
        }],
      },
    );
  }

  throw new Error("Agent exceeded maximum steps");
}
```

### Почему ReAct работает лучше прямого вызова

Прямой вызов модели на сложной задаче даёт плохой результат по двум причинам:

1. **Модель не знает актуального состояния мира**. Она не может «посмотреть» базу данных, прочитать файл, проверить API. Без наблюдения за реальным состоянием модель галлюцинирует — придумывает данные, которых не существует.

2. **Один вывод — одна попытка рассуждения**. Если модель ошиблась в середине цепочки, она продолжает от ошибочного предположения. ReAct позволяет «сбросить» ошибку на каждом шаге: наблюдение за результатом действия даёт новую точку опоры.

```ts
// Без ReAct: модель галлюцинирует содержимое файла
const badPrompt = `В файле src/config.ts есть переменная API_URL? 
Если да, какое у неё значение?`;
// Модель ответит уверенно, но может выдумать значение

// С ReAct: модель читает файл и видит реальное содержимое
// Thought: Нужно проверить содержимое файла
// Action: read_file("src/config.ts")
// Observation: [содержимое файла]
// Thought: Вижу, API_URL = "https://api.example.com"
```

### Ограничение шагов

Без ограничения агент может зациклиться: повторять одни и те же действия, бесконечно уточнять, «ходить по кругу». Ограничение шагов — обязательный элемент:

```ts
// Защита от зацикливания
const MAX_STEPS = 10;
const MAX_TOKENS_BUDGET = 50_000;

for (let step = 0; step < MAX_STEPS; step++) {
  // ... шаг агента

  if (totalTokensUsed > MAX_TOKENS_BUDGET) {
    return `Задача не решена за ${MAX_STEPS} шагов. Промежуточный результат: ${lastThought}`;
  }
}
```

## Plan-and-execute

### Идея

ReAct принимает решения пошагово: каждый шаг — локальное решение. Для простых задач это работает. Для сложных — может привести к тому, что агент «заблудится»: будет выполнять нерелевантные действия, упустит важные шаги, не сможет вернуться к плану.

Plan-and-execute разделяет процесс на две фазы:

1. **Планирование**: модель составляет план — список шагов для решения задачи
2. **Выполнение**: модель (или другой агент) последовательно выполняет каждый шаг плана

```ts
// Фаза 1: планирование
async function createPlan(task: string): Promise<Step[]> {
  const response = await client.messages.create({
    model: "claude-sonnet-4-6",
    tools: [{
      name: "create_plan",
      description: "Создать план выполнения задачи",
      input_schema: {
        type: "object",
        properties: {
          steps: {
            type: "array",
            items: {
              type: "object",
              properties: {
                description: { type: "string" },
                tool: { type: "string" },
                dependsOn: { type: "array", items: { type: "number" } },
              },
            },
          },
        },
      },
    }],
    messages: [{
      role: "user",
      content: `Составь план выполнения задачи. Не выполняй — только спланируй.
Задача: ${task}`,
    }],
  });

  return response.content[0].input.steps;
}

// Фаза 2: выполнение
async function executePlan(plan: Step[], task: string): Promise<string> {
  const results: string[] = [];

  for (const step of plan) {
    const context = results.map((r, i) => `Шаг ${i + 1}: ${r}`).join("\n");

    const result = await reactLoop(
      `Выполни шаг плана: ${step.description}\n\nКонтекст предыдущих шагов:\n${context}`,
      availableTools,
    );

    results.push(result);
  }

  // Финальная агрегация
  return await synthesize(task, results);
}
```

### ReAct vs Plan-and-execute

| Критерий | ReAct | Plan-and-execute |
|----------|-------|------------------|
| Принятие решений | Каждый шаг — локальное решение | План вначале, потом выполнение |
| Гибкость | Высокая: может изменить направление на лету | Низкая: план может устареть |
| Сложные задачи | Может «заблудиться» | Структурированный подход |
| Стоимость | Меньше вызовов на простые задачи | Дополнительный вызов на планирование |
| Перепланирование | Не предусмотрено | Можно добавить re-planning |

### Перепланирование

План, составленный вначале, может устареть: данные изменились, обнаружены непредвиденные проблемы, некоторые шаги оказались лишними. Plan-and-execute с перепланированием добавляет третью фазу:

```ts
async function planAndReplan(task: string) {
  let plan = await createPlan(task);
  const results: string[] = [];

  for (let i = 0; i < plan.length; i++) {
    const result = await executeStep(plan[i], results);
    results.push(result);

    // Каждые 3 шага — проверяем актуальность плана
    if ((i + 1) % 3 === 0 && i < plan.length - 1) {
      const remaining = plan.slice(i + 1);
      const needsReplan = await assessPlan(task, remaining, results);

      if (needsReplan) {
        plan = await replan(task, results, remaining);
      }
    }
  }

  return synthesize(task, results);
}
```

Перепланирование — баланс между структурированностью и гибкостью. Без него агент слепо следует изначальному плану. С ним — адаптируется к реальности, но тратит дополнительные токены на переоценку.

## Tool use / Function calling

### Что такое tool use

Tool use (function calling) — механизм, при котором модель не генерирует свободный текст, а выбирает вызов заранее определённой функции со структурированными аргументами. Это мост между «рассуждением» модели и «действием» в агентной петле.

```ts
// Определение инструментов
const tools: Tool[] = [
  {
    name: "search_codebase",
    description: "Поиск по кодовой базе. Возвращает релевантные фрагменты кода.",
    input_schema: {
      type: "object",
      properties: {
        query: { type: "string", description: "Поисковый запрос" },
        file_pattern: { type: "string", description: "Фильтр файлов, например *.tsx" },
      },
      required: ["query"],
    },
  },
  {
    name: "read_file",
    description: "Прочитать содержимое файла по пути",
    input_schema: {
      type: "object",
      properties: {
        path: { type: "string", description: "Путь к файлу" },
      },
      required: ["path"],
    },
  },
  {
    name: "run_command",
    description: "Выполнить shell-команду и вернуть вывод",
    input_schema: {
      type: "object",
      properties: {
        command: { type: "string", description: "Команда для выполнения" },
      },
      required: ["command"],
    },
  },
];
```

### Как модель выбирает инструменты

Модель не «вызывает» инструменты напрямую. Она генерирует специальный токен `tool_use`, который содержит имя инструмента и аргументы. Приложение перехватывает этот токен, выполняет реальную функцию и возвращает результат как `tool_result`.

```ts
// Модель решает: "Мне нужно прочитать файл, чтобы ответить на вопрос"
// Генерирует: tool_use { name: "read_file", input: { path: "src/auth.ts" } }
// Приложение: читает файл, возвращает содержимое
// Модель: получает содержимое, продолжает рассуждение

// Важный нюанс: модель НЕ выполняет код сама.
// Она только ЗАПРАШИВАЕТ выполнение. Приложение решает, выполнять ли.
```

Это разделение — ключевой принцип безопасности. Модель предлагает действие, приложение решает, выполнить ли его. Мы вернёмся к этому в статье о безопасности.

### Проектирование инструментов

Качество инструментов определяет качество работы агента. Плохо описанный инструмент — модель его не использует или использует неправильно.

```ts
// Плохо: неясное описание, модель не поймёт, когда использовать
{
  name: "search",
  description: "Ищет что-нибудь",
  input_schema: { type: "object", properties: { q: { type: "string" } } },
}

// Хорошо: конкретное описание, понятные параметры, указан формат результата
{
  name: "search_codebase",
  description: `Полнотекстовый поиск по кодовой базе. 
Возвращает до 10 релевантных фрагментов с путями файлов и номерами строк.
Используй для поиска определений функций, импортов, типов.
Не используй для чтения всего файла — для этого есть read_file.`,
  input_schema: {
    type: "object",
    properties: {
      query: {
        type: "string",
        description: "Поисковый запрос: имя функции, тип, ключевое слово",
      },
      file_pattern: {
        type: "string",
        description: "Фильтр по расширению: *.ts, *.tsx, *.css. Опусти для поиска по всем файлам.",
      },
    },
    required: ["query"],
  },
}
```

### Гранулярность инструментов

Слишком крупные инструменты превращают агента в «чёрный ящик» — модель не контролирует промежуточные шаги. Слишком мелкие — перегружают модель решениями о последовательности вызовов.

```ts
// Слишком крупный: модель не видит промежуточных шагов
{
  name: "deploy",
  description: "Собрать, протестировать и задеплоить приложение",
}

// Слишком мелкие: модель тратит шаги на координацию
{ name: "npm_install", description: "Выполнить npm install" }
{ name: "npm_build", description: "Выполнить npm run build" }
{ name: "npm_test", description: "Выполнить npm test" }
{ name: "git_push", description: "Выполнить git push" }
{ name: "deploy_prod", description: "Задеплоить на продакшн" }

// Оптимально: каждый инструмент — законченное действие с понятным результатом
{ name: "run_tests", description: "Запустить тесты и вернуть результаты" }
{ name: "build", description: "Собрать проект и вернуть статус" }
{ name: "deploy", description: "Задеплоить собранную версию" }
```

### Обработка результатов инструментов

Результат инструмента — вход для следующего шага рассуждения. Формат результата влияет на качество рассуждения.

```ts
// Плохо: сырой вывод на 10000 строк — модель потеряется
const result = execSync("npm test 2>&1").toString();

// Хорошо: структурированный результат с контекстом
function formatTestResult(raw: string): string {
  const summary = extractTestSummary(raw);
  const failures = extractFailures(raw);

  return `
Тесты: ${summary.passed}/${summary.total} пройдено
Время: ${summary.duration}

Проваленные тесты:
${failures.map(f => `  ${f.name}: ${f.message} (${f.file}:${f.line})`).join("\n")}
  `.trim();
}
```

## Multi-agent системы

### Зачем несколько агентов

Один агент — одна модель, один набор инструментов, одна петля. Для многих задач этого достаточно. Но сложные задачи требуют разных компетенций, разных наборов инструментов и разных стратегий. Multi-agent системы разделяют задачу между несколькими агентами.

### Паттерн: supervisor (руководитель)

Один агент координирует работу других:

```ts
async function supervisorPattern(task: string) {
  const supervisorPrompt = `Ты — координатор. У тебя есть три специалиста:
- researcher: ищет информацию в документации и кодовой базе
- coder: пишет и модифицирует код
- reviewer: проверяет код на ошибки и соответствие стандартам

Для каждого шага укажи, какой специалист должен работать и что он должен сделать.
Когда задача решена — ответь "done" с итоговым описанием.`;

  return await agentLoop(task, [
    { name: "delegate_to_researcher", handler: researcherAgent },
    { name: "delegate_to_coder", handler: coderAgent },
    { name: "delegate_to_reviewer", handler: reviewerAgent },
  ], supervisorPrompt);
}
```

Каждый «специалист» — отдельный агент со своим системным промптом, набором инструментов и стратегией. Supervisor решает, кому делегировать, и агрегирует результаты.

### Паттерн: pipeline (конвейер)

Агенты работают последовательно, каждый обрабатывает свой аспект задачи:

```ts
async function pipelinePattern(task: string) {
  // Агент 1: анализ задачи
  const analysis = await analystAgent(task);

  // Агент 2: реализация на основе анализа
  const implementation = await coderAgent(analysis);

  // Агент 3: проверка реализации
  const review = await reviewerAgent(implementation);

  // Агент 4: если есть замечания — исправление
  if (review.hasIssues) {
    return await coderAgent(review.feedback);
  }

  return implementation;
}
```

Pipeline предсказуем: порядок фиксирован, каждый агент знает свой вход и выход. Это проще для отладки, чем supervisor.

### Паттерн: debate (дебаты)

Несколько агентов независимо решают задачу, затем сравнивают решения:

```ts
async function debatePattern(task: string, agentCount = 3) {
  // Параллельное независимое решение
  const solutions = await Promise.all(
    Array.from({ length: agentCount }, (_, i) =>
      agentLoop(`Реши задачу: ${task}`, tools, `Агент ${i + 1}`)
    )
  );

  // Агент-судья выбирает лучшее решение
  const judge = await client.messages.create({
    model: "claude-sonnet-4-6",
    messages: [{
      role: "user",
      content: `Три решения задачи. Выбери лучшее, объясни почему.

Задача: ${task}

${solutions.map((s, i) => `Решение ${i + 1}:\n${s}`).join("\n\n")}`,
    }],
  });

  return judge.content[0].text;
}
```

Debate повышает качество за счёт «конкуренции» — разные агенты находят разные проблемы и решения. Но стоимость растёт линейно с количеством агентов.

### Риски multi-agent систем

**Каскадные ошибки.** Ошибка одного агента передаётся следующему. Если analystAgent неправильно понял задачу, coderAgent реализует не то, а reviewerAgent не заметит проблему, потому что проверяет не то.

```ts
// Каскад ошибок:
// 1. Analyst: "Задача — добавить кнопку удаления" (неверно: задача — добавить кнопку архивации)
// 2. Coder: реализует удаление
// 3. Reviewer: проверяет удаление — всё ок, код корректный
// Результат: реализована не та фича, но все агенты «довольны»
```

**Стоимость.** Каждый агент — дополнительные вызовы модели. Supervisor + 3 специалиста + переделка = 10+ вызовов на одну задачу.

**Недетерминизм.** Чем больше агентов, тем больше точек недетерминизма. Один агент с temperature > 0 даёт вариативность. Три агента — экспоненциально больше комбинаций.

**Отладка.** Когда pipeline из 4 агентов даёт неправильный результат, нужно понять, какой агент ошибся и почему. Логирование каждого шага — обязательное требование.

```ts
// Обязательное логирование для multi-agent
async function tracedAgent(name: string, task: string, tools: Tool[]) {
  console.log(`[${name}] Начало: ${task.slice(0, 100)}`);

  const result = await agentLoop(task, tools);

  console.log(`[${name}] Завершено. Шагов: ${result.steps}, токенов: ${result.tokens}`);
  console.log(`[${name}] Результат: ${result.output.slice(0, 200)}`);

  return result;
}
```

## Когда агентный подход оправдан

### Агент нужен

Агентный подход оправдан, когда задача соответствует хотя бы одному из критериев:

1. **Количество шагов неизвестно заранее**. Задача требует «смотреть и решать»: найти баг → проверить гипотезу → если не подтвердилась, попробовать другую. Невозможно заранее знать, сколько шагов понадобится.

2. **Нужны внешние данные**. Модель не знает содержимого вашей базы данных, состояния API, содержимого файлов. Агент может получить эти данные через инструменты.

3. **Задача naturally decomposable**. Задача естественно разбивается на независимые этапы: «найди все использования этой функции → проверь каждое → исправь проблемные».

```ts
// Пример, где агент оправдан: автоматический дебаггинг
// Количество шагов неизвестно, нужны внешние данные (логи, код), 
// задача naturally decomposable
const debugAgent = {
  tools: [
    { name: "read_logs", description: "Прочитать логи ошибок" },
    { name: "search_codebase", description: "Найти код по стеку" },
    { name: "read_file", description: "Прочитать файл" },
    { name: "run_test", description: "Запустить конкретный тест" },
  ],
  task: "Тест auth.test.ts падает. Найди причину и предложи исправление.",
};
```

### Агент избыточен

Агентный подход — overkill, когда:

1. **Задача решается одним вызовом**. Классификация, извлечение данных, генерация по шаблону — всё это не требует петли.

2. **Детерминированный pipeline**. Если шаги известны заранее и не зависят от промежуточных результатов — пишите обычный код, а не агента.

3. **Высокая цена ошибки + нет human-in-the-loop**. Если ошибка агента стоит дорого (удаление данных, финансовые операции), а человек не проверяет каждый шаг — агент опасен.

```ts
// Избыточно: задача решается одним вызовом
const classifier = await client.messages.create({
  messages: [{ role: "user", content: `Классифицируй: ${text}` }],
});

// Избыточно: шаги известны заранее — это обычный код, не агент
async function processOrder(order: Order) {
  const validated = validateOrder(order);     // шаг 1 — детерминированный
  const charged = await chargePayment(validated); // шаг 2 — один вызов
  await sendConfirmation(charged);             // шаг 3 — один вызов
}
```

### Критерий принятия решения

Простое правило: если вы можете написать задачу как фиксированный pipeline с известным количеством шагов — не делайте агента. Если количество шагов зависит от промежуточных результатов — агент оправдан.

```
Фиксированный pipeline:     Шаг 1 → Шаг 2 → Шаг 3 → Результат
                            (известно заранее, сколько шагов)

Агентная петля:             Шаг 1 → результат → решить → Шаг 2a или 2b → ...
                            (количество и выбор шагов зависят от данных)
```

## Ключевые тезисы для интервью

- LLM-агент — система с петлёй «модель → инструмент → наблюдение → модель», в которой модель принимает решения о потоке выполнения; отличается от простого вызова тем, что количество шагов и их содержание определяются моделью, а не кодом приложения.
- ReAct (Reasoning + Acting) — паттерн, в котором модель чередует рассуждение (thought), действие (action) и наблюдение (observation); повышает точность за счёт «привязки» рассуждения к реальному состоянию мира через инструменты.
- Plan-and-execute разделяет задачу на фазы планирования и выполнения; план может устаревать, поэтому добавляют перепланирование — переоценку оставшихся шагов после нескольких выполненных.
- Tool use (function calling) — механизм, при котором модель генерирует структурированный запрос на вызов инструмента, а приложение выполняет реальный вызов и возвращает результат; модель не выполняет код сама, только запрашивает выполнение.
- Multi-agent системы: supervisor координирует специалистов, pipeline обрабатывает этапы последовательно, debate сравнивает независимые решения; основные риски — каскадные ошибки, стоимость, недетерминизм, сложность отладки.
- Агентный подход оправдан, когда количество шагов неизвестно заранее, нужны внешние данные или задача naturally decomposable; избыточен для фиксированных pipeline и задач, решаемых одним вызовом.
- Ограничение шагов и бюджета токенов — обязательный элемент агентной петли; без них агент может зациклиться или потратить неограниченное количество ресурсов.
- Качество инструментов определяет качество работы агента: описание инструмента должно объяснять, когда его использовать, а когда — нет; гранулярность — баланс между контролем и сложностью координации.

## Заключение

Агентные паттерны — эволюция от «модель как функция» к «модель как принятия решений»:

- **Агент** — цикл рассуждения и действия с инструментами; модель определяет, что делать дальше, на основе наблюдений.
- **ReAct** — пошаговое рассуждение с действиями; хорошо для задач с непредсказуемым количеством шагов.
- **Plan-and-execute** — планирование впереди, выполнение по плану; лучше для сложных многоэтапных задач, с перепланированием для адаптации.
- **Tool use** — мост между рассуждением и действием; модель запрашивает, приложение выполняет.
- **Multi-agent** — разделение компетенций между агентами; supervisor, pipeline, debate — каждый паттерн для своего класса задач.
- **Ограничения** — обязательны: лимит шагов, бюджет токенов, логирование каждого шага.

Агент — не универсальное решение. Если задача решается фиксированным pipeline — пишите pipeline. Агент нужен там, где количество и характер шагов зависят от промежуточных результатов.
