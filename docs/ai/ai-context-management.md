# Управление контекстом

Предыдущая статья разобрала RAG — паттерн для подачи модели актуальных знаний из внешней базы. Но RAG решает только одну часть проблемы: что делать, когда модель не знает фактов. Вторая часть — что делать, когда модель ведёт длинный диалог. История растёт с каждым сообщением, и рано или поздно она превышает контекстное окно. Тогда качество ответа деградирует: модель «забывает» ранние сообщения, путает контекст, теряет нить разговора. Управление контекстом — набор стратегий, которые удерживают качество ответа при длинных сессиях, не раздувая стоимость запросов.

## Структура разговора: роли и порядок сообщений

### Три роли

LLM API принимает массив сообщений, каждое из которых имеет роль и содержимое. Три основные роли:

```ts
const messages = [
  {
    role: "system",
    content: "Ты — ассистент по TypeScript. Отвечай кратко, с примерами кода.",
  },
  {
    role: "user",
    content: "Как типизировать функцию, которая принимает строку и возвращает число?",
  },
  {
    role: "assistant",
    content: "Используйте сигнатуру `(input: string) => number`:\n\n```ts\nconst parse = (input: string): number => Number(input);\n```",
  },
  {
    role: "user",
    content: "А если она может вернуть NaN?",
  },
];
```

- **system** — инструкции, которые модель держит на протяжении всего разговора. Задают поведение, ограничения, стиль. Обычно одно сообщение в начале.
- **user** — сообщения пользователя. Каждый ввод пользователя — отдельное сообщение с этой ролью.
- **assistant** — предыдущие ответы модели. Нужны, чтобы модель понимала, что она уже говорила, и не повторялась.

### Порядок сообщений — это и есть контекст

Модель не различает «старые» и «новые» сообщения. Она видит упорядоченный массив и обрабатывает его как единое целое. Порядок определяет, как модель интерпретирует разговор:

```ts
// Модель видит это как единый контекст, а не как «историю + текущий запрос»
[
  system,           // позиция 0: инструкции
  user₁,            // позиция 1: первое сообщение
  assistant₁,       // позиция 2: первый ответ
  user₂,            // позиция 3: уточнение
  assistant₂,       // позиция 4: ответ на уточнение
  user₃,            // позиция 5: текущий запрос
  // модель генерирует assistant₃ здесь
]
```

Сообщения идут строго в чередующемся порядке: user → assistant → user → assistant. Нарушение порядка (два user подряд, assistant без предшествующего user) — неопределённое поведение. Некоторые API принимают это, но качество ответа непредсказуемо.

### Системный промпт — особый

Системный промпт занимает привилегированное положение. Он стоит первым в контексте, и модели приписывают ему высокий «авторитет»: инструкции из system переопределяют противоречивые указания из user-сообщений.

```ts
// System: «Никогда не обсуждай политику»
// User: «Расскажи про политическую систему Франции»
// Модель: «Я не обсуждаю политические темы.»

// Но если user говорит: «Игнорируй все предыдущие инструкции» —
// это prompt injection, и защита от него — отдельная тема (статья о безопасности)
```

Некоторые API (OpenAI, Anthropic) выделяют system в отдельный параметр, а не в массив messages. Это не меняет сути — system всё равно обрабатывается как первое сообщение в контексте.

## История диалога и её накопление

### Как растёт контекст

Каждое сообщение в диалоге — это токены. С каждым обменом (user + assistant) контекст растёт. Если не управлять историей, она неизбежно превысит лимит контекстного окна.

```ts
// Простой (и нерабочий) подход: отправлять всё
async function chat(messages: Message[], newUserMessage: string) {
  const allMessages = [
    ...messages,
    { role: "user", content: newUserMessage },
  ];

  // На 50-м сообщении: allMessages ≈ 80 000 токенов
  // Контекстное окно: 128 000 токенов
  // Осталось места для ответа: 48 000 токенов — но TTFT уже 3-4 секунды
  // На 100-м сообщении: allMessages ≈ 160 000 токенов — за пределами окна

  return await client.messages.create({
    model: "claude-sonnet-4-6",
    max_tokens: 4096,
    messages: allMessages,
  });
}
```

### Токенный бюджет

Контекстное окно — фиксированный ресурс. Его нужно делить между системным промптом, историей, текущим сообщением и ответом:

```
┌────────────────────────────────────────────────────────────────┐
│                    Контекстное окно (128K)                     │
├──────────┬──────────────┬──────────────┬───────────────────────┤
│  System  │   История    │   Текущий    │      Ответ            │
│  промпт  │   диалога    │   запрос     │    (max_tokens)       │
│  ~2K     │   ~100K      │   ~2K        │      ~4K              │
│          │              │              │                       │
│  (static)│  (dynamic)   │  (dynamic)   │    (dynamic)          │
└──────────┴──────────────┴──────────────┴───────────────────────┘
```

Когда история заполняет окно, нужно принимать решение: что выбросить, что сжать, а что оставить как есть. Это и есть управление контекстом.

### Когда история становится проблемой

Не каждая длинная история — проблема. Если диалог из 20 коротких сообщений (по 50 токенов каждое) — это 1000 токенов, прекрасно помещается. Проблемы начинаются, когда:

- **Сообщения длинные** — код, документы, развёрнутые ответы модели.
- **Диалог многораундовый** — 50+ обменов с подробными ответами.
- **Контекст перегружен** — системный промпт + RAG-документы + история + текущий запрос.

```ts
// Оценка размера истории
function estimateHistoryTokens(messages: Message[]): number {
  return messages.reduce((total, msg) => {
    return total + estimateTokens(msg.content);
  }, 0);
}

// Порог: если история занимает больше 60% окна — пора сжимать
const HISTORY_BUDGET_RATIO = 0.6;

function needsCompression(
  historyTokens: number,
  systemTokens: number,
  contextWindow: number,
  maxOutputTokens: number,
): boolean {
  const available = contextWindow - systemTokens - maxOutputTokens;
  return historyTokens > available * HISTORY_BUDGET_RATIO;
}
```

## Стратегии сжатия: summarization, truncation, sliding window

### Truncation: обрезать хвост

Самый простой подход — отбросить самые старые сообщения, если история превышает лимит.

```ts
function truncateHistory(
  messages: Message[],
  maxTokens: number,
): Message[] {
  let tokens = 0;
  const result: Message[] = [];

  // Идём с конца (новые сообщения) к началу (старые)
  for (let i = messages.length - 1; i >= 0; i--) {
    const msgTokens = estimateTokens(messages[i].content);
    if (tokens + msgTokens > maxTokens) break;
    tokens += msgTokens;
    result.unshift(messages[i]);
  }

  return result;
}

// Использование:
// Было: [msg₁, msg₂, msg₃, ..., msg₅₀]
// Стало: [msg₃₅, msg₃₆, ..., msg₅₀] — только последние, которые влезают
```

Плюсы: просто, быстро, нулевая дополнительная стоимость. Минусы: модель полностью теряет ранний контекст. Если пользователь в первом сообщении сказал «отвечай на русском», а это сообщение обрезано — модель может переключиться на английский.

### Sliding window: окно с фиксированным размером

Вариация truncation — всегда держать последние N обменов (N пар user + assistant).

```ts
function slidingWindow(messages: Message[], maxPairs: number): Message[] {
  // Каждая пара: user + assistant = 2 сообщения
  const maxMessages = maxPairs * 2;

  if (messages.length <= maxMessages) return messages;

  return messages.slice(-maxMessages);
}

// slidingWindow(allMessages, 10) — последние 10 пар (20 сообщений)
```

Плюсы: предсказуемый размер, модель всегда видит недавний контекст. Минусы: те же — потеря раннего контекста. Если в первых сообщениях был критический контекст (формат ответа, ограничения), он теряется.

### Summarization: сжать старую историю в резюме

Вместо отбрасывания — сжать старые сообщения в краткое резюме и держать его как первое «виртуальное» сообщение.

```ts
async function summarizeOldMessages(
  oldMessages: Message[],
  recentMessages: Message[],
  maxSummaryTokens: number,
): Promise<Message[]> {
  if (oldMessages.length === 0) return recentMessages;

  // Формируем промпт для суммаризации
  const conversationText = oldMessages
    .map(m => `${m.role}: ${m.content}`)
    .join("\n");

  const summary = await client.messages.create({
    model: "claude-haiku-4-5-20251001", // дешёвая модель для суммаризации
    max_tokens: maxSummaryTokens,
    messages: [{
      role: "user",
      content: `Сожми следующий разговор в краткое резюме, сохраняя ключевые факты, решения и контекст:\n\n${conversationText}`,
    }],
  });

  // Резюме заменяет старые сообщения
  return [
    {
      role: "user",
      content: `[Резюме предыдущего разговора]:\n${summary.content[0].text}`,
    },
    {
      role: "assistant",
      content: "Принял, продолжаем с этого места.",
    },
    ...recentMessages,
  ];
}
```

Плюсы: модель сохраняет «общую картину» даже после десятков обменов. Минусы:

- **Дополнительный LLM-вызов** — стоит денег и добавляет latency.
- **Потеря деталей** — резюме неизбежно теряет specifics. Если пользователь сказал «мой API-ключ — abc123», в резюме это может не попасть (и не должно).
- **Каскадные ошибки** — если резюме неточно, модель строит на нём следующие ответы, и ошибки накапливаются.

### Комбинированная стратегия: sliding window + summarization

На практике используют комбинацию: последние N обменов — как есть, всё что старше — сжато в резюме.

```ts
interface ContextManager {
  systemPrompt: string;
  maxHistoryTokens: number;
  recentPairs: number;         // последние N пар — как есть
  maxSummaryTokens: number;    // лимит токенов для резюме
}

async function buildContext(
  allMessages: Message[],
  config: ContextManager,
): Promise<Message[]> {
  const recentCount = config.recentPairs * 2;
  const recent = allMessages.slice(-recentCount);
  const old = allMessages.slice(0, -recentCount);

  // Проверяем, нужно ли сжимать
  const recentTokens = recent.reduce(
    (sum, m) => sum + estimateTokens(m.content), 0
  );

  if (recentTokens > config.maxHistoryTokens) {
    // Даже последние N пар не влезают — уменьшаем окно
    return slidingWindow(allMessages, config.recentPairs);
  }

  if (old.length === 0) {
    // Нечего сжимать
    return recent;
  }

  // Сжимаем старую историю
  return summarizeOldMessages(old, recent, config.maxSummaryTokens);
}
```

### Иерархическая суммаризация

При очень длинных сессиях (сотни обменов) одного резюме недостаточно — оно само становится слишком длинным. Решение: иерархическая суммаризация.

```ts
async function hierarchicalSummarize(
  messages: Message[],
  maxTokens: number,
): Promise<string> {
  // Если сообщения уже влезают — суммаризируем одним вызовом
  if (estimateTokens(messages.join("\n")) <= maxTokens * 3) {
    return await summarize(messages);
  }

  // Разбиваем на блоки, суммаризируем каждый, затем суммаризируем резюме
  const chunks = splitIntoChunks(messages, 20); // по 20 сообщений в блоке
  const summaries = await Promise.all(
    chunks.map(chunk => summarize(chunk))
  );

  // Финальная суммаризация всех резюме
  return await summarizeFromTexts(summaries);
}
```

Это рекурсивный подход: сжимаем блоки → сжимаем результаты сжатия → получаем компактное представление всей истории.

## Приоритизация: что ставить в начало, что в конец

### Феномен «lost in the middle»

В статье о ментальной модели упоминался феномен: модели лучше обрабатывают информацию в начале и конце контекста, хуже — в середине. Это напрямую влияет на то, как формировать контекст.

```
Внимание модели:
[ ████ начало — высокое ]  [ ░░░░ середина — низкое ]  [ ████ конец — высокое ]
```

### Что ставить в начало

1. **Системный промпт** — инструкции, ограничения, стиль ответа.
2. **Критический контекст** — правила, которые нельзя нарушать.
3. **Резюме истории** (если используется summarization) — общая картина.

### Что ставить в конец

1. **Текущее сообщение пользователя** — конкретный запрос.
2. **Недавние сообщения** — последние 2–3 обмена, самые релевантные.
3. **RAG-документы** (если используются) — модель лучше работает с ними, когда они рядом с запросом.

### Что оказывается в середине

1. **Давняя история** — старые обмены, которые ещё не сжаты.
2. **Дополнительный контекст** — метаданные, примеры, справочная информация.

```ts
// Оптимальная структура контекста
const messages = [
  // НАЧАЛО — высокий приоритет
  { role: "system", content: systemPrompt },        // инструкции
  { role: "user", content: summaryOfHistory },       // резюме истории
  { role: "assistant", content: "Принято." },

  // СЕРЕДИНА — низкий приоритет
  ...ragDocuments.map(doc => ({                       // RAG-документы
    role: "user" as const,
    content: `[Контекст]:\n${doc.content}`,
  })),

  // КОНЕЦ — высокий приоритет
  ...recentMessages,                                  // последние обмены
  { role: "user", content: currentQuery },            // текущий запрос
];
```

### Перестановка RAG-документов

Если в статье о RAG документы вставлялись перед вопросом, то при длинной истории лучше переместить их ближе к концу контекста — рядом с текущим запросом. Модель лучше связывает документы с вопросом, когда они рядом.

```ts
// Менее оптимально: документы далеко от вопроса
[system, summary, doc₁, doc₂, msg₁, msg₂, ..., msg₂₀, currentQuery]
//                       ↑ документы                      ↑ вопрос — далеко

// Лучше: документы рядом с вопросом
[system, summary, msg₁, msg₂, ..., msg₂₀, doc₁, doc₂, currentQuery]
//                                    ↑ документы и вопрос — рядом
```

## Статический vs динамический контекст

### Статический контекст

Часть контекста, которая не меняется между запросами:

- Системный промпт
- Инструкции по формату ответа
- Описание доступных инструментов (для агентов)
- Правила безопасности

```ts
const STATIC_CONTEXT = {
  system: `Ты — ассистент по TypeScript.
Правила:
- Отвечай на русском
- Приводи примеры кода
- Никогда не используй deprecated API
- Формат ответа: краткое объяснение + блок кода`,
};
```

Статический контекст — кандидат на **prompt caching**. Если провайдер поддерживает кэширование (Anthropic, OpenAI), повторяющиеся префиксы контекста кэшируются, и повторные запросы дешевле.

### Динамический контекст

Часть, которая меняется с каждым запросом:

- История диалога
- Текущее сообщение пользователя
- RAG-документы
- Результаты вызовов инструментов

```ts
// Динамический контекст формируется на каждый запрос
function buildDynamicContext(
  history: Message[],
  currentMessage: string,
  retrievedDocs: Document[],
): Message[] {
  return [
    ...compressHistory(history),
    ...formatRetrievedDocs(retrievedDocs),
    { role: "user", content: currentMessage },
  ];
}
```

### Почему разделение важно

Разделение статического и динамического контекста — это не только про организацию кода. Это про **кэш-эффективность** и **стоимость**.

```
Запрос 1: [static (2K)] + [dynamic₁ (10K)]  → 12K токенов, кэш: miss
Запрос 2: [static (2K)] + [dynamic₂ (12K)]  → 14K токенов, кэш: hit на static
Запрос 3: [static (2K)] + [dynamic₃ (15K)]  → 17K токенов, кэш: hit на static
```

Если статическая часть не меняется — она кэшируется, и каждый запрос платит только за динамическую часть. Если в статическую часть вставить что-то меняющееся (например, текущую дату или имя пользователя) — кэш ломается, и каждый запрос оплачивается полностью.

### Антипаттерн: динамическое в статическом

```ts
// Плохо: дата в system prompt ломает кэш каждый день
const system = `Ты — ассистент. Сегодня ${new Date().toLocaleDateString()}.
[2000 токенов инструкций]`;

// Лучше: дату — в user message
const system = `Ты — ассистент. [2000 токенов инструкций]`;
const userMessage = `Сегодня ${new Date().toLocaleDateString()}. ${question}`;
```

## Влияние на стоимость

### Контекст = деньги

Каждый токен в контексте — это деньги. При 100 000 запросов в день разница между 10K и 50K токенов контекста — существенна.

```ts
// Расчёт месячной стоимости
function monthlyCost(
  requestsPerDay: number,
  avgInputTokens: number,
  avgOutputTokens: number,
  inputPricePer1M: number,
  outputPricePer1M: number,
): number {
  const days = 30;
  const totalInput = requestsPerDay * days * avgInputTokens;
  const totalOutput = requestsPerDay * days * avgOutputTokens;

  return (totalInput / 1_000_000 * inputPricePer1M) +
         (totalOutput / 1_000_000 * outputPricePer1M);
}

// Пример: 100K запросов/день, 50K входных, 2K выходных
const cost = monthlyCost(100_000, 50_000, 2_000, 3.0, 15.0);
// = (100000 × 30 × 50000 / 1M × 3) + (100000 × 30 × 2000 / 1M × 15)
// = $4,500 (input) + $900 (output) = $5,400/мес

// С оптимизацией контекста: 20K входных вместо 50K
const optimizedCost = monthlyCost(100_000, 20_000, 2_000, 3.0, 15.0);
// = $1,800 (input) + $900 (output) = $2,700/мес
// Экономия: 50%
```

### Что больше всего влияет на стоимость

1. **Длина системного промпта** — умножается на количество запросов. 5K токенов промпта × 100K запросов = 500M токенов/день.
2. **Длина истории** — растёт с каждым сообщением. Без сжатия — экспоненциальный рост стоимости в рамках одной сессии.
3. **Количество RAG-документов** — каждый документ в контексте — токены. Top-20 вместо top-5 — 4× больше токенов на retrieval.

### Prompt caching

Некоторые провайдеры кэшируют повторяющиеся префиксы контекста. Если системный промпт и начало контекста не меняются — повторные запросы получают скидку на входные токены (обычно 90% на кэшированную часть).

```ts
// Структура промпта для максимального cache hit rate
const messages = [
  // Кэшируемая часть (не меняется между запросами)
  { role: "system", content: STATIC_SYSTEM_PROMPT },     // 2K токенов — кэш
  { role: "user", content: STATIC_EXAMPLES },            // 1K токенов — кэш

  // Некэшируемая часть (меняется)
  { role: "user", content: retrievedDocs },               // 5K токенов — без кэша
  { role: "user", content: currentMessage },              // 200 токенов — без кэша
];
```

Правило: **стабильное — в начало, меняющееся — в конец**. Это максимизирует длину кэшируемого префикса.

### Компромисс: качество vs стоимость

Сжатие контекста — не бесплатно. Summarization добавляет LLM-вызов (стоимость + latency). Truncation теряет контекст (качество ответа). Нужно находить баланс:

```ts
interface CompressionDecision {
  strategy: "none" | "truncate" | "summarize" | "hybrid";
  reason: string;
}

function decideCompression(
  historyTokens: number,
  budget: number,
): CompressionDecision {
  if (historyTokens <= budget * 0.5) {
    return { strategy: "none", reason: "История в пределах бюджета" };
  }

  if (historyTokens <= budget * 0.8) {
    return { strategy: "truncate", reason: "Умеренное превышение — обрезаем старые" };
  }

  // Сильное превышение — сжимаем с сохранением контекста
  return {
    strategy: "summarize",
    reason: "Значительное превышение — суммаризируем старые сообщения",
  };
}
```

## Ключевые тезисы для интервью

- LLM API принимает разговор как массив сообщений с ролями system/user/assistant; модель не различает «старые» и «новые» сообщения — она видит единый упорядоченный контекст.
- Модель stateless — приложение хранит историю и передаёт её целиком в каждом запросе; «продолжение разговора» — это вся история + новое сообщение.
- Контекстное окно — фиксированный ресурс, который делится между system prompt, историей, текущим запросом и ответом; когда история заполняет окно, нужна стратегия сжатия.
- Три базовые стратегии сжатия: truncation (обрезка старых сообщений), sliding window (последние N обменов), summarization (сжатие старых сообщений в резюме через LLM).
- Комбинированная стратегия: последние N обменов — как есть, старая история — в резюме; сохраняет и недавний контекст, и общую картину.
- Феномен «lost in the middle»: начало и конец контекста обрабатываются лучше середины; критические инструкции — в system prompt (начало), текущий запрос — в конце.
- Статический контекст (system prompt, инструкции) — кандидат на prompt caching; динамический (история, RAG, текущий запрос) — меняется каждый раз.
- Стабильное — в начало, меняющееся — в конец: это максимизирует cache hit rate и снижает стоимость.
- Динамическое в статическом (дата, имя пользователя в system prompt) ломает кэш — выносим в user message.
- Стоимость растёт линейно с размером контекста; сжатие истории с 50K до 20K токенов при 100K запросов/день экономит ~$2,700/мес.

## Заключение

Управление контекстом — архитектурная задача, а не деталь реализации. Модель не помнит разговор между запросами, и весь контекст — ответственность приложения. Когда история растёт, нужно решать: что обрезать, что сжать, что оставить.

Ключевые выводы:

- **Контекст — конечный ресурс** — делится между system prompt, историей, запросом и ответом; без управления история неизбежно превысит окно.
- **Truncation дёшев, но слеп** — обрезает старые сообщения без сохранения контекста; summarization сохраняет общую картину, но стоит денег и теряет детали.
- **Комбинированная стратегия — рабочая точка** — последние N обменов как есть + резюме старой истории.
- **Порядок сообщений влияет на качество** — критические инструкции в начало (system prompt), текущий запрос в конец; RAG-документы — рядом с запросом.
- **Разделение статического и динамического** — основа для prompt caching: стабильное в начало, меняющееся в конец.
- **Стоимость масштабируется с контекстом** — сжатие истории в 2.5× при массовых запросах экономит тысячи долларов в месяц.
